# Architecture / 现行架构

> **语言 / Language / 語言 / 言語**：[繁體中文](../zh-tw/架構.md) | 简体中文 | [English](../en/architecture.md) | [日本語](../jp/アーキテクチャ.md)

Marketing Workbench 提供多品牌的内部营销工作空间。品牌、账号、内容及 prompt 彼此隔离；后台用户有 admin／marketing／viewer 权限。

## Agent 入口

内部 `/mcp` 使用 MCP SDK 的 Streamable HTTP，与 FastAPI 网页服务同端口，公开边界仍只放行既有 Webhook／媒体。Agent 以成员自己的 OAuth 授权或连接令牌登录；Bearer 仅用于 `/mcp`，网页 API 维持 session、CSRF 与 Origin 检查。每次工具调用都重新读取成员状态、角色与品牌范围；依 `docs/cn/MCP规范.md`（[MCP 规范](MCP规范.md)）提供查询及营销／管理员的选题、脚本保存回写，接口版本仍为 1。

`agent_tools` 统一工具说明、输入验证、审计与响应大小；`agent_queries` 明确投影遮蔽内容，`agent_content` 沿用领域服务。Agent 报告 provider=agent，来源存于 data_json.source（连接名与 grant id）。既有评论 worker、jev 分类与汇总完成后停在 awaiting_ideas，不调用文本 AI；既有 ideation 定时任务会把等待超过 24 小时的报告标为失败。用户在对话中定稿后存回十五个选题，沿用 ready／编辑／导出流程，保留 Agent 来源。脚本每次新增 VideoScript 与 ScriptVersion，同一选题的旧稿保留。没有数据表变更或新 migration。

0037 新增客户端、授权、待批准请求、授权码与令牌数据表；机密只存哈希。授权码绑定客户端／回调／S256 PKCE，refresh 每次轮换，重复使用会撤销整个授权。连接闲置 30 天失效，停用或重置密码立即撤销；使用时间每分钟最多写入一次，既有定时任务每小时清理过期数据。旧 Hermes stdio MCP 已移除，Hermes 改以查看者账号连接 `/mcp`（见 `docs/cn/MCP规范.md`（[MCP 规范](MCP规范.md)））。

## noinbox 范围

收件箱、回复草稿／检查／发送、价目表、转人工条件、主管与路由指派、待回复／期限提醒及成交进度已移除。工作台只接收帖子评论。评论 Webhook、分类队列、公开评论紧急通知、选题策划、脚本及导出保留；私信数据由部署者备份后以独立 purge 脚本删除，不新增 migration。

分类继续保存 Classification 的意图、原始响应、signals、版本与指纹；新 action 为 classified（垃圾／无文字为 skip），不再指派人员。历史字段及表格保留。定时任务只有 classify、notify、comments、metrics、ideation。脚本的禁止承诺检查改由 content_safety 共用。紧急通知只涵盖公开评论中的客诉、高紧急度与公开声誉风险，不含工作台对话链接；旧的一般／期限通知不再发送。

## 技术与数据

- FastAPI 对原始字节验签；LINE inbound 通过后一律回 200 并丢弃，不保存或查询 profile。Meta messaging 丢弃，feed comments／IG comments 成功持久化后才 ACK。LINE notify 仍由独立凭证接收群组事件。
- SQLite WAL 为唯一业务数据源；SQLAlchemy 2 管理数据访问，结构升级用 Alembic。事件以平台外部 ID 唯一键 upsert，重发不会重复。
- 后端内置分类、通知、数据、选题策划定时任务；评论 worker 仅接续用户已点按钮创建的一次性任务。各自持久化租约、游标、定时开关与结果，不依赖外部工作流引擎。
- ngrok 指向后端 loopback；Traffic Policy 及后端双层阻挡公开 UI/API、路径穿越与转发来源伪装。管理界面只供本机／Tailscale 使用。
- 公开评论在帖子页只读；DM worker、回补服务与 API 已移除。历史 DM 表格／字段保留以兼容既有 schema，数据删除使用 scripts/purge_direct_messages.py。选题策划的来源选取保持本次基准，既有报告不删除。

### 界面语言

- 支持繁中（默认）、简中、English、日本語。`frontend/src/i18n.ts` 的 `t('繁中原文', 變數)` 以繁中原文作为键，繁中不查表；其他语言查 `frontend/src/locales/<語言>/` 的翻译表，缺翻译时退回繁中。翻译表按语言动态加载，`main.tsx` 先 `initLanguage()` 再加载页面，因此模块级常量也会是正确语言；切换语言时刷新页面。同一原文在不同位置需要不同译法时用 `tx('情境', '原文')`；用词以 `docs/cn/i18n术语表.md` 为准。
- 语言偏好存在 `staff.language`（0051，可为空），由 `PUT /api/auth/language` 设置，所有角色都能改自己的；登录前记在 localStorage。
- 后端仍返回繁中错误，`api.ts` 拿 `detail` 去查表（`locales/*/backend.ts` 收录固定信息）；需要比对特定错误时用原文比对。日期与数字格式跟随界面语言，时区仍固定为 Asia/Taipei。

### SQLite 事务与锁定

SQLAlchemy 统一发出 BEGIN，连接初始化的 PRAGMA 在事务外执行；维持 WAL、外键及五秒 busy timeout。`session_factory()` 的显式 `session.begin()`／`factory.begin()` 是写入边界，以 `BEGIN IMMEDIATE` 在第一个查询前取得写锁；普通 `factory()` 的自动事务则使用 `BEGIN` 保留读取快照，不占用写锁。写入不得沿用可能过期的读取快照；一般请求先结束干净的读取事务，通过 `ensure_write()` 建立写入事务并重新读取／验证。此函数拒绝丢弃尚未提交的变动。新增写入路径必须使用这些边界，嵌套事务仍由 SAVEPOINT 处理。

WAL 的读取快照若在另一连接提交后升级为写入，SQLite 会返回 `SQLITE_BUSY_SNAPSHOT`（517），busy timeout 无法解决。取得写锁时最多尝试三次，每次沿用五秒 timeout，中间等待 0.05／0.15 秒，最长约 15.2 秒（不含系统调度）。只重试尚未执行任何业务 SQL 的 BEGIN；不重放已执行的 SQL、模型或平台调用，也不增加后台任务的业务重试轮数。耗尽时返回 `503`、`Retry-After: 1` 与中文可重试说明；其他错误按原规则处理。

外部服务、jev、模型都在写入事务提交后执行；结果与用量记录另开短写入事务。脚本／策划内容先保存在当次执行的内存中，取得存档锁的有限重试不会再生成内容。权限、版本、租约／claim 与迟到结果的检查仍在写锁内。读取事务不得被当成写入事务，只读 GET 不会因此取得写锁。

异步策划报告若连失败状态也无法入库，只在进程内存中保留最多 128 条“数据库位置、报告 ID、该次租约”的存档失败标记，不保留异常或生成内容。查询维持数据库的 processing 状态并显示中文错误、允许人工重试；新租约或完成结果不套用旧标记。重启会清除标记，仍依数据库原有的 30 分钟租约到期规则恢复重试。这是临时的操作状态，SQLite 仍为唯一业务数据源。

依据：[SQLite 隔离与 BUSY_SNAPSHOT](https://www.sqlite.org/isolation.html)、[SQLAlchemy SQLite 事务控制](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#enabling-non-legacy-sqlite-transactional-modes-with-the-sqlite3-or-aiosqlite-driver)。不新增数据表或 migration；Alembic 连接设置配合由 SQLAlchemy 管理 BEGIN，升降级验证仍必须通过。


## 私信窗口与评论同步范围

私信 messages 由新到旧读取；含早于日期下限的页面先导入窗口内的消息，再结束该对话。conversations 请求保留 `id,updated_time`，略过日期下限以前的对话；响应时间持续由新到旧时在边界结束探索，缺少时间或顺序反转则保守翻页。全部历史不套用日期停止条件。同一 messages 游标的连续超时／5xx 计数持久化于进度中，成功读页后归零；达到 `META_DM_CURSOR_RETRY_LIMIT`（默认 5）后结束该对话，计入平台未响应的部分未完成对话，其他对话继续，任务可完成。提示沿用等待样式。

评论只由帖子详情页“抓取评论”创建单篇一次性读取，管理员／营销可抓取及停止，查看者只读；品牌权限、CSRF 与 `comments.request`／`comments.stop` 审计均由后端执行。同一帖子的唯一状态在写锁下去重。没有手动任务时定时任务不执行评论 worker；帖子列表与效果指标仍由 metrics worker 同步。旧的批量同步／回补 POST 返回 410，不再探索帖子或排队。旧 `META_COMMENTS_AUTO_DAYS` 在设置解析时被忽略。

cwindow：手动抓取依评论日期筛选设置 `window_start`，`window_end` 固定为所选截止日次日与请求时间中较早者，使用半开区间；只有明确 period=all 才令起点为 null。选题策划同样传入独立的评论范围，帖子发布期间仍只用于选帖；旧评论数据不删除。IG 使用 `comments?fields=id,text,timestamp,from{id,username},replies.limit(50){id,text,timestamp,from{id,username}}`；FB 使用 `comments?filter=toplevel&order=reverse_chronological&fields=id,message,created_time,from{id,name},parent{id},comments.filter(stream).order(reverse_chronological).limit(50){id,message,created_time,from{id,name},parent{id}}`。顶层及嵌套各请求最多 50 条。嵌套边不存在代表没有可见回复，不逐条补查；仅当嵌套 `paging.next` 存在时保存其 `cursors.after`，以该评论的 replies／comments edge 翻页。不使用平台返回的 next URL，避免携带凭证或指向非官方主机；游标缺少、重复或过长则报错。

主评论与回复分别在非空整页都早于 window_start 时停止翻页；混合页继续，缺少时间则报错。已读页的旧父评论仍可保存范围内的回复，但停止主评论翻页后不再探查更早父评论的回复。FB 明确使用 reverse_chronological；IG 沿用平台原生排序，不新增未列于官方 SDK 的排序参数。完成后立即解除手动排队，不再续抓。每次 worker 限 35 次 GET／50 秒，预算用尽或平台限速时保留固定窗口、游标、已处理页数及已存条数，沿用每小时配额、用量标头、退避与等待原因接续同一任务。可处理的网络临时故障也保留重试；权限、凭证或无效响应等需要人工介入的错误结束本次读取，由用户处理后重新点按钮。

停止会先撤销 run_id／租约并清除手动排队，保留消息与已保存的进度。已在网络中的 GET 无法撤回，其结果在撤销后不能写入评论，也不能再发出下一个 GET。重新抓取从新的固定窗口及第一页开始，依平台 ID 去重。0025 migration 安全结束所有旧评论任务及回补探索，清空旧游标与定时任务所有权，保留所有业务数据及最后成功时间，不复活旧任务。

显示只查 DB：详情页默认近 30 天，提供 7／30／90 天台北日历筛选；每页 50 组并附范围内的回复，“显示更多”只读下一批。父评论不在范围内或未入库时，具有相同明确父 ID 的回复合为一组并标示父评论不可见，不补造或抓取父评论正文。旧 API 的全部／自定义日期保留，供既有报告定位与查询，详情页不提供该选项。状态轮询只读 DB，不触发 Meta。

官方参考：[Field Expansion](https://developers.facebook.com/docs/graph-api/guides/field-expansion/)、[IG media comments](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-media/comments/)、[IG comment replies](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-comment/replies/)、[FB object comments](https://developers.facebook.com/docs/graph-api/reference/object/comments/)。本次上述参考页返回 429，未宣称成功读取；字段／edge 交叉核对了 [Meta 官方 IGComment SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/igcomment.py) 与 [Comment SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/comment.py)，并以三次 IG 只读 GET 确认嵌套读取、空边省略及独立分页。正式库副本无 FB 帖子；另两次 FB 只读 GET 取得一篇帖子，展开查询返回 200 但没有评论，未宣称实测到 FB 回复分页。FB 回复以官方 SDK 与 HTTP mock 覆盖，部署者须核对有评论的帖子的实际回复与平台可用性。

## 粉丝数追踪

`follower_snapshots`（0026）保存账号、UTC 观测时间及非负整数粉丝数，账号／时间唯一键避免重发重复。数据表与每日记录流程不变。`GET /api/posts/followers` 必填 `platform`，可传 `brand_id`、`account_id`、`year`、`month`、`week`；省略年月周时选台北今天所在的年月周。沿用帖子的登录及品牌权限，admin／marketing／viewer 均可读，查询只读本机 DB，不触发平台或模型。

返回平台连接状态、有快照的年份（至少包含今年）、月内各周日期、当前数量、所选周／月增减及是否为当周／当月；另保留各账号数值，支持单账号筛选。平台工具栏合计可见账号，任一账号缺少该期数据时该合计为 null，避免把未知当零。快照输入采用共用平台类型，未来的平台抓取器可沿用同一数据表、写入服务、API 与显示，不需复制计算逻辑。

周一为一周起点，并以台北月份边界切开：2026 年 10 月第 1 周为 10/1–10/4、第 2 周为 10/5–10/11、第 5 周为 10/26–10/31；2027 年 1 月第 1 周为 1/1–1/3。周月边界采用台北 00:00，结束含末日并最多计算到查询当下。每个日期取最后一条；基准沿用边界快照或此前最后一条，起点早于首次记录时以第一条原始快照为基准。完全没有该期快照时返回 null；负值保留负号，不补造缺失日期的数据。当前数量永远取最新快照。

粉丝数放在各平台标签页下方，FB／IG／Threads 共用精简粉丝工具栏，桌面端下拉菜单与三项行内数字合为一行，768／390px 时下拉菜单一行、数字一行；切换年份、月份、周次即查询，选择历史周月时改用“该周／该月”标签。未连接的平台显示指定提示。区块自然撑高、使用共用尺寸／内边距变量；手机上可换行。自定义日期、每日序列、折线图、起记／快照时间及基准说明已移除；旧 `date_from`／`date_to` 查询返回 422，没有其他粉丝数 API 用户需要保留此功能。帖子效果的日期筛选与图表不变。

既有每小时 metrics 定时任务先检查粉丝快照，再同步帖子指标，没有当日快照才调用 FB／IG 的 `GET /{account-id}?fields=id,followers_count`，或 Threads 的 `GET /v1.0/{threads-user-id}/threads_insights?metric=followers_count`。Threads 使用独立令牌与既有数据权限闸门，缺权限时略过、权限错误时暂停；不经 Meta 配额，格式／数值异常时不写入并记录错误。正常情况下每天每个账号额外一次 GET（FB＋IG 为两次），不需读取任何 Insights 历史；失败可在后续定时任务中重试，仍受共享的每小时调用上限、usage headers 及 Retry-After／退避限制。启动时请求一次 metrics 定时任务，以免持久化的下次执行时间推迟第一条记录；停用定时任务时不执行。发布成功与帖子数据的“立即同步”也各请求一次：立即同步限管理员／营销，后端以 `scheduler.manual.metrics` 记录最近请求时间，60 秒内再点返回 429；已排入或执行中时不重复排入、不计冷却；审计 `scheduler.request`。实际调用仍受上述共享每小时上限与用量标头退避限制。字段失败不妨碍可执行的帖子同步，定时任务结果另列 `followers` 错误，既有快照保留。

IG 与 FB 均只用 `followers_count`。官方字段参考：[IG User](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/)、[Page](https://developers.facebook.com/docs/graph-api/reference/page/)。本次文档页返回 429，字段以 [Meta 官方 IGUser SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/iguser.py) 与 [Page SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/page.py) 交叉核对，两者都列出 `followers_count`。本次未调用实机 Meta API；平台授权可用性仍由部署者核对。未返回字段时记录失败，不写零值；`fan_count` 是语义不同的公共主页字段，不自动混入序列。

## 受众分析（0052）

`audience_insights` 每个账号、每种分布（`metric` followers／viewers／online × `breakdown` age／gender／country／city／hour）只存最新一份，含状态（ready／unavailable）、缺数据代码（permission_missing／not_available／no_data）、平台统计期间、单位（count／percent）、`items_json` 与取得时间；每天覆写，不保留历史。抓取挂在每小时 metrics 定时任务的缩略图之后（`Workers.audience`），每个账号每个台北自然日一次：同一账号的各项全部拿到结果才一起写入；网络、限流、5xx 或格式异常不写入，下一轮重试；平台明确拒绝（权限、门槛、指标不支持）时存为 unavailable，当天不再尝试。没事可做时返回 0，定时任务视为空跑。断开账号的数据删除会一并删除。

- **Instagram**：`GET /{ig-user-id}/insights?metric=follower_demographics&period=lifetime&timeframe=this_month&metric_type=total_value&breakdown=age|gender|country|city`，四次；另 `metric=online_followers&period=lifetime&since&until`（近 7 天）一次。online_followers 每天一组 0–23 时（太平洋时间的一天，`end_time` 为次日太平洋时间午夜），换算成台北时段后取平均。权限沿用 `instagram_manage_insights`；粉丝不足 100 人时平台不返回数据。
- **Facebook 公共主页**：`GET /{page-id}/insights?metric=page_follows_country,page_follows_city&period=day` 一次，取最新一天。`page_fans_gender_age` 等年龄／性别指标 Meta 已于 2024-03-14 停用，没有替代；`page_fans_country／city` 于 2025-11-15 停用，官方替代为 `page_follows_*`。
- **Threads**：`GET /{threads-user-id}/threads_insights?metric=follower_demographics&breakdown=…`，四次（官方一次只允许一种 breakdown），沿用 Threads 数据权限闸门；权限错误时暂停并保留前一天的数据，一般 API 错误（多半是不足 100 人）存为 not_available。
- **YouTube**：YouTube Analytics `reports`，近 28 天（截至太平洋时间两天前）`dimensions=ageGroup,gender&metrics=viewerPercentage` 与 `dimensions=country&metrics=views&sort=-views&maxResults=10` 两次，计入既有 `youtube.quota`。年龄／性别只含已登录的观众。
- **TikTok、LINE**：不调用。Display API 没有受众数据；LINE 只用于通知。界面直接显示原因。

Meta 调用经 `meta_api` 记录，并受每小时上限、冷却与 usage headers 限制，限流后同一轮不再调用其他 Meta 账号；正常情况下每天 IG 五次、FB 一次。`GET /api/dashboard/audience` 可选 `brand_id`，沿用账号的品牌权限，admin／marketing／viewer 都可读，只读本机 DB。仪表盘“受众分析”卡片以平台分段切换（网址参数 `audience_platform`），能取得的项目以条形图（人数换算为占比）或 24 小时柱状图呈现，缺数据或平台不提供时显示原因。国家代码以 `Intl.DisplayNames` 按界面语言显示。实机响应格式未验证：FB `page_follows_*` 的值格式比照旧 `page_fans_country`（`{代码: 人数}`），Threads `follower_demographics` 比照 IG 的 `total_value.breakdowns`，部署后须核对。

## AI 与消息分类

官方 Gemini／OpenAI／Anthropic 共用应用层重试，SDK 内置重试关闭。408、一般 429、500、502、503、504 与连接／读取超时最多尝试 4 次，等待 2／5／10 秒，各加 0–0.25 秒抖动；优先采用 Retry-After（秒数或 HTTP 日期）及 Google `google.rpc.RetryInfo.retryDelay`。供应商建议的等待超过剩余时间时立即报告，不空等、不提前重发、不延长上限。

Google 429 的错误内容含 `free_tier` 时返回 `provider_quota_free_tier`，视为短时间重试无效，立即结束且不切换同供应商备用模型；其他 429 返回 `provider_rate_limited`。OpenAI 429 的 `insufficient_quota` 或账务／支出上限代码返回 `provider_quota_exhausted`，不重试、不切换备用模型；Anthropic 429 的 `rate_limit_error` 返回一般限速代码，不凭该代码推断账务原因。只保存代码与有限的非负等待秒数，以既有错误字段的 `;retry_after_seconds=N` 附注供 UI 使用，不保存供应商错误原文或绝对单调时钟，无数据表变更。

品牌 `ai.brand.<id>` 设置新增三家的 `*_fallback_model`，沿用品牌写入权限、版本冲突检查与 `ai.settings` 审计。Gemini 默认 `gemini-3.7-flash`，其他供应商默认为空；明确留空即停用备用模型，主模型与备用模型相同时不重复切换。主模型重试后仍为 408／一般 429／5xx／超时／连接故障时才切换到同供应商备用模型，永久错误及未完成／遭拒的内容立即结束。主备模型共用 `AI_API_TIMEOUT_SECONDS`（默认 60 秒）；有备用模型时预留 `max(20 秒, 总时限 / 3)`，默认主模型最多 40 秒。退避后若不足 10 秒即需发出下一次请求，则停止主模型重试并交给备用模型；主模型提前结束所省下的时间也可供备用模型使用。备用模型最多 4 次，每次 SDK timeout 为该阶段的剩余时间。每次请求前剩余少于 10 秒时禁止建立请求，返回 `provider_time_exhausted`。较短的总时限可能直接略过主模型，且无法保证超过总时限的 20 秒；总时限不足 10 秒则全程不发请求。最后一次响应的 Retry-After 也适用于备用模型；若等待会侵占备用模型的保留时间，直接报告限速／供应商错误，不空等也不提前请求。

Gemini 配额按项目管理，实际限制因模型与方案而异；不把个别错误中的限额当成整体默认值。免费方案额度失败采用保守的停止策略，不能假设备用模型会解除限制。持续使用建议到 Google AI Studio 为该项目设置付费账务，再核对有效配额、用量与预算。官方说明：[Gemini 配额](https://ai.google.dev/gemini-api/docs/rate-limits)、[账务设置](https://ai.google.dev/gemini-api/docs/billing)、[OpenAI 错误代码](https://developers.openai.com/api/docs/guides/error-codes)、[Anthropic 错误代码](https://platform.claude.com/docs/en/api/errors)。

文本模型与后台任务只使用 Gemini、OpenAI、Anthropic 官方 API 密钥；本地 CLI 已移除，写作改由 Agent 处理。所有发往云端的文本先遮蔽个人信息，模型用量按品牌追踪。共用与品牌 prompt 具有版本、差异及还原功能，不能放宽后端护栏。

jev 使用 TypeSafe v1 的 Choice／Noul／Score；每题以反引号引用具名的 state 字段，客人文字与待审内容视为数据。同一 state 的独立问题一次发送，全部经过 `redact.scrub` 与 `jev.valid_response`。Choice 保留“不符合”出口；Noul 是条件成立的概率，接近 0.5 并不表示中等强度；Choice／Score 的 confidence 是分布集中度。既有政策与阈值不变，调整前须先用标注数据评估。依据：[提问](https://docs.typesafe.ai/primitives)、[state](https://docs.typesafe.ai/concepts/state)、[confidence](https://docs.typesafe.ai/confidence)。

品牌类别补充说明以 `classification.intents.brand.<id>` 存入 Setting，九个意图代码固定，每段去除首尾空白且最多 200 字，未知字段拒绝。`GET/PUT /api/classifications/intents?brand_id=` 沿用品牌权限、设置版本冲突 409 与 `classification.intents` before／after 审计。通用服务说明后附加品牌示例，并明示示例不是指令；发往云端前仍经 redact。`QUESTION_VERSION=triage-2026-10-23-v3`，raw_json 保存 `intent_notes_version`；补充说明不加入 context／fingerprint，指纹固定沿用 `triage-2026-09-26-v3`，既有结果保持有效，不重算、不重排任务，新设置只影响后续的新消息与手动重新分流。

分流 state 明确规定 sender 为客人，消息与遮蔽计数不会被 context 中的同名字段覆盖；提问版本与 input hash 版本分开，措辞改版时保留既有结果的效力。人工重新分流或新的既有任务才采用新题目；政策重算仍仅套用已存信号。选题分类的提问版本同样独立于指纹，不会因措辞改版触发付费重算，既有分类流程仍受原有 limit／预算限制。

代表原话的 Choice 可返回 none，此时保留已选来源并停止，不凑满五条；后续选取依已选结果更新 state，因此仍逐次请求。CSV state 使用 `columns.column_<index>`，question ID 与返回列索引不变，保留 ignore。`scripts/eval_jev_questions.py` 以五组合成数据（分流十六例、其余各八例）比较固定的旧问法与现行 builders；默认使用 transport 替身，只有 `--live` 才连接官方 API，输出限于 `.runtime/`。替身通过只证明管道可运作，不代表质量改善。

## 品牌中立设置

`settings.workspace.display_name`（实际 key 为 `workspace.display_name`）保存产品名称。公开的内部登录识别 API 只返回名称及版本；修改限管理员且有审计。登录页、导航、页眉、标签页标题、Word 页眉共用此值。

`ideation.brand.<id>` 保存例会与选题；新默认值为停用、星期／时间留空、选题只有“其他”。`brand.rules.<id>` 保存禁用词；默认为空列表。历史价目数据保留，但没有操作入口。

模板是受版本控制的 JSON；管理员先预览差异，再以包含品牌状态及模板内容的哈希确认。套用在单一数据库事务中更新选题、禁用词、品牌 prompt 新版本，保留例会及发送权限。任何数据变动都会使旧预览失效。

内容研究只使用真实证据；报告须引用同一选题的实际消息 ID，数量不足时不补造。品牌内容直接来自设置与 prompt，不读取特定的外部知识库。脚本可编辑、重新检查及保存版本，不能发布平台内容。

## 仪表盘营销摘要与每日趋势

`GET /api/dashboard` 统计台北时间周一 00:00 至查询当下，返回 new_messages（既有非历史私信）、new_comments（公开 comment_thread 中 direction=in／author_type=fan 的消息数，含期间内补抓的评论）、top_intent（本周非历史客人消息中最新且指纹有效的分类，排除 spam／未知代码）。热门分类包含私信与公开评论，数量相同时按代码排序；无数据时返回 null。每个品牌只建立一次分类 context。问题分布维持本周新私信的最近分类。移除 pending_threads、first_reply_seconds、first_reply_samples、stages 与相关查询。

`GET /api/dashboard/trends?days=30` 可选 brand_id，沿用 Access；days 仅限 7／30。响应 `{days, timezone: "Asia/Taipei", series: [{date, new_messages}]}`，按台北自然日补齐零值。摘要及趋势共用 incoming_messages，依 sent_at 计算、排除历史私信，不计未来的消息。

趋势只做一次批量 SELECT，在内存中按日聚合，不开写入事务、不触发平台／模型。沿用索引，没有 migration。test_workspace 保留 2,000 条／500 段、只读及 300ms 上限（CI 1 秒），改为验证只有一次 SELECT。导出报表原本就没有上述客服 KPI，格式不变。

### 增长比较与转化漏斗（2026-10-16 补上延后项目）

- 摘要多返回 `previous: {start, end, new_comments}`：上周一 00:00 到七天前的此刻（与本周等长，终点不含）。趋势多返回 `previous_total`：紧接在窗口之前、等长的前 7／30 天新评论总数，与序列在同一次 SELECT 中取得。前期为 0 时前端不计算百分比。
- `GET /api/dashboard/funnel?days=30` 可选 brand_id，权限同趋势；days 仅限 7／30。总体是近 N 天（台北自然日）发布、未删除、最新快照有 reach 的帖子；四个阶段依次为覆盖人数（reach 合计）、互动（likes＋comments＋shares＋saves 次数合计，可能多于覆盖人数）、评论（这些帖子的客人入站评论数）、消费咨询（其中最新且指纹有效的分类为 price／booking／model_question）。响应 `{days, timezone, posts, stages: [{key, value}]}`，转化率由前端以上一阶段计算。原规划的“成交”阶段已随 noinbox 移除，不再出现。

## 帖子缩略图缓存（0046）

平台 CDN 的图片网址会过期，所以每篇帖子另存一张缩小的 JPEG（最长边 480px）在 `post_thumbnails`（每篇一行，data 延迟加载）。抓取挂在每小时的 metrics 定时任务后面，由 `post_thumbnails.hourly` 每轮最多处理 20 篇（新帖子优先）：FB 读 `GET /{post-id}?fields=full_picture`，IG 读 `media_type,media_url,thumbnail_url`（视频只取封面），Threads 读同名字段，TikTok 用 Display API `POST /v2/video/query/`（`fields=id,cover_image_url`，需 `video.list`，连接条件与 TikTok 同步相同）取当下有效的封面网址后立刻下载（封面网址会过期；列表中没有该视频代表已删除或改为私密，标为 unavailable；限流或授权失效时整轮略过 TikTok，不扣重试次数），YouTube 直接用公开的 `i.ytimg.com/vi/{id}/hqdefault.jpg`，不消耗 Data API 配额。FB／IG 每篇一次 Meta 调用，经 `meta_api` 记录并受每小时上限与冷却限制，冷却中整轮略过 Meta。图片只从 `fbcdn.net`／`cdninstagram.com`／`ytimg.com`／`tiktokcdn.com`／`tiktokcdn-us.com`／`tiktokcdn-eu.com` 的 https 网址下载（其他主机记录 `thumbnail_untrusted_host` 警告，只含主机名；TikTok 封面域名文档没写，遇到未知域名走重试而非直接放弃），不跟随重定向，来源上限 8 MB，以 Pillow 缩小后转为 JPEG（透明背景转白）。纯文字或已删除的帖子标为 unavailable，不再尝试；网络、限流等临时失败按 1／6／24 小时重试，第四次仍失败即停止。`GET /api/posts/{id}/thumbnail` 沿用帖子的品牌权限返回图片；帖子列表、单篇与仪表盘排行返回 `thumbnail_url`（含摘要片段作为缓存破坏），没有缩略图时为 null。只读官方 GET，不写入平台；验收以 HTTP 替身进行。

- 读到 CLI 类型的设置值（品牌 `ai.brand.<id>` 的 `default_provider`、`manual_provider`、`background_provider`）时视为未设置，`ai.config` 只在读取时转换，数据库原值保留；`AISettings` 写入只接受三个 API 供应商与空值，旧值不会阻挡预算或备用模型的保存。全局 `ai.local_cli`、`ai.cli.*` Setting 不再被读取，也不删除。

平台：Facebook 公共主页、Instagram、Threads、YouTube、TikTok（只发送到收件箱，需在 App 内完成发布）；格式：短视频、图片、轮播、纯文字、快拍（限时动态）。目标账号跟随当前品牌在“平台连接”中设置的账号。

- **规则与检查**：一份主文案，可按平台覆写。规则集中在 `backend/app/services/publish_rules.py`：`RULES`（文案、时长等，原样返回给前端）与 `MEDIA_RULES`／`IMAGE_BYTES`／`VIDEO_BYTES`（媒体比例、宽度、大小、mime），`GET /api/publish/options`、Agent `get_publish_options`、上传检查与 Agent 上传共用同一份（字数、hashtag、视频长度／比例、文件大小、mime、宽度）。不符合的平台标红并阻止发布；系统不自动截断、改写或转码（唯一例外：发往 Instagram 的 PNG 转为 JPEG）。平台不支持的格式直接停用并说明（例如 Instagram 不支持纯文字、YouTube 只支持视频）。
- **定时发布**：立即发布或指定台北时间，由工作台调度器每分钟执行，到期帖子交给后台线程发布（调度器不等待上传完成，长时间上传不会让其他同时到期的帖子被标为已错过）；定时前一分钟起锁定编辑／取消。逾期超过五分钟不补发，标为“已错过”并通知，由用户决定立即发布或重新定时。总开关关闭时暂停所有定时发布，重新开启后未到期者照常、已过期者标为已错过。
- **部分成功与重试**：成功的平台永不重发；只能“仅重试失败的平台”。服务启动时把中断的 publishing 标为 interrupted，不自动重发，由用户先到平台确认再决定是否重试。多段内容（Threads 串文、多则快拍）每成功一段即以短事务保存平台 ID，失败后重试只接续剩余段；已有成功段时锁定分段、素材与账号。结果无法确认的超时须人工核对平台，避免重复发帖。发布途中的非预期错误会把未完成的平台标为 `unknown`（请到平台确认）并结算帖子，不会卡在发布中。取消定时或标为已错过时，未发送的平台中未尝试者被移除、尝试过者回到失败；每次发送只发本次选定且仍勾选的平台。
- **媒体**：以随机文件名存于 PUBLISH_MEDIA_ROOT；全部平台成功后 30 天清除，其他状态保留。IG／Threads 需要公开网址时建立 `/media/<權杖>`（令牌）临时链接（15 分钟或取用完成即撤销，最多 32 次，无效一律 404，纳入公开边界检查）；YouTube 由工作台直接上传，不用临时链接。
- **Facebook 未发布帖子**：`facebook_unpublished` 以 `published=false` 建立，只影响 Facebook；Facebook 已成功或发布中后锁定，重试沿用原选项。不会出现在 `/published_posts`，因此不抓取效果；已删除判定改为逐篇查询（先确认能读到公共主页，返回 100/33 或 10 才算不存在，其他错误不判定）。
- **Reels 与 Threads 串文（composer1，0041）**：FB Reels 走 start → rupload → finish；与未发布同时选择时改以 feed 建立并提示。IG 只有 `share_to_feed=false` 时才明确发送该参数。IG Reels 封面（0048，`publish_media.role=cover`，绑定在 `instagram.cover_media_id`，由服务端维护）以限时公开链接作为 `cover_url` 发送，PNG 走 `.jpg` 衍生文件（官方只收 JPEG）；没有封面时请求维持原样（平台用第一帧）。IG 已成功／发布中后不能换封面。FB 视频／Reels 封面（0049，`role=fb_cover`，绑定 `facebook.cover_media_id`）在帖子成功并保存后才以 `POST /{video-id}/thumbnails`（`source`＋`is_preferred=true`）套用，结果写在目标的 `detail.cover`；失败不影响帖子，可“重新应用封面”（`POST /api/publish/posts/{id}/facebook-cover`，绝不重传视频）。需要可选权限 `pages_manage_engagement`（`oauth.META_OPTIONAL_SCOPES`）：授权时一并请求，缺少时不影响连接状态与发布就绪，发布选项只返回 `cover_hint`。Threads 第一段附素材，后续以 reply_to_id 串接；自动分段优先按空行／换行，其次按句末标点，最后硬切，不加编号，emoji 按 UTF-8 字节计算。平台 ID 与删除检测只看第一段；FB 视频与 Reels 记录视频 ID，与 `/videos` 列表比对。
- **快拍（限时动态，composer3，0042）**：`format=story`，1–10 则，每则一张图片或一个视频，只限 FB／IG，不带文字或帖子选项。IG 已成功的各则在 24 小时内每小时读取 insights，或收到验签的 `story_insights` 最终快照即停止；不支持的指标留空，不补零。FB 快拍暂无效果数据。快拍不做已删除判定。
- **YouTube（ytpublish，0043）**：需要 `youtube.upload` 范围（不要求更广的 `youtube`／`force-ssl`），缺少时发布标签页变灰并引导重新连接。官方 resumable upload：8 MiB 分段，中断或 5xx 时以 1／2／4／8／16 秒退避最多 5 次，每次先询问已接收的字节再续传；会话 404 时重新开始一次；会话网址存于 `detail_json.upload`，不返回给浏览器或 MCP。视频完成后先保存 `video_id` 与实际公开状态，之后缩略图成败或中断都不会重传视频。缩略图另行 `thumbnails.set`，失败不影响视频成功，可“重新应用缩略图”；会被归为 Shorts（竖屏／正方形且 ≤180 秒）的视频停用缩略图（`RULES.youtube.shorts_thumbnail`）。调用 `videos.insert` 前扣除 `youtube.uploads` 每日额度，缩略图扣除共用的 `youtube.quota`。
- **已删除检测**：只以“完整列表中不存在”判定，不以单篇查询错误判定（FB 未发布帖子例外，见上）；任何一页失败、达到分页上限、格式异常或账号变更一律不判定。重新出现在列表中时清除 deleted_at。
- **安全**：“允许发布到平台”总开关（Setting `publishing.enabled`）默认关闭，只有管理员可切换；每次发布或定时前显示确认弹窗；每次发布写入审计；成功、部分成功、失败、已错过与令牌即将到期的事件排入既有的品牌 LINE 通知群组（不含媒体网址或凭证）。发布后只保留平台链接，不从工作台修改或删除平台帖子。

## 平台凭证（creds）

0031 新增 platform_credentials（provider／encrypted_key／version／时间）；所有字段（含 ID／官方 base URL）均以 Fernet 加密，主密钥仍只在 .env。既有 ai_credentials 的 jev 密文与版本迁到 JEV_API_KEY，不解密、不丢失原值；旧 AI jev API 保留兼容并共用新表。删除时以空密文保留版本，防止删除后重建让过期界面通过版本检查。

credentials.resolve(name, settings, session) 是平台设置的唯一解析入口，DB 优先，无覆写时才用 env；密文错误时不降级使用 env。不缓存数值，每个新请求／worker 操作都取最新值。Webhook 签名、身份、Meta Graph token／账号、LINE profile／通知、健康通知与 jev 都经过此入口；webhook_normalize.secret 对平台字段委派给它。Python 评估工具及 Node 平台设置脚本同样使用共用解析；Node 通过本机 Python 子进程取得设置，一次性 AES-GCM IPC 密钥只经 stdin 传递，stdout 只有密文，错误为固定文案，没有公开的解密 API。

GET／PUT／DELETE /api/credentials 与 POST /api/credentials/{group}/test 仅限 admin。写入时检查版本，审计只存字段名、动作、操作者；API 只返回 configured／source／mask／version／error。连接测试只在管理员明确点击时执行，写入本身不对外连接；Meta /me、LINE bot info 为单次 GET，jev 沿用既有 post_json 与 redact。固定 timeout、禁止 redirect、不返回原始响应／异常，jev URL 限官方端点。测试全部使用 HTTP／CLI 替身。
