# Architecture / 現行アーキテクチャ

> **言語 / Language / 語言 / 语言**：[繁體中文](../zh-tw/架構.md) | [简体中文](../cn/架构.md) | [English](../en/architecture.md) | 日本語

Marketing Workbench はマルチブランドの社内マーケティング用ワークスペースを提供します。ブランド、アカウント、コンテンツ、prompt は互いに分離されています。管理画面のユーザーには admin／marketing／viewer の権限があります。

## Agent の入口

内部の `/mcp` は MCP SDK の Streamable HTTP を使い、FastAPI の Web サービスと同じポートで動作します。公開境界で通すのは引き続き既存の Webhook／メディアだけです。Agent はメンバー自身の OAuth 認可または接続トークンでログインします。Bearer は `/mcp` 専用で、Web API は session、CSRF、Origin チェックを維持します。ツールを呼び出すたびにメンバーの状態、ロール、ブランド範囲を読み直します。`docs/jp/MCP仕様.md` に従って照会と、マーケティング担当者／管理者によるテーマ・台本の保存を提供します。インターフェースのバージョンは引き続き 1 です。

`agent_tools` はツール説明、入力検証、監査、レスポンスサイズを統一します。`agent_queries` はマスクされた内容を明示的に射影し、`agent_content` はドメインサービスをそのまま使います。Agent のレポートは provider=agent で、出所は data_json.source（接続名と grant id）に保存します。既存のコメント worker、jev 分類、集約が終わると awaiting_ideas で止まり、テキスト AI は呼び出しません。既存の ideation スケジュールは、24 時間を超えて待機しているレポートを失敗にします。ユーザーが会話で確定した後に 15 件のテーマを保存し、ready／編集／エクスポートの流れをそのまま使い、Agent の出所を保持します。台本は毎回 VideoScript と ScriptVersion を新規作成し、同じテーマの古い稿は残します。テーブル変更や新しい migration はありません。

0037 でクライアント、認可、承認待ちリクエスト、認可コード、トークンのテーブルを追加しました。秘密情報はハッシュだけを保存します。認可コードはクライアント／コールバック／S256 PKCE に紐づき、refresh は毎回ローテーションし、再利用されると認可全体を取り消します。接続は 30 日間使われないと失効し、無効化やパスワードのリセットで即時に取り消されます。使用時刻の書き込みは 1 分に最大 1 回で、既存のスケジュールが 1 時間ごとに期限切れデータを掃除します。旧 Hermes stdio MCP は削除済みで、Hermes は閲覧者アカウントで `/mcp` に接続します（`docs/jp/MCP仕様.md` を参照）。

## noinbox の範囲

受信箱、返信の下書き／チェック／送信、価格表、有人対応への切り替え条件、上長とルーティングの割り当て、返信待ち／期限リマインダー、成約の進捗は削除済みです。ワークベンチが受け取るのは投稿へのコメントだけです。コメントの Webhook、分類キュー、公開コメントの緊急通知、アイデア出し、台本、エクスポートは残しています。DM のデータはデプロイ担当者がバックアップした後、独立した purge スクリプトで削除します。migration は追加しません。

分類は引き続き Classification の意図、生のレスポンス、signals、バージョン、フィンガープリントを保存します。新しい action は classified（スパム／テキストなしは skip）で、担当者の割り当ては行いません。過去のカラムとテーブルは残します。スケジュールは classify、notify、comments、metrics、ideation のみです。台本の禁止された約束表現のチェックは content_safety に共通化しました。緊急通知は公開コメントのクレーム、高い緊急度、公開での評判リスクだけを対象とし、ワークベンチ内の会話リンクはありません。旧来の一般／期限通知はもう送信されません。

## 技術とデータ

- FastAPI は生のバイト列で署名を検証します。LINE inbound は検証を通過したら一律 200 を返して破棄し、profile の保存や照会はしません。Meta messaging は破棄し、feed comments／IG comments は永続化に成功してから ACK します。LINE notify は引き続き独立した資格情報でグループのイベントを受け取ります。
- SQLite WAL が唯一の業務データソースです。データアクセスは SQLAlchemy 2 で管理し、スキーマのアップグレードには Alembic を使います。イベントはプラットフォームの外部 ID をユニークキーとして upsert し、再送されても重複しません。
- バックエンドに分類、通知、データ、アイデア出しのスケジュールを内蔵しています。コメント worker は、ユーザーがボタンを押して作成した単発ジョブを引き継ぐだけです。それぞれがリース、カーソル、スケジュールのオン／オフ、結果を永続化し、外部のワークフローエンジンには依存しません。
- ngrok はバックエンドの loopback に転送します。Traffic Policy とバックエンドの二重で、公開 UI/API、パストラバーサル、転送元の偽装をブロックします。管理画面はローカル／Tailscale からのみ利用できます。
- 公開コメントは投稿ページで読み取り専用です。DM worker、取得補完サービス、API は削除済みです。過去の DM テーブル／カラムは既存 schema との互換のために残し、データ削除には scripts/purge_direct_messages.py を使います。アイデア出しのソース選択は今回の基準を維持し、既存のレポートは削除しません。

### 画面の言語

- 繁体字中国語（デフォルト）、简体中文、English、日本語に対応します。`frontend/src/i18n.ts` の `t('繁中原文', 變數)` は繁体字中国語の原文をキーとし、繁体字中国語では表を引きません。その他の言語は `frontend/src/locales/<語言>/` の翻訳表を引き、翻訳がなければ繁体字中国語に戻ります。翻訳表は言語ごとに動的に読み込みます。`main.tsx` は先に `initLanguage()` を実行してからページを読み込むので、モジュールレベルの定数も正しい言語になります。言語を切り替えるとページを再読み込みします。同じ原文で場所によって訳し分けが必要なときは `tx('情境', '原文')` を使います。用語は `docs/jp/i18n用語集.md` に従います。
- 言語の設定は `staff.language`（0051、空でも可）に保存し、`PUT /api/auth/language` で設定します。すべてのロールが自分の設定を変更できます。ログイン前は localStorage に記録します。
- バックエンドは引き続き繁体字中国語のエラーを返し、`api.ts` が `detail` で表を引きます（`locales/*/backend.ts` に固定メッセージを収録）。特定のエラーを判定する必要があるときは原文で比較します。日付と数値の書式は画面の言語に従い、タイムゾーンは Asia/Taipei 固定のままです。

### SQLite のトランザクションとロック

BEGIN は SQLAlchemy が一元的に発行し、接続初期化時の PRAGMA はトランザクションの外で実行します。WAL、外部キー、5 秒の busy timeout を維持します。`session_factory()` の明示的な `session.begin()`／`factory.begin()` が書き込みの境界で、`BEGIN IMMEDIATE` により最初のクエリより前に書き込みロックを取得します。通常の `factory()` の自動トランザクションは `BEGIN` を使って読み取りスナップショットを保持し、書き込みロックは占有しません。書き込みで、古くなっている可能性のある読み取りスナップショットを使い回してはいけません。一般的なリクエストは、まずクリーンな読み取りトランザクションを終了し、`ensure_write()` で書き込みトランザクションを作ってから読み直し／検証します。この関数は未コミットの変更を破棄することを拒否します。新しい書き込み経路はこれらの境界を使う必要があり、ネストしたトランザクションは引き続き SAVEPOINT で処理します。

WAL の読み取りスナップショットが、別の接続のコミット後に書き込みへ昇格すると、SQLite は `SQLITE_BUSY_SNAPSHOT`（517）を返し、busy timeout では解決できません。書き込みロックの取得は最大 3 回試行し、毎回 5 秒の timeout をそのまま使い、間に 0.05／0.15 秒待機します。最長で約 15.2 秒です（OS のスケジューリングは含みません）。リトライするのは、業務 SQL をまだ 1 つも実行していない BEGIN だけです。実行済みの SQL、モデルやプラットフォームの呼び出しは再実行せず、バックグラウンドジョブの業務リトライ回数も増やしません。使い切ると `503`、`Retry-After: 1`、中国語のリトライ可能である旨の説明を返します。その他のエラーは元のルールどおりに処理します。

外部サービス、jev、モデルはすべて書き込みトランザクションのコミット後に実行します。結果と使用量の記録は、別に短い書き込みトランザクションを開いて保存します。台本／アイデア出しの内容は、まずその実行のメモリに保持し、保存ロック取得のための限られたリトライで内容を再生成することはありません。権限、バージョン、リース／claim、遅れて届いた結果のチェックは引き続き書き込みロック内で行います。読み取りトランザクションを書き込みトランザクションとして扱ってはならず、読み取り専用の GET はこのために書き込みロックを取得しません。

非同期のアイデア出しレポートで、失敗状態すらデータベースに保存できない場合は、プロセスのメモリに「データベースの場所、レポート ID、その回のリース」の保存失敗マークを最大 128 件だけ保持し、例外や生成内容は保持しません。照会ではデータベース上の processing 状態を維持したまま中国語のエラーを表示し、手動での再試行を許可します。新しいリースや完了した結果には古いマークを適用しません。再起動するとマークは消え、データベースにある 30 分のリース期限ルールに従って再試行が再開されます。これは一時的な運用状態であり、SQLite が唯一の業務データソースであることに変わりはありません。

根拠：[SQLite の分離と BUSY_SNAPSHOT](https://www.sqlite.org/isolation.html)、[SQLAlchemy の SQLite トランザクション制御](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#enabling-non-legacy-sqlite-transactional-modes-with-the-sqlite3-or-aiosqlite-driver)。テーブルや migration は追加しません。Alembic の接続設定は SQLAlchemy が BEGIN を管理する方式に合わせており、アップグレード／ダウングレードの検証は引き続き通過する必要があります。


## DM のウィンドウとコメント同期の範囲

DM の messages は新しい順に読み取ります。日付の下限より古いものを含むページでは、先にウィンドウ内のメッセージを取り込んでから、その会話を終了します。conversations のリクエストは `id,updated_time` を保持し、日付の下限より前の会話はスキップします。レスポンスの時刻が新しい順に並び続けている場合は境界で探索を終了し、時刻が欠けているか順序が逆転している場合は安全側に倒して次のページへ進みます。全履歴には日付による停止条件を適用しません。同じ messages カーソルでの連続したタイムアウト／5xx の回数は進捗に永続化し、ページの読み取りに成功すると 0 に戻します。`META_DM_CURSOR_RETRY_LIMIT`（デフォルト 5）に達するとその会話を終了し、プラットフォームが応答しなかった一部未完了の会話として数えます。他の会話は続行し、ジョブは完了できます。表示は待機中のスタイルをそのまま使います。

コメントは、投稿詳細ページの「コメントを取得」でのみ、1 投稿分の単発の読み取りとして作成されます。管理者／マーケティング担当者は取得と停止ができ、閲覧者は読み取り専用です。ブランド権限、CSRF、`comments.request`／`comments.stop` の監査はすべてバックエンドで行います。同じ投稿の一意な状態は書き込みロック下で重複を排除します。手動ジョブがなければ、スケジュールはコメント worker を実行しません。投稿一覧と成果指標は引き続き metrics worker が同期します。旧来の一括同期／取得補完の POST は 410 を返し、投稿の探索やキューへの追加は行いません。旧 `META_COMMENTS_AUTO_DAYS` は設定の解析で無視されます。

cwindow：手動取得はコメントの日付フィルターの設定に従って `window_start` を決め、`window_end` は選択した終了日の翌日とリクエスト時刻のうち早い方に固定し、半開区間を使います。明示的に period=all の場合だけ開始点を null にします。アイデア出しも同様に独立したコメント範囲を渡し、投稿の公開期間は引き続き投稿の選択にのみ使います。古いコメントのデータは削除しません。IG は `comments?fields=id,text,timestamp,from{id,username},replies.limit(50){id,text,timestamp,from{id,username}}` を、FB は `comments?filter=toplevel&order=reverse_chronological&fields=id,message,created_time,from{id,name},parent{id},comments.filter(stream).order(reverse_chronological).limit(50){id,message,created_time,from{id,name},parent{id}}` を使います。トップレベルとネストはそれぞれ最大 50 件を要求します。ネストの edge が存在しないことは表示可能な返信がないことを意味し、1 件ずつの追加照会はしません。ネストの `paging.next` が存在する場合に限り、その `cursors.after` を保存し、そのコメントの replies／comments edge でページを続けます。プラットフォームが返す next URL は、資格情報を含んだり非公式ホストへ誘導したりしないよう使いません。カーソルが欠けている、重複している、長すぎる場合はエラーにします。

親コメントと返信は、それぞれ空でないページ全体が window_start より古い場合にページ送りを止めます。混在したページでは続行し、時刻が欠けていればエラーにします。読み取り済みページの古い親コメントについては範囲内の返信を保存できますが、親コメントのページ送りを止めた後は、それより古い親コメントの返信は探索しません。FB は明示的に reverse_chronological を使います。IG はプラットフォーム本来の並び順に従い、公式 SDK に載っていない並び替えパラメーターは追加しません。完了するとすぐ手動キューを解除し、それ以上取得しません。worker 1 回あたり GET は 35 回／50 秒までです。予算の上限やプラットフォームのレート制限に達したときは、固定ウィンドウ、カーソル、処理済みページ数、保存済み件数を保持し、1 時間ごとのクォータ、使用量ヘッダー、バックオフと待機理由に従って同じジョブを継続します。処理可能な一時的なネットワーク障害もリトライのために保持します。権限、資格情報、無効なレスポンスなど人の対応が必要なエラーでは今回の読み取りを終了し、ユーザーが対処した後に改めてボタンを押してもらいます。

停止すると、まず run_id／リースを取り消して手動キューをクリアし、メッセージと保存済みの進捗は残します。すでにネットワーク上にある GET は取り消せませんが、その結果は取り消し後にコメントとして書き込めず、次の GET を発行することもできません。再取得は新しい固定ウィンドウと最初のページから始まり、プラットフォーム ID で重複を排除します。0025 の migration は、旧来のコメントジョブと取得補完の探索をすべて安全に終了し、古いカーソルとスケジュールの所有権をクリアします。業務データと最後に成功した時刻はすべて残し、古いジョブは復活させません。

表示は DB だけを照会します。詳細ページはデフォルトで直近 30 日を表示し、7／30／90 日の台北の暦日フィルターを用意します。1 ページ 50 組で範囲内の返信を添え、「さらに表示」は次のまとまりだけを読み込みます。親コメントが範囲外または未取り込みの場合、同じ明示的な親 ID を持つ返信を 1 組にまとめ、親コメントが表示できないことを示します。親の本文を補ったり取得したりはしません。旧 API の全期間／カスタム日付は、既存レポートの位置特定と照会のために残しますが、詳細ページではこの選択肢を提供しません。状態のポーリングは DB だけを読み、Meta にはアクセスしません。

公式リファレンス：[Field Expansion](https://developers.facebook.com/docs/graph-api/guides/field-expansion/)、[IG media comments](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-media/comments/)、[IG comment replies](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-comment/replies/)、[FB object comments](https://developers.facebook.com/docs/graph-api/reference/object/comments/)。今回、上記のリファレンスページは 429 を返したため、読み取りに成功したとは主張しません。フィールド／edge は [Meta 公式 IGComment SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/igcomment.py)と [Comment SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/comment.py) で照合し、3 回の IG 読み取り専用 GET でネストの読み取り、空の edge の省略、独立したページ送りを確認しました。本番データベースのコピーには FB の投稿がありませんでした。別に 2 回の FB 読み取り専用 GET で投稿を 1 件取得し、展開クエリは 200 を返しましたがコメントはなく、FB の返信のページ送りを実測できたとは主張しません。FB の返信は公式 SDK と HTTP mock でカバーしています。デプロイ担当者は、コメントのある投稿で実際の返信とプラットフォームでの利用可否を確認する必要があります。

## フォロワー数の追跡

`follower_snapshots`（0026）はアカウント、UTC の観測時刻、非負整数のフォロワー数を保存し、アカウント／時刻のユニークキーで再送による重複を防ぎます。テーブルと毎日の記録処理は変わりません。`GET /api/posts/followers` は `platform` が必須で、`brand_id`、`account_id`、`year`、`month`、`week` を渡せます。年・月・週を省略すると、台北の今日が属する年・月・週を選びます。投稿と同じログインとブランド権限を使い、admin／marketing／viewer の全員が読み取れます。照会はローカル DB だけを読み、プラットフォームやモデルは呼び出しません。

レスポンスには、プラットフォームの連携状態、スナップショットのある年（少なくとも今年）、月内の週の日付、現在の数、選択した週／月の増減、それが今週／今月かどうかを含みます。さらにアカウントごとの値も保持し、単一アカウントでの絞り込みに対応します。プラットフォームのツールバーは表示可能なアカウントを合計し、いずれかのアカウントにその期間のデータがない場合は合計を null にして、不明を 0 として扱わないようにします。スナップショットの入力は共通のプラットフォーム型を使うので、将来のプラットフォームの取得処理も同じテーブル、書き込みサービス、API、表示を使え、計算ロジックを複製する必要はありません。

週は月曜始まりで、台北の月の境界で区切ります。2026 年 10 月の第 1 週は 10/1–10/4、第 2 週は 10/5–10/11、第 5 週は 10/26–10/31 です。2027 年 1 月の第 1 週は 1/1–1/3 です。週と月の境界は台北の 00:00 で、終了日はその日を含み、最大で照会時点までを計算します。各日付は最後の 1 件を取ります。基準は境界のスナップショット、またはそれ以前の最後の 1 件を使い、開始点が最初の記録より前の場合は最初の生のスナップショットを基準にします。その期間のスナップショットがまったくなければ null を返します。負の値は符号を残し、欠けた日のデータは補いません。現在の数は常に最新のスナップショットを使います。

フォロワー数は各プラットフォームのタブの下に置き、FB／IG／Threads は簡潔なフォロワーツールバーを共用します。デスクトップではプルダウンと 3 つのインラインの数値を 1 行にまとめ、768／390px ではプルダウンで 1 行、数値で 1 行にします。年、月、週を切り替えるとすぐに照会し、過去の週や月を選ぶと「その週／その月」のラベルに変わります。未連携のプラットフォームには所定の案内を表示します。ブロックは内容に合わせて高さが伸び、共通のサイズ／余白の変数を使います。スマートフォンでは折り返せます。カスタム日付、日ごとの系列、折れ線グラフ、記録開始／スナップショット時刻、基準の説明は削除しました。旧 `date_from`／`date_to` のクエリは 422 を返し、この機能を残す必要のある他のフォロワー数 API の利用者はいません。投稿の成果の日付フィルターとグラフは変わりません。

既存の 1 時間ごとの metrics スケジュールは、先にフォロワーのスナップショットを確認してから投稿の指標を同期し、当日のスナップショットがない場合にだけ FB／IG の `GET /{account-id}?fields=id,followers_count`、または Threads の `GET /v1.0/{threads-user-id}/threads_insights?metric=followers_count` を呼び出します。Threads は独立したトークンと既存のデータ権限ゲートを使い、権限がなければスキップし、権限エラーでは一時停止します。Meta のクォータは経由せず、形式／値の異常は書き込まずにエラーを記録します。通常は 1 日 1 アカウントあたり追加で GET 1 回（FB＋IG なら 2 回）で、Insights の履歴を読む必要はありません。失敗しても後続のスケジュールで再試行でき、引き続き共有の 1 時間あたりの呼び出し上限、usage headers、Retry-After／バックオフの制限を受けます。起動時に metrics スケジュールを 1 回要求し、永続化された次回実行時刻のせいで最初の 1 件が遅れないようにします。スケジュールを無効にしている場合は実行しません。投稿の成功時と、投稿データの「今すぐ同期」でもそれぞれ 1 回要求します。今すぐ同期は管理者／マーケティング担当者に限られ、バックエンドが `scheduler.manual.metrics` に最後の要求時刻を記録し、60 秒以内にもう一度押すと 429 を返します。すでにキューに入っているか実行中の場合は重複して追加せず、クールダウンにも数えません。監査は `scheduler.request` です。実際の呼び出しは引き続き、上記の共有の 1 時間あたりの上限と使用量ヘッダーによるバックオフの制限を受けます。フィールドの失敗は実行可能な投稿同期の妨げにならず、スケジュールの結果に `followers` のエラーとして別に記載し、既存のスナップショットは残します。

IG と FB はどちらも `followers_count` だけを使います。公式のフィールドリファレンス：[IG User](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/)、[Page](https://developers.facebook.com/docs/graph-api/reference/page/)。今回、ドキュメントページは 429 を返したため、フィールドは [Meta 公式 IGUser SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/iguser.py)と [Page SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/page.py) で照合し、どちらにも `followers_count` が載っていました。今回は実機の Meta API は呼び出していません。プラットフォームの認可での利用可否は、引き続きデプロイ担当者が確認します。フィールドが返されなかった場合は失敗を記録し、0 は書き込みません。`fan_count` は意味の異なるページのフィールドなので、系列に自動で混ぜません。

## オーディエンス分析（0052）

`audience_insights` は、アカウントごと・分布の種類（`metric` followers／viewers／online × `breakdown` age／gender／country／city／hour）ごとに最新の 1 件だけを保存します。状態（ready／unavailable）、データ欠落のコード（permission_missing／not_available／no_data）、プラットフォームの集計期間、単位（count／percent）、`items_json`、取得時刻を含みます。毎日上書きし、履歴は残しません。取得は 1 時間ごとの metrics スケジュールでサムネイルの後に行い（`Workers.audience`）、アカウントごとに台北の暦日で 1 日 1 回です。同じアカウントの各項目の結果がすべて揃ってからまとめて書き込みます。ネットワーク、レート制限、5xx、形式の異常では書き込まず、次の回で再試行します。プラットフォームが明確に拒否した場合（権限、しきい値、指標の非対応）は unavailable として保存し、その日は再試行しません。処理することがなければ 0 を返し、スケジュールは空実行として扱います。アカウントの連携を解除したときのデータ削除で、これも一緒に削除されます。

- **Instagram**：`GET /{ig-user-id}/insights?metric=follower_demographics&period=lifetime&timeframe=this_month&metric_type=total_value&breakdown=age|gender|country|city` を 4 回、さらに `metric=online_followers&period=lifetime&since&until`（直近 7 日）を 1 回呼び出します。online_followers は 1 日ごとに 0–23 時の 1 組（太平洋時間の 1 日で、`end_time` は翌日の太平洋時間の午前 0 時）なので、台北の時間帯に換算してから平均します。権限は `instagram_manage_insights` をそのまま使います。フォロワーが 100 人未満の場合、プラットフォームはデータを返しません。
- **Facebook ページ**：`GET /{page-id}/insights?metric=page_follows_country,page_follows_city&period=day` を 1 回呼び出し、最新の 1 日を取ります。`page_fans_gender_age` などの年齢／性別の指標は Meta が 2024-03-14 に廃止し、代替はありません。`page_fans_country／city` は 2025-11-15 に廃止され、公式の代替は `page_follows_*` です。
- **Threads**：`GET /{threads-user-id}/threads_insights?metric=follower_demographics&breakdown=…` を 4 回呼び出し（公式には 1 回につき breakdown は 1 種類のみ）、Threads のデータ権限ゲートをそのまま使います。権限エラーでは一時停止して前日のデータを残し、一般的な API エラー（ほとんどは 100 人未満）は not_available として保存します。
- **YouTube**：YouTube Analytics の `reports` で、直近 28 日（太平洋時間で 2 日前まで）の `dimensions=ageGroup,gender&metrics=viewerPercentage` と `dimensions=country&metrics=views&sort=-views&maxResults=10` の 2 回を呼び出し、既存の `youtube.quota` に計上します。年齢／性別はログインしている視聴者だけを含みます。
- **TikTok、LINE**：呼び出しません。Display API にはオーディエンスのデータがなく、LINE は通知にのみ使います。画面には理由をそのまま表示します。

Meta の呼び出しは `meta_api` で記録され、1 時間あたりの上限、クールダウン、usage headers の制限を受けます。レート制限を受けた後は、同じ回で他の Meta アカウントを呼び出しません。通常は 1 日に IG 5 回、FB 1 回です。`GET /api/dashboard/audience` は `brand_id` を任意で指定でき、アカウントのブランド権限をそのまま使います。admin／marketing／viewer の全員が読み取れ、ローカル DB だけを読みます。ダッシュボードの「オーディエンス分析」カードはプラットフォームのセグメントで切り替え（URL の `audience_platform`）、取得できた項目は横棒（人数を割合に換算）または 24 時間の縦棒で表示し、データがない場合やプラットフォームが提供しない場合は理由を表示します。国コードは `Intl.DisplayNames` で画面の言語に合わせて表示します。実機のレスポンス形式は未検証です。FB の `page_follows_*` の値の形式は旧 `page_fans_country`（`{コード: 人数}`）に、Threads の `follower_demographics` は IG の `total_value.breakdowns` に準じています。デプロイ後に確認する必要があります。

## AI とメッセージ分類

公式の Gemini／OpenAI／Anthropic はアプリケーション層のリトライを共用し、SDK に内蔵されたリトライはオフにしています。408、一般的な 429、500、502、503、504、接続／読み取りのタイムアウトは最大 4 回試行し、2／5／10 秒の待機にそれぞれ 0–0.25 秒のジッターを加えます。Retry-After（秒または HTTP 日付）と Google の `google.rpc.RetryInfo.retryDelay` を優先します。プロバイダーが勧める待機時間が残り時間を超える場合はすぐに報告し、無駄に待ったり、早めに再送したり、上限を延ばしたりはしません。

Google の 429 のエラー内容に `free_tier` が含まれる場合は `provider_quota_free_tier` を返し、短時間のリトライでは解決しないとみなして即座に終了し、同じプロバイダーのフォールバックにも切り替えません。その他の 429 は `provider_rate_limited` を返します。OpenAI の 429 で `insufficient_quota` または請求／支出上限のコードの場合は `provider_quota_exhausted` を返し、リトライもフォールバックへの切り替えもしません。Anthropic の 429 の `rate_limit_error` は一般的なレート制限のコードを返し、このコードから請求上の原因を推測しません。保存するのはコードと有限の非負の待機秒数だけで、既存のエラーフィールドに `;retry_after_seconds=N` として付記して UI で使います。プロバイダーのエラー原文や絶対的な単調時計の値は保存せず、テーブル変更はありません。

ブランドの `ai.brand.<id>` 設定に 3 社分の `*_fallback_model` を追加しました。ブランドの書き込み権限、バージョン競合チェック、`ai.settings` の監査をそのまま使います。Gemini のデフォルトは `gemini-3.7-flash` で、他のプロバイダーのデフォルトは空です。明示的に空にするとフォールバックを無効にし、メインとフォールバックが同じなら重複して切り替えません。メインモデルがリトライ後も 408／一般的な 429／5xx／タイムアウト／接続障害の場合にだけ、同じプロバイダーのフォールバックに切り替えます。恒久的なエラーや、未完了／拒否された内容は即座に終了します。メインとフォールバックは `AI_API_TIMEOUT_SECONDS`（デフォルト 60 秒）を共用します。フォールバックがある場合は `max(20 秒, 全体の制限時間 / 3)`を確保し、デフォルトではメインモデルは最大 40 秒です。バックオフ後、次のリクエストを出すまでの残りが 10 秒未満ならメインモデルのリトライを止めてフォールバックに渡します。メインモデルが早めに終わった分の時間もフォールバックが使えます。フォールバックは最大 4 回で、各回の SDK timeout はその段階の残り時間です。各リクエストの前に残りが 10 秒未満ならリクエストの作成を禁止し、`provider_time_exhausted` を返します。全体の制限時間が短い場合はメインモデルを飛ばすことがあり、全体の制限時間を超える 20 秒を保証することはできません。全体の制限時間が 10 秒未満なら、最初から最後までリクエストを送りません。最後のレスポンスの Retry-After はフォールバックにも適用されます。待機するとフォールバック用に確保した時間を侵食する場合は、レート制限／プロバイダーエラーとしてそのまま報告し、無駄に待ったり早めにリクエストしたりはしません。

Gemini のクォータはプロジェクト単位で管理され、実際の制限はモデルとプランによって異なります。個々のエラーに含まれる制限値を全体のデフォルトとはみなしません。無料プランの枠による失敗では保守的に停止する方針を取り、フォールバックモデルで制限が解除されるとは仮定できません。継続して使う場合は、Google AI Studio でそのプロジェクトに有料の請求先を設定し、有効なクォータ、使用量、予算を確認することをお勧めします。公式の説明：[Gemini のクォータ](https://ai.google.dev/gemini-api/docs/rate-limits)、[請求の設定](https://ai.google.dev/gemini-api/docs/billing)、[OpenAI のエラーコード](https://developers.openai.com/api/docs/guides/error-codes)、[Anthropic のエラーコード](https://platform.claude.com/docs/en/api/errors)。

テキストモデルとバックグラウンドタスクは、Gemini、OpenAI、Anthropic の公式 API キーだけを使います。ローカル CLI は削除済みで、執筆は Agent が担当します。クラウドに送るテキストはすべて先に個人情報をマスクし、モデルの使用量はブランドごとに追跡します。共通およびブランドの prompt にはバージョン、差分、復元があり、バックエンドのガードレールを緩めることはできません。

jev は TypeSafe v1 の Choice／Noul／Score を使います。各質問ではバッククォートで名前付きの state フィールドを参照し、顧客のテキストと審査対象の内容はデータとして扱います。同じ state に対する独立した質問は一度にまとめて送り、すべて `redact.scrub` と `jev.valid_response` を通します。Choice は該当なしの出口を残します。Noul は条件が成り立つ確率であり、0.5 に近いことは中程度の強さを意味しません。Choice／Score の confidence は分布の集中度です。既存のポリシーとしきい値は変えず、調整する場合はまずラベル付きデータで評価する必要があります。根拠：[質問](https://docs.typesafe.ai/primitives)、[state](https://docs.typesafe.ai/concepts/state)、[confidence](https://docs.typesafe.ai/confidence)。

ブランドのカテゴリ補足説明は `classification.intents.brand.<id>` として Setting に保存します。9 つの意図コードは固定で、各項目は前後の空白を除いて最大 200 文字、未知のフィールドは拒否します。`GET/PUT /api/classifications/intents?brand_id=` はブランド権限、設定バージョン競合の 409、`classification.intents` の before／after 監査をそのまま使います。汎用のサービス説明の後にブランドの例を追加し、例は指示ではないことを明示します。クラウドに送る前には引き続き redact を通します。`QUESTION_VERSION=triage-2026-10-23-v3` で、raw_json に `intent_notes_version` を保存します。補足説明は context／fingerprint に含めず、フィンガープリントは `triage-2026-09-26-v3` に固定したままです。既存の結果は有効なままで、再計算やジョブの再キューイングはしません。新しい設定は、以降の新しいメッセージと手動での再振り分けにだけ影響します。

振り分けの state では sender が顧客であることを明記し、メッセージとマスク件数は context の同名フィールドで上書きされません。質問のバージョンと input hash のバージョンは分けてあり、文言の改訂で既存の結果の効力は失われません。手動の再振り分けか、新たな既存ジョブの場合にだけ新しい質問を使います。ポリシーの再計算は引き続き保存済みのシグナルにのみ適用します。テーマ分類の質問バージョンも同様にフィンガープリントから独立しており、文言の改訂で有料の再計算が走ることはありません。既存の分類処理は引き続き元の limit／予算の制限を受けます。

代表的な原文を選ぶ Choice は none を返すことができ、その場合は選択済みのソースを残して停止し、5 件に満たなくても無理に埋めません。後続の選択は選択済みの結果に基づいて state を更新するため、引き続き 1 件ずつリクエストします。CSV の state は `columns.column_<index>` を使い、question ID と返却される列のインデックスは変えず、ignore を残します。`scripts/eval_jev_questions.py` は 5 組の合成データ（振り分け 16 例、その他は各 8 例）で、固定の旧来の質問と現行の builders を比較します。デフォルトは transport の代替で、`--live` を付けたときだけ公式 API に接続し、出力は `.runtime/` に限られます。代替で通過しても、パイプラインが動作することを示すだけで、品質の改善を意味するものではありません。

## ブランド中立の設定

`settings.workspace.display_name`（実際の key は `workspace.display_name`）に製品名を保存します。公開されている内部のログイン識別 API は名前とバージョンだけを返します。変更は管理者に限られ、監査されます。ログインページ、ナビゲーション、ヘッダー、タブのタイトル、Word のヘッダーはこの値を共用します。

`ideation.brand.<id>` には定例会議とテーマを保存します。新しいデフォルトは無効で、曜日／時刻は空、テーマは「その他」だけです。`brand.rules.<id>` には NG ワードを保存し、デフォルトは空のリストです。過去の価格データは残していますが、操作する入口はありません。

テンプレートはバージョン管理された JSON です。管理者はまず差分をプレビューし、ブランドの状態とテンプレートの内容を含むハッシュで確定します。適用は単一のデータベーストランザクションで、テーマ、NG ワード、ブランド prompt の新しいバージョンを更新し、定例会議と送信権限は保持します。データが少しでも変わると、古いプレビューは無効になります。

コンテンツのリサーチには実際の根拠だけを使います。レポートは同じテーマの実際のメッセージ ID を引用する必要があり、数が足りなくても補ったり作り出したりはしません。ブランドのコンテンツは設定と prompt から直接取り、特定の外部ナレッジベースは読みません。台本は編集、再チェック、バージョンの保存ができますが、プラットフォームへの投稿はできません。

## ダッシュボードのマーケティング概要と日ごとのトレンド

`GET /api/dashboard` は台北の月曜 00:00 から照会時点までについて、new_messages（既存の履歴以外の DM）、new_comments（公開の comment_thread のうち direction=in／author_type=fan のメッセージ数。期間内に追加取得したコメントを含む）、top_intent（今週の履歴以外の顧客メッセージのうち、最新でフィンガープリントが有効な分類。spam／未知のコードを除く）を返します。上位の分類には DM と公開コメントの両方を含み、同数の場合はコード順に並べます。データがなければ null を返します。ブランドごとに分類の context は一度だけ作成します。問題の分布は、引き続き今週の新しい DM の直近の分類を使います。pending_threads、first_reply_seconds、first_reply_samples、stages と関連するクエリは削除しました。

`GET /api/dashboard/trends?days=30` は brand_id を任意で指定でき、Access をそのまま使います。days は 7／30 のみです。レスポンスは `{days, timezone: "Asia/Taipei", series: [{date, new_messages}]}` で、台北の暦日ごとに 0 を補います。概要とトレンドは incoming_messages を共用し、sent_at で計算し、過去の DM を除き、未来のメッセージは数えません。

トレンドは 1 回の一括 SELECT だけを行い、メモリ上で日ごとに集計します。書き込みトランザクションは開かず、プラットフォーム／モデルも呼び出しません。既存のインデックスを使い、migration はありません。test_workspace は 2,000 件／500 スレッド、読み取り専用、300ms の上限（CI では 1 秒）を維持し、SELECT が 1 回であることの検証に変えました。エクスポートのレポートにはもともと上記のカスタマーサポートの KPI がないため、形式は変わりません。

### 成長の比較とコンバージョンファネル（2026-10-16 に延期項目を追加）

- 概要は追加で `previous: {start, end, new_comments}` を返します。先週の月曜 00:00 から 7 日前の現時点まで（今週と同じ長さで、終点は含みません）です。トレンドは追加で `previous_total` を返します。ウィンドウの直前にある同じ長さの直前 7／30 日の新規コメントの合計で、系列と同じ 1 回の SELECT で取得します。前期が 0 の場合、フロントエンドは割合を計算しません。
- `GET /api/dashboard/funnel?days=30` は brand_id を任意で指定でき、権限はトレンドと同じです。days は 7／30 のみです。母集団は直近 N 日（台北の暦日）に公開され、削除されておらず、最新のスナップショットに reach がある投稿です。4 段階は順に、リーチ（reach の合計）、エンゲージメント（likes＋comments＋shares＋saves の回数の合計。リーチより多くなることがあります）、コメント（それらの投稿への顧客からの受信コメント数）、購入の問い合わせ（そのうち最新でフィンガープリントが有効な分類が price／booking／model_question のもの）です。レスポンスは `{days, timezone, posts, stages: [{key, value}]}` で、コンバージョン率はフロントエンドが 1 つ前の段階をもとに計算します。当初予定していた「成約」の段階は noinbox で削除され、表示されなくなりました。

## 投稿サムネイルのキャッシュ（0046）

プラットフォームの CDN の画像 URL は期限切れになるため、投稿ごとに縮小した JPEG（長辺 480px）を 1 枚、`post_thumbnails`（投稿ごとに 1 行、data は遅延読み込み）に別途保存します。取得は 1 時間ごとの metrics スケジュールの後に行い、`post_thumbnails.hourly` が 1 回につき最大 20 件（新しい投稿を優先）を処理します。FB は `GET /{post-id}?fields=full_picture` を読み、IG は `media_type,media_url,thumbnail_url` を読み（動画はカバーだけを取得）、Threads は同名のフィールドを読みます。TikTok は Display API の `POST /v2/video/query/`（`fields=id,cover_image_url`、`video.list` が必要、連携条件は TikTok の同期と同じ）でその時点で有効なカバーの URL を取得し、すぐにダウンロードします（カバーの URL は期限切れになります。一覧にその動画がなければ削除または非公開に変更されたとみなし、unavailable にします。レート制限や認可の失効時はその回の TikTok をまるごとスキップし、リトライ回数は減らしません）。YouTube は公開されている `i.ytimg.com/vi/{id}/hqdefault.jpg` をそのまま使い、Data API のクォータを消費しません。FB／IG は投稿ごとに Meta の呼び出しが 1 回で、`meta_api` で記録され、1 時間あたりの上限とクールダウンの制限を受けます。クールダウン中はその回の Meta をまるごとスキップします。画像は `fbcdn.net`／`cdninstagram.com`／`ytimg.com`／`tiktokcdn.com`／`tiktokcdn-us.com`／`tiktokcdn-eu.com` の https URL からだけダウンロードします（それ以外のホストはホスト名だけを含む `thumbnail_untrusted_host` の警告を記録します。TikTok のカバーのドメインはドキュメントに書かれていないため、未知のドメインに遭遇した場合はすぐに諦めずリトライに回します）。リダイレクトはたどらず、取得元の上限は 8 MB で、Pillow で縮小して JPEG に変換します（透明な背景は白に変換）。テキストのみの投稿や削除済みの投稿は unavailable にして、それ以上試しません。ネットワーク、レート制限などの一時的な失敗は 1／6／24 時間後にリトライし、4 回目も失敗したら停止します。`GET /api/posts/{id}/thumbnail` は投稿のブランド権限をそのまま使って画像を返します。投稿一覧、単一の投稿、ダッシュボードのランキングは `thumbnail_url`（キャッシュ破棄用に要約の断片を含む）を返し、サムネイルがなければ null です。公式の GET だけを読み、プラットフォームには書き込みません。検証は代替の HTTP で行います。

## エクスポートと監査

Markdown／Word は、設定可能なルートディレクトリの下のブランド別サブディレクトリに置きます。Word はワークスペース名を使い、エクスポートでは秘密情報を除外します。パスはトラバーサルを防止します。MCP ツールの戻り値は常に個人情報をマスクし、呼び出しごとに agent.tool.read／write の監査を残します（`docs/jp/MCP仕様.md` を参照）。

通常の変更では監査と prompt のバージョンを保持します。過去の内容の消去には、別途明示的な許可、プレビュー、バックアップが必要で、監査を自動で書き換えることはありません。


## テキストモデルの実行方式（nocli）

執筆は Agent（`/mcp`、Claude Code plugin、Codex、Claude デスクトップ拡張機能、Hermes）に任せます。2026-10-12 から、`codex_cli`、`claude_cli`、`agy_cli` の 3 種類のローカル CLI の実行、検出、ログインチェック、モデル一覧、更新、設定ページ、関連 API を削除しました。ワークベンチは codex／claude／agy のプロセスを一切起動しません。テキスト AI はすべて Gemini、OpenAI、Anthropic の公式 API キーだけを使い、キー、モデル、フォールバック、使用量、月の予算のルールは変わりません。送信するテキストは引き続き先に `redact.py` を通します。`ai.run` は 3 つの API プロバイダーだけを受け付け、それ以外の値には `provider_unavailable` を返します。新しい使用量の記録は一律 `mode=api` です。

古いデータはすべて互換性を保ち、書き換えも migration も行いません：
- CLI 系の設定値（ブランドの `ai.brand.<id>` の `default_provider`、`manual_provider`、`background_provider`）を読んだ場合は未設定とみなします。`ai.config` は読み取り時にだけ変換し、データベースの元の値は残します。`AISettings` の書き込みは 3 つの API プロバイダーと空の値だけを受け付け、古い値があっても予算やフォールバックモデルの保存は妨げません。グローバルの `ai.local_cli`、`ai.cli.*` の Setting はもう読まれず、削除もしません。
- `ai_runs` の `mode=subscription` の古い記録（token が null のものを含む）は引き続き「今月の使用量」の表に表示され、名前は廃止済みの旧 CLI と表示されます。月の予算は `mode=api` だけを数えるので影響はありません。
- 古いレポートの provider が CLI でも、閲覧とエクスポートは引き続きできます。再試行はできず（`can_retry` は false）、エラー文は「ローカル CLI はサポートされなくなりました（過去の記録）」と表示されます。スケジュールと再試行は API と agent のレポートだけを処理します。

`GET /api/ai/settings` は設定、利用可能な API の選択肢、予算、使用量だけを返し、トップレベルの `draft_provider` はなくなりました。`GET /api/ai/execution-options` の `draft_provider` はブランドの `default_provider`（未設定なら空文字列）で、選択肢は 3 つの API プロバイダーだけです。「デフォルトの AI」は現在、アイデア出しのデフォルトの実行方式だけを決めます。

Web のアイデア出しでレポートを作成するときの `provider` は、3 つの API プロバイダーまたは `agent` です。API を選んだ場合は従来どおり、コメントを取得し、jev で分類し、根拠を集約してから、API が 15 件のテーマを一度に生成します（`compose_prompt` はアイデア出しでだけ使われ、プロンプトのフィールドの順序は変わりません）。`agent` を選んだ場合は、根拠を集約した後に既存の `awaiting_ideas` で止まり、テキスト AI は一切呼び出しません。画面では、Claude Code なら `/mwb:ideas` を使うか、他の Agent なら `get_guide("ideas")` で引き継ぎ、24 時間以内に保存するよう説明します。`agent_content` の根拠、保存、タイムアウトのルールをそのまま使います。Web で作成した agent のレポートには接続元のマークがなく、失敗（タイムアウトを含む）した場合は再試行できます。定例会議のスケジュールによるレポート（`trigger="background"`）は常に Gemini API を使います。画面のデフォルトの優先順位は、ブラウザーの `ideation-choice:<brandId>` の記憶（手動で変更したときだけ書き込み）、ブランドのデフォルトの AI、最初に利用可能な API、「Agent に作成を任せる」の順です。CLI の記憶とデフォルト値は一律に無視します。

削除したもの：テーマカードの「再生成」「派生テーマ」「台本を生成」と、`POST /api/ideation/reports/{id}/ideas/regenerate`、`.../ideas/{index}/extend`、`POST /api/ideation/reports/{id}/scripts`、`idea_actions.request／process`、`video_scripts.generate／compose_prompt`（ルートは `permissions.py` から削除済みで、呼び出すと 404 または 405 を返します）。残したもの：テーマの編集と 1 つ前の版への復元（Agent の `edit_idea` は `idea_actions.edit` を共用）、台本の閲覧と編集、`video_scripts.review`、Agent の `save_script`。カードに残るのは右上の「編集」だけです。下部には、台本がある場合は「台本を表示」が加わり、それ以外は「投稿の下書きを作成」、下書きがすでにある場合は「投稿の下書きを開く」です。レポートの `data_json` にある古い `ideas_job` と `regenerated`／`extended_from` のマークは履歴の表示にだけ使い、進捗やエラーの画面はもうありません。アップグレード時にまだキューに残っていた古いジョブは実行されず、レポートを処理するときに元のテーマへ戻してそのジョブのフィールドを削除します。`video_scripts.view` に `topic_index` を追加し、カードがそのテーマの最新の台本を見つけられるようにしました。

投稿の下書きでは、もう AI で本文を作成しません。`POST /api/publish/ideation-draft` はテーマのタイトル、冒頭、hashtag（`publish.idea_caption`）から初稿を組み立て、台本は参照しません。`include_script` フィールドは無視され、古い画面から送信しても失敗しません。`GET /api/publish/ideation-preview`、`POST /api/publish/posts/{id}/caption/retry`、`.../caption/apply`、`publish_caption` サービス、起動時の中断された本文ジョブへのマーク付けは削除しました。`publish_posts.caption_job_json` カラムは残しますが（破壊的な migration はしません）、プログラムはもう読み書きせず、`view` と一覧にも出力しません。古い下書きに本文ジョブのデータが含まれていても、投稿ページには AI の状態を一切表示せず、それを理由に空の下書きを一覧に出すこともありません。Agent の `create_draft_from_idea` の動作は変わりません（渡された本文をそのまま使います）。

`services/processes.hidden_process_kwargs()` は引き続き起動時の自動起動とバックアップの 7-Zip が共用しており、CLI 専用ではありません。

## 投稿

プラットフォーム：Facebook ページ、Instagram、Threads、YouTube、TikTok（受信トレイに送るだけで、投稿はアプリ内で完了する必要があります）。形式：ショート動画、画像、カルーセル、テキストのみ、ストーリーズ。投稿先のアカウントは、現在のブランドで「プラットフォーム連携」に設定されているアカウントに従います。

- **ルールとチェック**：本文は 1 つで、プラットフォームごとに上書きできます。ルールは `backend/app/services/publish_rules.py` に集約しています。`RULES`（本文、長さなど。そのままフロントエンドに返します）と `MEDIA_RULES`／`IMAGE_BYTES`／`VIDEO_BYTES`（メディアの比率、幅、サイズ、mime）です。`GET /api/publish/options`、Agent の `get_publish_options`、アップロード時のチェック、Agent のアップロードが同じものを共用します（文字数、hashtag、動画の長さ／比率、ファイルサイズ、mime、幅）。条件を満たさないプラットフォームは赤く表示して投稿をブロックします。システムは自動で切り詰め、書き換え、変換をしません（唯一の例外：Instagram に送る PNG は JPEG に変換します）。プラットフォームが対応していない形式はそのまま無効にして理由を説明します（たとえば Instagram はテキストのみに非対応、YouTube は動画のみ対応）。
- **予約投稿**：即時または台北時間での指定で、ワークベンチのスケジューラーが毎分実行し、期限が来た投稿をバックグラウンドのスレッドに渡して投稿します（スケジューラーはアップロードの完了を待たないため、長時間のアップロードがあっても同時に期限が来た他の投稿が「期限切れ」になることはありません）。予約時刻の 1 分前から編集／キャンセルをロックします。5 分を超えて遅れた場合は後から投稿せず、「期限切れ」として通知し、すぐに投稿するか予約し直すかはユーザーが決めます。マスタースイッチがオフの間はすべての予約投稿を一時停止し、再びオンにすると、期限前のものは通常どおり、期限を過ぎたものは期限切れになります。
- **部分的な成功と再試行**：成功したプラットフォームには二度と再送しません。できるのは「失敗したプラットフォームのみ再試行」だけです。サービスの起動時に中断した publishing を interrupted にし、自動では再送しません。ユーザーがまずプラットフォームで確認してから再試行するかを決めます。複数の部分からなる内容（Threads のスレッド、複数件のストーリーズ）は、1 つ成功するたびに短いトランザクションでプラットフォーム ID を保存し、失敗後の再試行は残りの部分だけを続けます。すでに成功した部分がある場合は、分割、素材、アカウントをロックします。結果を確認できないタイムアウトは、重複投稿を避けるためにプラットフォームで人が確認する必要があります。投稿中に予期しないエラーが起きた場合は、未完了のプラットフォームを `unknown`（プラットフォームで確認してください）にして投稿を確定させ、投稿中のまま止まることはありません。予約をキャンセルしたとき、または期限切れにしたときは、未送信のプラットフォームのうち、一度も試していないものは対象から外し、試したことのあるものは失敗に戻します。毎回の送信では、今回選択し、まだチェックが入っているプラットフォームにだけ送ります。
- **メディア**：ランダムなファイル名で PUBLISH_MEDIA_ROOT に保存します。すべてのプラットフォームで成功してから 30 日後に削除し、その他の状態では残します。IG／Threads で公開 URL が必要な場合は `/media/<權杖>` の一時リンクを作成します（15 分経過または取得完了で取り消し、最大 32 回、無効なものは一律 404、公開境界のチェック対象）。YouTube はワークベンチが直接アップロードするので、一時リンクは使いません。
- **Facebook の未公開投稿**：`facebook_unpublished` は `published=false` で作成し、Facebook にだけ影響します。Facebook で成功または投稿中になった後はロックされ、再試行は元の選択肢を使います。`/published_posts` には出てこないため、成果は取得しません。削除済みの判定は 1 件ずつの照会に変えています（先にページを読み取れることを確認し、100/33 または 10 が返った場合だけ存在しないとみなし、その他のエラーでは判定しません）。
- **リールと Threads のスレッド（composer1、0041）**：FB リールは start → rupload → finish の流れです。未公開と同時に選んだ場合は feed で作成し、その旨を案内します。IG は `share_to_feed=false` のときだけ明示的に送ります。IG リールのカバー（0048、`publish_media.role=cover`、`instagram.cover_media_id` に紐づき、サーバー側で管理）は期限付きの公開リンクを `cover_url` として送ります。PNG は `.jpg` の派生ファイルを使います（公式には JPEG だけを受け付けます）。カバーがない場合、リクエストは従来どおりです（プラットフォームが最初のフレームを使います）。IG で成功または投稿中になった後はカバーを変更できません。FB の動画／リールのカバー（0049、`role=fb_cover`、`facebook.cover_media_id` に紐づく）は、投稿が成功して保存された後に `POST /{video-id}/thumbnails`（`source`＋`is_preferred=true`）で適用し、結果を対象の `detail.cover` に書き込みます。失敗しても投稿には影響せず、「カバー画像を再適用」できます（`POST /api/publish/posts/{id}/facebook-cover`。動画を再アップロードすることは決してありません）。任意の権限 `pages_manage_engagement`（`oauth.META_OPTIONAL_SCOPES`）が必要です。認可時に一緒に要求し、なくても連携状態や投稿の準備状況には影響せず、投稿の選択肢で `cover_hint` だけを返します。Threads は最初の部分に素材を付け、以降は reply_to_id でつなげます。自動の分割は空行／改行を優先し、次に文末の句読点、最後は強制的に切ります。番号は付けず、emoji は UTF-8 のバイト数で数えます。プラットフォーム ID と削除の検出は最初の部分だけを見ます。FB の動画とリールは動画 ID を記録し、`/videos` の一覧と照合します。
- **ストーリーズ（composer3、0042）**：`format=story` で 1–10 件、各件は画像 1 枚または動画 1 本で、FB／IG のみです。テキストや投稿の選択肢は付けません。IG で成功した各件は、24 時間以内は 1 時間ごとに insights を読み、署名が検証された `story_insights` の最終スナップショットを受け取ったら停止します。非対応の指標は空のままにし、0 で埋めません。FB のストーリーズにはまだ成果がありません。ストーリーズは削除済みの判定を行いません。
- **YouTube（ytpublish、0043）**：`youtube.upload` スコープが必要です（より広い `youtube`／`force-ssl` は要求しません）。ない場合は投稿タブがグレーになり、再連携を案内します。公式の resumable upload を使います。8 MiB ずつ分割し、中断や 5xx では 1／2／4／8／16 秒のバックオフで最大 5 回、毎回まず受信済みのバイト数を問い合わせてから続きを送ります。セッションの 404 では 1 回だけ最初からやり直します。セッションの URL は `detail_json.upload` に保存し、ブラウザーや MCP には返しません。動画の完了後はまず `video_id` と実際の公開状態を保存するので、その後サムネイルの成否や中断があっても動画を再アップロードすることはありません。サムネイルは別に `thumbnails.set` で設定し、失敗しても動画の成功には影響せず、「サムネイルを再適用」できます。Shorts に分類される動画（縦長／正方形で 180 秒以下）ではサムネイルを無効にします（`RULES.youtube.shorts_thumbnail`）。`videos.insert` を呼び出す前に `youtube.uploads` の 1 日の枠から差し引き、サムネイルは共用の `youtube.quota` から差し引きます。
- **削除済みの検出**：「完全な一覧に存在しない」ことだけで判定し、1 件ずつの照会のエラーでは判定しません（FB の未公開投稿は例外、上記参照）。いずれかのページが失敗した、ページ数の上限に達した、形式に異常がある、アカウントが変わった場合は、一律に判定しません。再び一覧に現れた場合は deleted_at をクリアします。
- **安全性**：「プラットフォームへの投稿を許可」するマスタースイッチ（Setting `publishing.enabled`）はデフォルトでオフで、管理者だけが切り替えられます。投稿や予約のたびに確認ダイアログを表示し、投稿ごとに監査を書き込みます。成功、部分的な成功、失敗、期限切れ、トークンの期限切れ間近は、既存のブランドの LINE 通知グループに送ります（メディアの URL や資格情報は含みません）。投稿後はプラットフォームのリンクだけを残し、ワークベンチからプラットフォームの投稿を変更したり削除したりはしません。

カスタムロール（0053 `roles`）：管理者は「設定 → メンバー」でロールを追加し、上の表の機能の権限にチェックを入れます。メンバーの `staff.role` には組み込みのキーか、カスタムロールのキー `custom_<id>` を保存します。組み込みの 3 つのロールはプログラムに書かれており、変更できません。カスタムロールは常に割り当てられたブランドしか見えず、メンバー管理にはチェックを入れられないため、自分を管理者に昇格させることはできません。`publish.submit` にチェックを入れると、バックエンドが自動で `publish.edit` を追加します。権限が 1 つもないロールは閲覧者と同じで、全体が読み取り専用です。まだメンバーが使っているロールは削除できません。ロールが存在しなくなった場合は権限が 1 つもないものとみなし、Agent の接続は失効します。0053 をダウングレードすると、カスタムロールのメンバーは閲覧者に変更されます。MCP の書き込みツールはそれぞれ機能の権限に対応し（`agent_tools.TOOL_PERMISSIONS`）、`get_server_info.user.permissions` に現在のメンバーの権限が列挙されます。

## プラットフォームの資格情報（creds）

0031 で platform_credentials（provider／encrypted_key／version／時刻）を追加しました。ID／公式の base URL を含むすべてのフィールドを Fernet で暗号化し、マスターキーは引き続き .env にだけ置きます。既存の ai_credentials にある jev の暗号文とバージョンは JEV_API_KEY に移し、復号せず、元の値も失いません。旧 AI jev API は互換のために残し、新しいテーブルを共用します。削除時は空の暗号文でバージョンを残し、削除して作り直すことで古い画面がバージョンチェックを通過するのを防ぎます。

credentials.resolve(name, settings, session) はプラットフォーム設定の唯一の解決入口で、DB を優先し、上書きがない場合だけ env を使います。暗号文が壊れている場合に env へ格下げして使うことはありません。値はキャッシュせず、新しいリクエスト／worker の操作ごとに最新の値を取ります。Webhook の署名、身元、Meta Graph の token／アカウント、LINE の profile／通知、ヘルス通知、jev はすべてこの入口を通ります。webhook_normalize.secret はプラットフォームのフィールドをこれに委譲します。Python の評価ツールと Node のプラットフォーム設定スクリプトも同じく共通の解決を使います。Node はローカルの Python サブプロセスを通じて設定を取得し、1 回限りの AES-GCM の IPC キーは stdin でだけ渡し、stdout は暗号文だけで、エラーは固定の文言です。公開された復号 API はありません。

GET／PUT／DELETE /api/credentials と POST /api/credentials/{group}/test は admin のみです。書き込みはバージョンをチェックし、監査にはフィールド名、操作、操作者だけを保存します。API は configured／source／mask／version／error だけを返します。接続テストは管理者が明示的にクリックしたときだけ実行し、書き込み自体は外部に接続しません。Meta の /me と LINE の bot info は 1 回の GET で、jev は既存の post_json と redact を使います。timeout は固定、redirect は禁止で、生のレスポンス／例外は返さず、jev の URL は公式のエンドポイントに限ります。テストはすべて HTTP／CLI の代替を使います。
