# UI 仕様

> **言語 / Language / 語言 / 语言**：[繁體中文](../zh-tw/UI規格.md) | [简体中文](../cn/UI规格.md) | [English](../en/ui-spec.md) | 日本語

## Agent のインストール（agentpack）

- マイアカウントのパスワードフォームと Agent 接続の間に `.agent-install` を追加します。h3「Agent をインストール」と compact `SegmentedControl` を同じ行に置き、Claude Code／Codex／Claude デスクトップ版を切り替えます。すべてのロールに表示し、狭い幅ではコントロールを次の行に回し、幅はカードに揃えます。
- 各 `.agent-install-command` はコマンド 1 行の code と `.secondary` のコピーだけで構成し、狭い幅ではコマンドを折り返せます。コピーに成功するとボタンは「コピーしました」に変わります。Claude Code の 2 つのインストールコマンドは現在の location.origin から組み立て、その下には自動更新についての説明を 1 文だけ残します。
- Codex は `.secondary.agent-install-download` で skills／config パッケージをダウンロードし、展開コマンド、skills の配置と config のマージについての説明 1 文、OAuth ログインコマンドを並べます。画面にすべてのツール設定は列挙しません。バージョンは既存の workspace/identity API が提供します。
- http://127.0.0.1 では `.notice.agent-install-origin` を表示し、他のメンバーには内部 HTTPS を使うよう案内します。リンクは同じ API の backoffice_origin が提供し、ホストをハードコードしません。
- コマンドは text-main／bg-subtle／ui-font-mono／help、説明は text-subtle／bg-surface です。角丸は control トークンを使い、その他は P1-1 と共通コンポーネントを踏襲し、外部リソースは一切使いません。1440／768／390px で横方向にはみ出さず、check_agent_auth などはデータ、フォント、レイアウトが安定してから計測し、check_ui_contrast は新規の組み合わせをすべて対象にします。
- Claude デスクトップ版は `.secondary`「デスクトップ拡張機能をダウンロード」と 3 ステップのリストだけです：ファイルをインストール、ワークベンチの URL を入力、接続トークンを貼り付け。URL とコピーボタンは同じ行に置き、location.origin を表示します。HTTPS ならそのままコピーできます。127.0.0.1 の HTTP では接続元の案内を踏襲し、2 番目のステップの同じ行で、メンバーには内部 HTTPS、ローカルでは <http://127.0.0.1:8000> を使うよう勧めます。小見出しは増やさず、上記の文字色と背景色のトークンを踏襲します。

## Agent のテーマと台本（agentquery）

- レポート一覧の `.report-row-state` とレポートページの `.report-heading-meta` の同じ行に `.agent-source-chip`「<接続名> から」を表示します。台本の `.script-heading` では h2 の横に同じチップを使い、幅は所属するブロックに揃えて自然に折り返します。
- awaiting_ideas では「Agent によるテーマ作成待ち」を表示し、レポートページでは `.agent-awaiting` の 1 段落で、根拠の集約が完了していること、会話で確定してから保存し直すこと、24 時間の期限を説明します。この状態ではエクスポートや再生成を表示せず、削除は可能です。ポーリングは MCP で保存し直された ready 状態を受け取れます。
- 接続元の表示は text-subtle／bg-subtle、help の文字サイズ、control の角丸を使い、待機中の説明は text-subtle／bg-surface を使います。P1-1 のトークンだけを使い、外部リソースは一切使いません。1440／768／390px で横方向にはみ出さず、組み合わせは check_ui_contrast に含めます。
- テーマ／台本ページの送信は primary、キャンセル、再ラベル付け、絵コンテの追加と削除、履歴の適用、台本の表示とダウンロード、投稿の下書きの作成／オープンは secondary、削除は primary danger です。この節は下記の過去のボタン規則より優先します。

## 新バージョンの通知

- ログイン後の画面では 5 分ごと、およびウィンドウが再びフォーカスされたときに、サーバーの `index.html` が参照するメインスクリプトのファイル名を比較します。現在読み込まれているものと異なる場合は、右下に `.update-notice`：「ワークベンチが更新されました」＋`.secondary`「再読み込み」を表示します。モバイル版では下部ナビゲーションの上に置きます。開発モードではチェックしません。

## Agent の接続と承認（agentauth）

- 承認画面は `.agent-approval-page > .section-card.agent-approval` で、h1 と `.agent-approval-details` だけで構成します。アプリの自称名、コールバック URL、現在のメンバー／ロール、できることをそれぞれ同じ行に並べます。閲覧者には照会だけを列挙し、管理者とマーケティング担当者には照会、下書きの作成、および別途確認が必要な投稿を列挙します。承認は primary、拒否は secondary で、同一オリジンのフォームに既存の CSRF 値を付けて送信します。未ログインやパスワード変更が必要な場合は元の画面を踏襲し、URL には認可リクエストを残します。レスポンスは DENY でフレーム埋め込みを防ぎ、承認ページの same-origin referrer policy によりネイティブフォームの Origin チェックを維持します。
- マイアカウントのパスワードフォームの後に `.agent-connections` を追加し、タイトルと secondary「接続トークンを作成」を同じ行に置き、幅はカードに揃えます。作成は `.member-dialog` を踏襲し、名前と primary の作成ボタンだけを置きます。成功後は `.agent-token-row` に完全なトークンを一度だけ表示し、secondary のコピー／閉じるを置きます。値はコンポーネントのメモリにだけ保持し、閉じるかアンマウントすると消去します。URL やブラウザーストレージには置きません。
- `.list-box.agent-connection-list` の各行 `.agent-connection-row` には、名前、OAuth／接続トークンのチップ、primary danger の取り消しを同じ行に並べます。作成日時、最終使用日時、有効期限は 1 行にまとめて Asia/Taipei で表示し、30 日間使われないと無効になります。取り消しは ConfirmDialog を使い、キャンセルに先にフォーカスし、Escape／Tab とフォーカスの復元に対応します。
- メンバー行に `.member-connections` を追加し、接続数と secondary の全取り消しを同じ行に置きます。0 件のときは無効にし、送信前に ConfirmDialog を使います。900px 以下では行を自然に 2 列に並べ、390px では接続コントロールが行全体を占めます。コールバック、名前、トークンは折り返し可能です。
- P1-1 の色／フォント、control／card の角丸トークンだけを参照し、外部リソースは一切使いません。1440／768／390px で横方向にはみ出しません。文字と背景色の組み合わせは check_ui_contrast に含め、check_agent_auth などはデータとフォントが安定してから計測し、スクリーンショット内の一度きりのトークンはニュートラルなマスクで表示します。

## 投稿（publish）

- Agent の下書き、編集、予約投稿では、既存の形式行の同じ行に `.agent-source-chip.publish-agent-source`「<接続名> から」を表示します。投稿履歴では投稿を確認した接続名を優先して表示し、なければ下書きの作成元を表示します。テーマ由来のチップは残します。編集の作成元は `.publish-editor-heading` に置き、小見出しや説明行は追加しません。text-subtle／bg-subtle、help の文字サイズ、control の角丸を使います。長い名前は自然に折り返し、1440／768／390px ではみ出しません。

デスクトップのサイドバーとモバイルの下部は、順にダッシュボード、投稿データ、アイデア出し、投稿、設定の 5 項目です。投稿は `view=publish` で再読み込みと戻る操作の状態を保持します。この節は下記の旧版の 4 項目ナビゲーション規則より優先します。

- `.publish-page.settings-page` は唯一の PageHeader「投稿」を残し、右側の `.publish-switch` は ready／neutral のチップと管理者用の secondary のスイッチです。オフのときは上部の `.notice.warning` に「投稿機能がオフのため、下書きとしてのみ保存できます」を表示します。ブランドと各アカウントは同じ行に置き、自然に折り返します。
- `.publish-tabs` は下線付きの tablist で、順に新規投稿／ストーリーズ／下書き／予約済み／投稿履歴です。tab、tabpanel、aria-controls、roving tabindex で関連付け、左右キーと Home／End に対応します。閲覧者には投稿履歴だけを表示します。
- composer2：新規投稿／下書き編集の上部の `.publish-composer-tabs` は共通、Facebook、Instagram、Threads、YouTube、TikTok の 6 タブで、tab／tabpanel、方向キー、Home／End に対応します。プラットフォームのタブには投稿のオン／オフスイッチを統合します。準備済みのプラットフォームは緑、未連携／トークン失効および未対応のプラットフォームはグレーで、スイッチは無効でもタブには入れます。その場合は「未連携」と secondary「設定 → プラットフォーム連携」を表示し、settings_tab=connections のナビゲーションを踏襲します。TikTok タブは YouTube と同じく動画のみ対応です：動画以外の形式ではスイッチを無効にし（title「動画のみ投稿できます。画像の投稿はアプリから行ってください」）、タブには同じ文だけを表示します。動画のときは TikTok のキャプションと `.notice.tiktok-caption-notice`「受信トレイにはキャプションが含まれません…」を表示し、その他のオプションはありません。確認ダイアログの TikTok 項目は「動画 · TikTok の受信トレイに送信（キャプションは送信されないため、アプリで貼り付けて投稿してください）」です。投稿履歴の TikTok の成功行には `.status-badge`「受信トレイに送信済み」（pending）／「アプリで投稿済み」（ready）／「TikTok で処理中」と、secondary「キャプションをコピー」（TikTok のキャプションをコピー。上書きしていなければ共通キャプションを使い、押すと「コピーしました」を表示）を付けます。プラットフォームがオフでも編集でき、「オフ」と表示します。
- composer3：ストーリーズは Facebook／Instagram の 2 つのプラットフォームタブとタブのスイッチだけで、接続状態の色、無効化、設定への誘導は composer2 を踏襲します。1 件あたり 1～10 枚で、1 枚につき画像 1 枚または動画 1 本です。ドラッグ、secondary の上へ／下へ、primary danger の削除に対応します。キャプション、形式、投稿オプションの欄はなく、自動保存を踏襲し、投稿／予約投稿の送信ボタンだけを残します。仕様上の理由は同じ場所の赤字にまとめます。9:16 のプレビューは secondary の前へ／次へで切り替え、枚数を表示します。9:16 でない場合は余白が付くことを案内するだけです。IG の動画は 3～60 秒、画像は 8MB 以下（PNG は警告で「Instagram は PNG を自動で JPEG に変換するため、透明な背景は白になります」と案内し、その他の JPEG 以外の形式はエラー）、FB の動画は 60 秒以下で、エラーは赤字で投稿を止めます。今すぐ投稿／予約投稿の確認では、プラットフォーム、アカウント、枚数、メディア、日時を列挙します。履歴には「ストーリーズ」と表示し、展開すると 1 枚ごとの IG のインサイト／最終値を表示し、値がない場合は「—」を表示します。FB は「Facebook はストーリーズのインサイトを提供していません」と表示し、ダッシュボードの情報は増やしません。一部成功後はメディアをロックし、再試行では投稿済みの枚数と失敗した位置を表示します。
- `.publish-composer-grid` は左が編集、右がプレビューです。共通タブには形式、共通メディア、メインのキャプションを置き、プラットフォームタブにはデフォルトで共通に従うキャプションを置きます。編集するとそのプラットフォーム専用になり、secondary「共通キャプションに戻す」で共通に従う状態に戻ります。FB の動画形式は動画投稿／リール（新しい下書きのデフォルトはリール、古い下書きは feed を踏襲）で、非公開オプションは FB タブに置きます。IG の動画は「フィードにもシェア」スイッチを使い、デフォルトはオンです。その下の `.publish-thumbnail.publish-cover` には、「リールのカバー画像」、高さ 54px・9:16 のカバープレビュー、ファイル名とサイズ（カバー画像がまだないときは text-subtle の小さな文字で「JPG／PNG · 8 MB 以内 · 9:16 推奨 · 未アップロードの場合は動画の最初のフレームを使用」）、secondary「カバー画像をアップロード」／「カバー画像を変更」と primary danger「カバー画像を削除」を同じ行に並べます（ファイル入力の aria-label は「リールのカバー画像をアップロード」）。カバー画像は IG のプレビュー動画の poster として使い、9:16 でない場合や PNG の場合は `.notice.warning` で案内するだけです。IG が成功済み／投稿中のときはカバー画像のボタンを無効にします。確認ダイアログの IG 動画の項目は「リール · フィードにもシェアする／フィードにシェアしない · カスタムカバー画像／デフォルトのカバー画像」です。FB の動画では「FB の下書きとして保存」の下に `.publish-thumbnail.publish-cover.publish-facebook-cover`「動画のカバー画像」の行があります（高さ 54px、元の比率どおり、最大幅 96px。カバー画像がまだないときは小さな文字で「JPG／PNG · 8 MB 以内 · 動画と同じ比率を推奨 · 未アップロードの場合は Facebook が自動選択」。ボタンは IG と同じで、ファイル入力の aria-label は「Facebook 動画のカバー画像をアップロード」）。pages_manage_engagement がない場合は、行内に `.notice.publish-cover-hint`（警告ではなくニュートラルな案内）「カスタムカバー画像には pages_manage_engagement 権限が必要です。Meta を連携し直してください」を加えます。カバー画像は FB のプレビュー動画の poster として使い、比率が動画と異なる場合は案内するだけです。確認ダイアログの FB 動画の項目は「動画投稿／リール · カスタムカバー画像／デフォルトのカバー画像（· 下書き）」です。投稿履歴で FB は成功したもののカバー画像が失敗した場合は、同じ行に `.status-badge.pending`「カバー画像未適用」、中国語の理由と secondary「カバー画像を再適用」を表示します（確認ダイアログは「Facebook にカバー画像を再適用しますか？差し替えるのはカバー画像のみで、動画は再アップロードされません。」。閲覧者にはボタンを表示しません）。成功済み／投稿中のプラットフォームと、一部送信済みの Threads のオプションはロックします。
- `.publish-preview` はブランドの頭文字のアバター、アカウント名、本文、ローカルのメディアを使い、外部リソースは読み込みません。共通プレビューにはオンになっているプラットフォームの secondary の小さなボタンだけを並べ、プラットフォームタブではそのプラットフォームに固定します。本文は簡易的な文字数／行数のしきい値で折りたたみ、secondary「もっと見る／閉じる」で切り替えます。@／ハッシュタグは link-color を使い、Threads は最初のトピックタグと最初の段落／返信スレッドを表示し、メディアは最初の段落にだけ付けます。IG の画像は 4:5／正方形は 1:1、リールは 9:16、FB の動画投稿／Threads は元の比率を使います。動画は常に全体を表示（contain）し、枠と動画の比率が異なる場合は `--media-letterbox` で余白を埋めます（たとえば縦長の枠内の横長動画は上下に余白）。送信するのは元のファイルで、プラットフォームはトリミングしないためです。画像は枠いっぱいに表示します。767px 以下ではプレビューを編集エリアの上部に置き、1440／768／390px で横方向にはみ出しません。
- Threads の分割は空行、改行、句点を優先し、それでも収まらなければ強制的に切ります。Unicode のカウント用データとテストベクターは shared/publish_threads_vectors.json に置き、pytest とフロントエンドの両方で検証します。自動モードでは元のキャプションにリアルタイムで追従し、手動で編集／追加／削除すると再計算を止めます。最低 1 段落は表示します。各段落は 1 行で段落番号／文字数／primary danger の段落削除を並べます。secondary「メインのキャプションで再分割」は先に ConfirmDialog で上書きを確認し、送信するキャプションには番号を付けません。
- プラットフォームタブでは、文字数、ハッシュタグ、@、メディアの長さ／比率の規則違反を赤字で表示し、タブのラベルに赤い点を付けます。バックエンドからの案内は notice warning で表示します。オンになっているプラットフォームにブロッキングエラーが 1 つでもあれば投稿を無効にします。エラーは 1 か所にだけ表示します：`.publish-footer` の 1 行目の `#publish-disabled-reason`（赤字で 1 行を占有し、「今すぐ投稿／予約投稿」と送信ボタンの上に位置）で、「プラットフォーム：理由」の形式を「；」でつなぎ、オンになっているプラットフォームと、現在表示中でオフになっているプラットフォームのタブを列挙します。タブ内には別途エラー一覧を置かず、タブのラベルの赤い点だけを残します。Threads の文字数超過は入力欄の下にだけ表示し、ここでは繰り返しません。この種のエラーだけが残っている場合は「先に上に表示されたエラーを修正してください」と表示します。投稿機能がオフのときは「投稿機能がオンになっていません」だけを表示します。どのプラットフォームもオンになっていない場合は「投稿先のプラットフォームをオンにしてください」から始め、その後に現在のタブのエラーを続けます。ボタンの title には理由の全文を残します。publish-actions には唯一の primary の投稿／予約投稿と secondary の下書き保存を残します。確認ダイアログはプラットフォームごとに形式、IG のフィードオプション、FB の非公開、Threads の段落数、およびアカウント／キャプション／メディア／日時を列挙します。履歴の Threads の詳細の進捗は「N／M 件投稿済み」と表示します。
- 新規投稿の初期状態は空のフォームだけです。初めてキャプション／プラットフォームを入力した後は遅延して自動保存し、初めてのアップロードや下書き保存ではすぐに保存します。タブの切り替え／ナビゲーションの前に未保存の内容を保存し終えます。形式の選択だけでは下書きを作りません。`publish_post_id` はページをまたぐ URL で現在の下書きを保持します。secondary「新規投稿」は先に保存してからクリアし、単なる再読み込みでは下書きは増えません。
- 投稿ページには AI がキャプションを書く UI はありません：メインのキャプションの上に進捗、不合格、完了の案内はなく、「書き直す」「AI のキャプションを適用」もなく、下書き一覧に「AI 作成中」もありません。古い下書きのデータベースにキャプションのジョブデータが残っていても、画面には AI の状態を表示しません。テーマから作成した下書きのメインのキャプションは、タイトル、冒頭、ハッシュタグで構成した初稿で、そのまま編集できます。
- 下書きは `.list-box.publish-records` を使い、各行に最終更新日時、形式／テーマから／AI 作成中のチップ、1 行で省略したキャプション、メディア数、プラットフォーム、secondary の編集／primary danger の削除を並べます。削除には ConfirmDialog が必要です。キャプション、メディア、プラットフォームがない過去の空の下書きは非表示にするだけです。投稿履歴には送信済み、失敗、または期限切れの投稿だけを列挙します。
- `.list-box.publish-records` 内の `.list-row.publish-record` は、日時、形式、キャプションの冒頭、プラットフォーム、状態を同じ行に並べます。予約投稿は 1 分前にロックします。「ページに公開しない」で送信した Facebook は、プラットフォーム名の後に「 · 非公開」と表示します（一覧の行と各プラットフォームの結果の両方）。履歴は `.publish-targets` を展開でき、成功したリンク／安全な中国語の理由を表示します。Facebook の非公開で成功した結果のチップは `.status-badge.neutral`「Facebook · 成功 · 非公開」（「プラットフォームで削除済み」と同じ色系。失敗や処理中は元の色のまま同じ接尾辞を付けます）です。失敗時は失敗したプラットフォームだけを再試行し、期限切れのものはすぐに投稿するか予約し直せます。下書きの削除は primary danger で確認が必要で、その他の操作は secondary です。
- 色、フォント、角丸は P1-1／共通トークンだけを参照し、外部リソースは一切使いません。文字と背景色の組み合わせは check_ui_contrast に含めます。1440／768／390px で横方向にはみ出さず、モバイルの 5 列ナビゲーションはセーフエリアを確保し、check_publish などはデータ、フォント、レイアウトが安定してから計測します。

## プラットフォームの OAuth 連携（metaoauth）

- プラットフォーム連携は順に Meta、Threads、YouTube、TikTok、LINE 通知、jev を表示します。Meta／Threads のカード上部の `.oauth-account` には、アカウント名、IG のユーザー名、状態のチップ、台北時間の有効期限を同じ行に並べます。ready は連携済み、pending はまもなく期限切れ、neutral は未連携、failed は権限不足／失敗です。不足している権限は `.notice.danger.oauth-permissions` に列挙し、権限名は自然に折り返します。
- 各カードには secondary の「接続テスト」を残し、強制的に再チェックします。連携／再連携は primary のボタンです（Threads でインサイトの権限だけが不足している場合は secondary に変わります。threadsdata を参照）。ページが複数あるときは、`.oauth-page-choice` のドロップダウンと primary「このページを使用」が連携ボタンの代わりになります。内部 HTTPS 以外のオリジンでは連携を無効にして `.notice.oauth-origin` を表示し、URL は API が提供します。
- 初回設定の手順とコールバック URL は「設定ガイド」のポップアップに移したため（guides を参照）、カードには重複して表示しません。`.oauth-manual` は「手動設定（詳細）」を折りたたみ、名前付きの認証情報フォーム、マスク、バージョン、パスワード入力を残します。Threads のアプリ ID とシークレットはそのまま表示し、その他の欄は折りたたみます。コールバックの結果は固定の中国語の `.notice.success`／`.notice.danger` だけを使い、結果の URL パラメーターを取り除き、トークンをブラウザーに保存しません。
- P1-1 の色とシステムフォントのトークン、既存の control／card の角丸を使い、外部リソースは一切使いません。コントロール行は自然に折り返し、URL と権限は overflow-wrap を使います。1440／768／390px で横方向にはみ出しません。新しい組み合わせは check_ui_contrast に含め、check_meta_oauth で連携、ページの選択、権限不足、Threads、バックオフィス以外のオリジン、ガイドを検証します。

## プラットフォーム設定ガイドのウィンドウ（guides）

- Meta、Threads、YouTube、LINE 通知のカードと TikTok のカードでは、タイトル行の右側、「接続テスト」の前に secondary の「設定ガイド」があります（jev にはありません）。押すとサイト内のポップアップが開き、新しいブラウザータブは開きません。カードとページ自体には `target="_blank"` のリンクを置いてはいけません（例外はウィンドウ内の管理画面へのハイパーリンクだけです。下記参照）。コールバック URL と Webhook URL はウィンドウ内でだけ表示・コピーし、カードには重複して表示しません。
- `.ideation-modal-backdrop > .guide-dialog` は body に配置します：`role="dialog"`、`aria-modal`、`aria-labelledby` はタイトルを指します。タイトル行は固定で、右上に secondary の「閉じる」、内容の `.guide-body` は独自にスクロールします。開いたときのフォーカスは「閉じる」にあり、Tab はウィンドウ内で循環します。Esc、閉じる、背景のクリックのいずれでも閉じられ、閉じた後はフォーカスが「設定ガイド」ボタンに戻ります。390px では全画面（背景の余白なし、高さ 100dvh）で、内容はスクロールでき、横方向にはみ出しません。
- 内容は `frontend/src/platformGuides.ts` にあり、開発者向け管理画面に初めて触れる人向けに書きます（guides2 で書き直し）。各ガイドには所要時間の目安 `minutes`、「始める前に必要なもの」`needs`、折りたためる「用語ミニ辞典」`glossary`、節ごとの手順があります。各手順で行うことは 1 つだけで、ボタンとメニューは「」で実際の画面上の用語を示し、確信がない場合は「（英語の画面では …）」を添えます。手順には `check`（「✅ 完了すると表示されるもの」、`.notice.success`）と `trouble`（「⚠️ うまくいかないときは（よくある質問）」、`.notice.warning`）を付けられます。Meta は「Facebook ページ」「Instagram」「アカウント連携」の 3 節に分けます。TikTok 以外は最後の手順がすべて「ワークベンチに戻って…」です：Meta、Threads、YouTube は「連携済み」と 1 時間ごとの同期を、LINE は「接続テスト」「接続に成功しました」を説明します。
- ウィンドウの冒頭の `.guide-intro`：「所要時間：約 N 分」、「始める前に必要なもの」のリスト、デフォルトで折りたたまれた `details.guide-glossary`（「用語ミニ辞典」）です。手順の `.guide-steps` は小さな四角の番号（`::before` のカウンターで、小節をまたいで連番）を使います。URL や権限は `.guide-copy`（`<code>` と secondary の「コピー」。成功すると「コピーしました」を表示）で示し、コールバック URL は `/api/oauth/status` の callbacks から、LINE の Webhook URL は設定の WEBHOOK_PUBLIC_URL から取得します。未設定のときは「未設定」と表示してコピーを無効にします。手順には `links` を付けられ、`.guide-links` にプラットフォームの管理画面へ直接移動するハイパーリンク（developers.facebook.com、console.cloud.google.com、manager.line.biz、developers.line.biz、developers.tiktok.com など）を並べます。`target="_blank"`、`rel="noopener noreferrer"` です。内容には実在のアカウント、氏名、ローカルパスを入れません。
- TikTok のカードは YouTube と同じレイアウト（`.connection-card`）です：アカウント行と状態のチップ、「アクセストークンは自動更新されます」の説明、refresh token の台北時間の有効期限。Client key／Client secret の 2 つの認証情報欄はカードに直接並べ（「手動設定」の折りたたみなし）、設定前は「TikTok アカウントを連携」を無効にします。連携済みのときは secondary「連携を解除」が ConfirmDialog を経て、同期済みのデータが削除されること、TikTok 上の動画には影響しないことを説明します。カードの最後の行の `.notice.tiktok-comments`「コメント（任意）」では、コメントの読み取りには法人の身元が必要であることを説明します。ガイドではユーザーに Sandbox でアプリを作成して連携させ、コールバック URL と 4 つの権限はそれぞれコピーできます。範囲は `docs/jp/TikTok計画.md` を参照してください。
- 配色は既存のトークンだけを使います：本文と冒頭の情報は text-main／bg-surface、辞典の説明は text-subtle／bg-surface、URL ブロックと「よくある質問」は text-subtle／bg-subtle、「完了すると表示されるもの」は state-success／bg-subtle、手順番号は bg-surface／brand-primary です。角丸は control／card で、外部リソースは一切使わず、check_ui_contrast に含め済みです。チェックは `check_platform_guides.py`（5 つのガイドのタイトル、始める前に必要なもの、確認ポイント、辞典の展開、コピー、Esc／背景／閉じる、フォーカスの復元、カードに新しいタブのリンクがないこと、ウィンドウ内の管理画面リンクのドメインと `target`／`rel`、3 種類の幅で辞典を展開しても横方向にはみ出さないこと、最後までスクロールすると最後の手順が見え、タイトル行が固定されていること。スクリーンショットは `.runtime/guides2-screens/`）とフロントエンドの `platformGuides.test.mjs` で行います。

## 投稿データの即時同期（metricsync）

- 管理者／マーケティング担当者の投稿データのページヘッダーでは、secondary「今すぐ同期」が「更新 ↻」の代わりになり、投稿とインサイトの同期を 1 回分予約します。閲覧者は引き続き「更新 ↻」だけです（ワークベンチのデータを読み直すだけ）。実行中は「同期中…」、予約済みのときは「同期を予約済み…」、クールダウン中は「今すぐ同期（N 秒）」を表示して無効にし、秒数はバックエンドの `retry_after` に従います。完了後は自動で再読み込みして sync-notice で知らせます。1 時間ごとの定期実行が終わっても自動では再読み込みしません。

## 投稿データのインサイトパネルの幅（metricwidth）

- 2026-10-23 以降は下記の postcenter に置き換えられ、インサイトは中央に移りました。元の規則：デスクトップの単一投稿詳細で、右側のインサイトパネル（`.post-metrics`）は 380px 固定、左側の一覧は 320px、中央のコメント欄は自動です。データのスナップショット表はセルごとに 16px の文字パディングを踏襲し、取得日時「2026/10/21 13:04」と指標の列名は 1440px 幅ですべて 1 行に収めます。数値が百万単位のときは取得日時を日付と時刻の間で改行してもかまいませんが、日付を分割したり横方向にはみ出したりしてはいけません。

## Threads の投稿データ（threadsdata）

- 投稿データの Threads タブは FB／IG と同じ動作です：投稿一覧と投稿日のフィルター、単一投稿の「投稿の成果」と読み取り専用の「コメントと返信」（コメントの日付、もっと表示は他のプラットフォームと同じ）。管理者／マーケティング担当者には同じく「コメントを取得」「すべて再取得」「停止」があり、コメント同期カードのタイトルは「Threads 返信」です。コントロール、小見出し、説明行は追加しません。
- インサイトは Threads にある 6 項目だけを表示し、順に「ビュー、いいね、返信、リポスト、引用、シェア」です（返信は comments 欄、リポストと引用はスナップショットの extra_json から読みます）。リーチと保存は表示しません。データの推移グラフの指標ドロップダウンは同じ 6 項目でデフォルトは「ビュー」、スナップショット表の列は「取得日時、ビュー、いいね、返信」です。「—」はプラットフォームがまだ提供していないこと、0 はプラットフォームが 0 を返したことを表します。FB／IG は元の 6 項目と列を維持します。
- 設定ページの Threads カード：連携済みで投稿権限はそろっているものの、`threads_manage_insights`、`threads_read_replies` が不足している（既存の連携でまだ取得していない）場合は、`.oauth-account` の下に `.notice.warning.oauth-permissions`「インサイトと返信の権限を得るには連携し直してください」を表示します。状態のチップは「連携済み」のままで、連携ボタン「再連携」は `.secondary` に変わります。投稿には影響しません。権限を取得すると案内は消え、ボタンは primary に戻ります。投稿権限が不足している場合は従来どおり `.notice.danger` と primary のボタンです。
- アイデア出しの投稿選択：期間内に Threads の投稿がある場合だけ「Threads」タブが 1 つ増え（FB／IG のタブは変わりません）、投稿行のプラットフォームのチップは「Threads」、ステップ 3 の要約では IG の後に「、Threads N 件」を付けます。Threads の投稿がない場合、画面はこれまでと同じです。
- 返信の読み込み待ちでは Threads の文言（「Threads が一時的に呼び出しを制限しています…」「Threads の応答がタイムアウトしたか、一時的なエラーが発生しました…」）を表示し、Meta の使用量は表示しません。
- P1-1 の色とシステムフォントのトークン、control／card の角丸だけを使い、外部リソースは一切使いません。権限の案内の text-subtle／bg-subtle は check_ui_contrast に含め済みです。check_posts_batch2（Threads タブの一覧、指標名、返信、1440／768／390px）、check_meta_oauth（再連携の案内）、check_ideation_fixes（Threads タブ）、check_followers_frontend（Threads タブが投稿一覧を読むこと）でカバーし、チェックの入口は増やしていません。

## メンバーとロールの権限（members）

この節は旧版の設定タブと、管理者以外向けの読み取り専用の設定の表示規則より優先します。管理者の設定タブは順に AI、プラットフォーム連携、メッセージ分類、ワークスペース、メンバー、マイアカウントです。その他のロールは機能権限に応じて表示します（プラットフォーム連携＝`connections.manage`、AI＝`ai.manage`、メッセージ分類とワークスペース＝`settings.manage`、メンバーは管理者のみ）。マーケティング担当者と閲覧者には「マイアカウント」だけを表示し、ブックマークから他の設定に移動した場合もこのタブを表示します。サイドバーのブランドメニューにはアクセスできるブランドだけを列挙し、ブランドを持たない管理者以外のユーザーには「ブランドがまだ割り当てられていません。管理者に連絡してください」を表示します。モバイルでは `.mobile-logout` を残します。

- メンバー編集のロールは `fieldset.member-role-options` のラジオボタンリストに変わりました：各行はネイティブの radio で、名前（太さ 600、radio の名前として使用）の下に text-subtle の小さな文字でできることを列挙します（`aria-describedby`）。組み込みの 3 種類が先、カスタムロールが後です。メンバー一覧の下の `.member-roles` は「ロール」エリアです：`.role-row` に名前（組み込みには neutral の「組み込み」バッジ）、権限の要約、「メンバー N 人」を並べ、カスタムロールには secondary の編集／削除もあります（メンバーが残っている間は削除を無効にし、title で説明します）。ロールの追加／編集は `.member-dialog` を踏襲します：ロール名と「使える機能」のチェックボックスリストで、「投稿の送信・再試行・取り消し」にチェックを入れると「投稿の下書き編集」にも一緒にチェックが入り、後者を外すと前者も外れます。投稿ページで `publish.submit` がない場合は、「投稿／予約投稿」ボタンの代わりに muted の文字を表示し、予約の取り消し、再試行、再適用のボタンを非表示にします。
- メンバーページは `.section-card.members-card` を使い、タイトル行の右側に primary の「メンバーを追加」を 1 つ置きます。`.list-box.member-list` 内の `.list-row.member-row` には、名前／ユーザー名、ロール、ブランド、状態、secondary の編集を並べます。名前は太さ 600、ユーザー名は text-subtle です。ブランドはカンマ区切りで列挙し、1 行で省略して完全な title を付けます。状態は ready／neutral／pending を使います。390px では名前とロールを同じ行に置き、編集は右寄せ、その他は自然に折り返します。
- 追加と編集は既存のモーダルの枠を踏襲し、`.member-dialog` は dialog／aria-modal、タイトルの関連付け、Esc、Tab のフォーカス循環、閉じた後のフォーカス復元を備えます。ロールは `.member-role-options` のラジオボタンリストを使います。管理者以外ではブランドの checkbox を表示し、ブランドが 1 つだけならデフォルトでチェックします。管理者ではブランドの checkbox を非表示にし、「管理者はすべてのブランドにアクセスできます」を表示します。
- 送信は primary、キャンセル／コピー／パスワードのリセット／有効化は secondary、無効化は primary danger で、ConfirmDialog による二重確認を経ます。保護規則のエラーは `.notice.danger` を使い、window.confirm は使いません。送信ブロックごとに主要な送信ボタンは 1 つだけ置きます。
- マイアカウントのパスワードフォームの後に、管理者には `.recovery-code` の段落が追加されます：h3「パスワードのリカバリーコード」と状態のチップ（設定済み `.ready`／未設定 `.neutral`）を同じ行に置き、説明、「現在のパスワード（確認用）」欄、secondary「リカバリーコードを発行／リカバリーコードを再発行」を並べます。成功後は `.member-dialog` と `.temporary-password` を踏襲してリカバリーコードを一度だけ表示し、secondary のコピーと「保存しました」を置きます。
- 初回セットアップページ：データベースにアカウントが 1 つもない場合、未ログインの画面は初回セットアップの表示に変わり、ログインページのレイアウトと欄のスタイルを踏襲します。左側に eyebrow「初回セットアップ」＋「ようこそマーケティングワークベンチへ。」、右側に h2「管理者を作成」、管理者のユーザー名、パスワード、パスワードの再入力、ブランド名、primary「作成してログイン」を置きます。2 回のパスワードが異なる場合は role=alert で「パスワードが一致しません」を表示し、送信しません。ローカル以外の URL で開いた場合は「ホストのパソコンでセットアップしてください」と説明だけを表示し、フォームはありません。作成に成功するとそのままワークベンチに入り、以後はログインページだけを表示します。
- ログインページでは「許可されたチームメンバーのみ利用できます」の下に、折りたたまれた `.login-forgot`「パスワードをお忘れですか？」を置きます：メンバー向けの説明、展開して初めて描画される管理者のリカバリーコードフォーム（管理者のユーザー名、リカバリーコード、新しいパスワードの 2 回入力、primary「パスワードをリセット」。ラベルはログインフォームと同じ名前にしません）、リカバリーコードがない場合のホスト上のコマンド `.login-command` とロックの注意です。成功後は `.notice.success` がフォームの代わりに表示され、自動ではログインしません。
- 仮パスワードのダイアログは `.temporary-password`、ui-font-mono を使い、secondary のコピーを提供し、「表示されるのは今回だけです。本人に伝えてください。初回ログイン時にパスワードの変更が必要です。」を表示します。閉じるとメモリ上の値を消去し、URL やブラウザーストレージには保存しません。
- マイアカウントでは、ユーザー名、名前、ロール、アクセスできるブランドを 1 行に表示し、その下にまず `.language-picker.account-language`「表示言語」のドロップダウン（選択肢は各言語自身の表記で表示し、選ぶとすぐにアカウントに保存して再読み込み）、次に 3 つのパスワード欄と primary の「パスワードを変更」を 1 つ置きます。ログインページでは `.login-panel` の右上に同じ形の `.login-language` ドロップダウンを置き（モバイルではフォームの上の右寄せ）、ログイン前は localStorage にだけ記録し、ログイン後にアカウントに言語設定がなければそれをアカウントに保存します。パスワード変更が必要な場合は `.password-required` の全画面「新しいパスワードを設定してください」を表示し、フォームとログアウトだけで、サイドバー／下部ナビゲーションはありません。成功して初めてワークベンチに入ります。
- 閲覧者のアイデア出しでは、ブランドの選択、既存の一覧とカードを残し、アイデア出しのフォーム、編集、元に戻す、台本の表示、投稿の下書きの作成／オープン、削除を非表示にします。台本は引き続き「台本のバージョン」一覧から表示できます。すべてのロール制限は API でも同時に適用します。

追加するスタイルは P1-1 の色、システムフォント、ui-radius-control／ui-radius-card だけを参照し、外部リソースは読み込みません。1440／768／390px で横方向にはみ出さず、新しい文字と背景色の組み合わせは check_ui_contrast に含めます。

## サイト全体の統一 第 2 弾（uniform2）

この節は uniform 第 1 弾のボタンとワークスペースの折りたたみ規則より優先します。変更するのは表示だけで、API、文言の意味、権限は踏襲します。

- ワークスペースの 5 グループはそれぞれ 1 枚の `details.workspace-group.section-card` で、summary の行全体がクリックでき、section-title／600、右側に展開アイコンを置きます。summary／内容は panel-padding を使い、外側でパディングを重複させません。展開した内容は `.workspace-subsection` と h3 を使い、タイトルの下 12px、小節の間 24px で、border-subtle で区切ることができます。カード同士の間隔は 24px で、PC 起動時の自動起動と揃えます。独立したフォームはそれぞれの送信を残し、グループ全体で主要ボタンの数を制限しません。
- チェックボックスの行と次の欄のラベルの間は最低 16px とし、設定エリアの同種の行すべてに適用します。アイデア出しの既存のコンテンツエリアの寸法は変えません。
- 投稿一覧は `.post-items.list-box` の外枠を使います。各 `.post-card.list-row` の `.post-card-meta` にはプラットフォームのチップ、アカウント、種類を同じ行に並べ、本文は最大 2 行、日付は text-subtle です。行の間は 1px の border-subtle、選択中は bg-subtle／左側に 3px の brand-primary のバーです。行自体を角丸のカードにはしません。ページ送りはコンテナの外の下に置き、投稿日とカスタム日付のフィルターは残します。
- フォロワー数の年／月／週はコンパクトなツールバーで、1440px ではドロップダウンと数値を同じ行、768／390px ではドロップダウンで 1 行、数値で 1 行にします。週は「第 N 週」と表示し、完全な日付は選択肢の title に残します。メニューのすべての選択肢が文字、パディング、ネイティブの矢印を収められる必要があり、要素の scrollWidth を確認するだけでは不十分です。
- 390px ではグローバルな `.mobile-settings-controls` をメインコンテンツの最上部、すべての h1 の上に置き、`.mobile-brand-picker` と `.mobile-logout` の動作／閲覧者のログアウトを残します。下部の現在のページは aria-current="page"、brand-primary の塗り／bg-surface の白文字／opacity 1 を使います。enabled のままにし、繰り返しクリックしても現在のページをリセットせず、hover と選択時は同じ背景色を保ちます。
- モバイルの投稿詳細、インサイト、コメントのカードはコンテナの 16px の gap で並べ、重なっていた上下の margin を取り除きます。デスクトップのカードの間隔は 24px です。
- プラットフォームの認証情報は名前付きの form を残し、`.credential-heading` の 1 行目は label（`.credential-name`＋`.credential-env`）、2 行目は `.credential-status`（状態のチップ＋マスク＋右側の変更／設定）です。モバイルでは名前を途中で改行せず、環境変数は折り返し可能です。入力の展開とパスワードの動作は変わりません。
- 操作ボタンは塗りの primary、キャンセル、戻る、ページ送り、削除などの副次的な操作は quiet を使います。P1-1 の色／システムフォントと control／card の角丸トークンだけを使い、外部リソースは読み込みません。新しい組み合わせは check_ui_contrast に含めます。

アイデア出しのコンテンツのスタイルは変えません。モバイル共通のブランド行は画面全体を変えるため、画面全体のスクリーンショットの差分ゼロという要件と矛盾します。実際のピクセルと寸法の比較は uniform2 のレポートに記載しています。


## Obsidian コメントとテーマの操作（obsidian）

- ワークスペース → データに `.obsidian-settings` を追加し、1 つの欄「Obsidian コメントフォルダー」と、`.obsidian-actions` の「Obsidian フォルダーを保存」「今すぐ Obsidian に同期」の塗りの primary ボタンを置きます。名前でエクスポートフォルダーの保存操作と区別します。表示と操作は管理者だけで、その他のロールには「マイアカウント」だけが表示されます。読み込み中や操作中は無効にし、結果は status／alert を踏襲し、コントロール行は自然に折り返します。
- `.ideation-card` の左上の `.idea-card-heading` には番号（`.idea-number`、text-subtle）と、古いデータの「再生成済み」「#番号 から派生」の印を置きます。選択用の checkbox はもうなく、カードエリアの上部にも一括操作の行はありません。
- 下部の `.idea-card-actions` には secondary だけを置きます：台本がある場合はまず「台本を表示」、次に「投稿の下書きを作成」（未投稿の下書きがすでにある場合は「投稿の下書きを開く」）、最後に「Agent に台本を依頼」で、間隔 8px、左寄せ、flex-wrap です。「Agent に台本を依頼」はレポートが ready のときだけ押せ、カード内の `.agent-handoff`（アイデア出しと同じ 4 つの引き継ぎボタン、カード内では 2 列固定）を切り替えます。コマンドにはレポート番号とテーマ番号を含め（`/mwb:script …`。コピー版は `topic_index` を含む）、一度に展開できるカードは 1 枚だけです。ウェブページ自体は AI を呼び出して台本を書きません。元に戻せる場合は独立した secondary「前のバージョンに戻す」を表示し、省略メニューはありません。
- 再生成と派生テーマは削除しました：カードには進捗、スケルトン、失敗の案内はありません。レポート JSON 内の古い ideas_job はデータに残すだけで画面には影響せず、古いレポートの「再生成済み」「#番号 から派生」の印は引き続き表示します。レポートの処理中はカードの操作と削除を無効にします。
- 投稿のコメント範囲に「すべて」を追加しました。範囲のパラメーターがない場合のデフォルトは引き続き直近 30 日、元のコメントへのリンクのデフォルトは直近 90 日で、comment_range=all を明示したときだけすべてを選択し、再読み込みしても選択した範囲を保持します。すべての範囲のときだけ secondary の「すべて再取得」を表示し、確認後に full_rescan=true を送ります。通常の取得と今すぐアイデア出しは増分です。初回の取得は最後まで読みます。従来の 7／30／90 日ともっと表示はそのまま残します。
- すべて P1-1 の色／フォントと control／card の角丸トークンを踏襲し、390px ではみ出しません。新しい文字と背景色の組み合わせは check_ui_contrast に含めます。check_ideation_fixes、check_workspace、check_comment_sync_frontend で操作とモバイルをカバーし、既存の隔離チェックの入口の数は変わりません。

## テーマから投稿の下書きを作成（ideadraft）

- テーマカードの右上の `.idea-card-tools` には secondary.small の「編集」だけを置き、ready でない場合や編集中は無効、閲覧者には非表示です。下部の `.idea-card-actions` は上記のとおりです。未投稿の下書きがすでにある場合は「投稿の下書きを開く」と表示し、直接開きます。どちらのグループも flex-wrap で、狭いカードでは自然に折り返します。
- 編集を押すと `.idea-editor` がその場でテーマの内容と置き換わり、ラベル付きの 5 つの欄が順にタイトル、冒頭、切り口、撮影できる画面、キーワードです。各欄は最大 1000 文字で、空にはできません。下部に primary の保存と secondary のキャンセルを置きます。保存後はラベル行に `.ideation-chip.idea-edited`「編集済み」を表示し、元の発言は読める状態を保ちます。secondary の前のバージョンに戻すは history を踏襲し、Markdown／Word の再エクスポートには編集後の内容を使います。
- 「投稿の下書きを作成」は直接下書きを作成して投稿ページを開きます。確認ダイアログや「参考台本」のチェックはなく、AI も呼び出しません。下書きのメインのキャプションは、タイトル、冒頭、ハッシュタグの初稿です。
- 作成後は同じブランドの投稿ページの「新規投稿」に切り替え、指定の下書きを読み込みます。上部の `.notice.success` に「テーマから下書きを作成しました。動画をアップロードし、投稿先のプラットフォームを確認してください。」を表示します。下書き ID は URL の `publish_post_id` に保存し、再読み込みしても読み込みます。読み込み中は編集と自動保存を無効にします。
- 投稿履歴／予約済みの `.publish-record-heading` では、形式のチップの横の同じ行に `.publish-source`「テーマから」を置き、説明行は別に追加しません。プレビューは text-main／bg-surface、body の文字サイズ、作成元の表示は text-subtle／bg-surface、help の文字サイズを使い、成功の案内は notice の state-success／bg-subtle を踏襲します。すべて P1-1 のトークン、既存の control／card の角丸、ローカルのリソースを使い、1440／768／390px で横方向にはみ出しません。
- 投稿履歴の一覧の上に 1 行の `.publish-presence` を置きます：左側は text-subtle／help の文字サイズで「前回の確認：<台北時間>」（各プラットフォームの結果のうち最新の presence_checked_at を使い、なければ「未確認」）、右側は塗りの `.primary`「プラットフォームの投稿を確認」（ユーザーの指定で塗りにしており、このタブで唯一の主要ボタンです。閲覧者には非表示）です。確認中はボタンに「確認中…」を表示して無効にします。完了後は `.notice.success`／`.notice.warning` で「N 件を確認しました。プラットフォームで削除済み：M 件」を表示し、判定できなかったプラットフォームがある場合は warning を使って中国語の理由を添えます。429 は `.notice.danger` で「先ほど確認したばかりです。しばらくしてからもう一度お試しください」を表示します。各プラットフォームの結果の `deleted_at` に値がある場合、チップは `.status-badge.neutral`「<プラットフォーム> · プラットフォームで削除済み」で、「投稿を表示」は表示せず、代わりに「<台北時間> に検出」を表示します。一覧の行で投稿全体が成功し、成功したプラットフォームがすべて削除されている場合は、状態のチップを neutral の「プラットフォームで削除済み」に変えます。一部だけ削除されている場合は元の状態のまま「· 一部削除済み」を付けます。削除されたプラットフォームも成功として扱い、再試行や予約し直しで再送されることはありません。既存のトークンだけを使い、1440／768／390px で横方向にはみ出しません。

- composer1（改版 1／3）ではバックエンドだけを追加しました：既存の投稿ページは元のレイアウトのままで、API が platform_options、effective_platform_options、warnings、スレッドの進捗を追加で返します。フロントエンドは後続の改版で、プラットフォームの動画オプション、段落ごとのプレビュー、案内を既存のブロックに統合し、説明行は追加しません。今回は新しい文字／背景色の組み合わせやボタンを追加していないため、コントラストのアサーションを拡張する必要はありません。既存の 390px とボタンの 3 階層の規則は維持します。

## 色とフォントのトークン（P1-1）

色とフォントは `frontend/src/style.css :root` に集約し、CSS と inline／SVG はトークンを使います。外部フォント、CDN、リモートの `@font-face` は読み込みません。デフォルトの本文／見出しには `--text-main` を使い、ブランド面でだけ `--brand-primary` を使います。文字サイズ、寸法、間隔、角丸のトークンは元の値を維持します。

| トークン | 定義 | 用途 |
|---|---|---|
| `--bg-app` | `#F8FAFC` | サイト全体のキャンバス |
| `--bg-surface` | `#FFFFFF` | カード、コントロール、反転文字 |

| `--text-main` | `#0F172A` | 本文と見出し |
| `--text-muted` | `#64748B` | 白背景／キャンバス上の補助テキスト |

旧名は別名として維持します：`--ink:var(--brand-primary)`、`--paper:var(--bg-surface)`、`--line:var(--border-subtle)`、`--muted:var(--text-muted)`。`--accent:var(--state-pending-text)` は互換性のための別名にすぎず、新しいスタイルから参照してはいけません。既存の参照はすべて意味に応じて置き換え済みです。

緑はインタラクションと成功だけを表します。警告は琥珀色、エラー、要修正、危険は赤を使います。フォーカスの外枠には 3:1 を満たす濃い緑を使い、リンクと成功の文字は 4.5:1 を満たします。明るい緑を白背景の小さな文字に使ってはいけません。淡い背景のニュートラルなラベルには `--text-subtle` を使い、補助テキストが淡い背景上で 4.5:1 に届かないことを避けます。`transparent` と `currentColor` は CSS の透明／継承の意味を保ち、その他の派生色は `color-mix()` でトークンを参照します。

主な組み合わせの WCAG 2.1 コントラスト（上表の値から計算。トークンを調整するときの参考用で、`check_ui_contrast.py` の実測値が優先します）：

| 文字 | 背景色 | コントラスト | 備考 |
|---|---|---|---|
| `--text-main` | `--bg-surface` | 17.85:1 | |
| `--text-muted` | `--bg-surface` | 4.76:1 | |
| `--text-muted` | `--bg-app` | 4.55:1 | 下限の 4.5 に近く、これ以上淡くできない |
| `--text-subtle` | `--bg-subtle` | 6.92:1 | 淡い背景の文字をこのトークンに変えた理由 |
| `--bg-surface` | `--brand-primary` | 12.61:1 | 主要ボタン、サイドバー |
| `--state-pending-text` | `--state-pending-bg` | 4.51:1 | 下限の 4.5 に近い |
| `--state-success` | `--bg-surface` | 5.48:1 | リンク、フォーカス、成功の文字 |
| `--state-danger` | `--state-danger-bg` | 5.30:1 | |

## マーケティングのナビゲーションと DOM（nav）

`.platform-connections` には 3 枚の `.settings-section.connection-card` を置きます：Meta（FB／IG）、LINE 通知、jev です。タイトル行の右側は塗りの「接続テスト」です。各欄の `.credential-field` は名前付きの form で、`.credential-heading` には環境変数名、DB／env／未設定の出所、マスクを同じ行に表示し、`.credential-controls` には password と保存／キャンセルを置きます。設定済みの場合は変更を表示します。削除できるのは DB の値だけです。削除すると env に戻ります。バージョンが競合した場合は秘密情報の入力をクリアして中国語のエラーを表示し、再読み込みで新しいバージョンを取得します。接続テストは保存済みの設定だけをテストし、空のオブジェクトを送ります。

プラットフォームの API と設定ページはすべて管理者限定です。その他のロールにはプラットフォームのタブを表示せず、認証情報のリクエストも送らず、「マイアカウント」だけが表示されます。最後の `.connection-endpoints` は WEBHOOK_PUBLIC_URL と meta-inbound、line-notify の 2 つの URL を読み取り専用で表示します（line-inbound は廃止済みで、もう表示しません）。その下には .env 専用の名前と理由を列挙する段落が 1 つだけあり、実際の値はありません。すべての password は平文で読み戻さず、ブラウザーストレージにも入れません。Webhook の URL は、公開してコピーすることを特別に許可した読み取り専用の設定です。

名前／欄は text-main／bg-surface、マスクは text-subtle／bg-surface、出所は success／success-bg、説明は muted／bg-surface、エラーは danger／danger-bg を使います。プロバイダーの淡い背景のマスクは text-subtle／bg-subtle に変えました。角丸は control／card トークンを使い、外部リソースは読み込みません。390px では名前と変数名を 1 行目、状態／マスク／操作を 2 行目とし、名前は途中で改行せず、変数名は折り返し可能で、横方向にはみ出しません。組み合わせは check_ui_contrast に含めます。

## ワークスペースの内容（creds）

`.general-settings` の上部には現在のブランドの label／select を残します。その下に 5 つのネイティブの `details.workspace-group.section-card` を置き、順に「ブランドテンプレート」「アイデア出し」「データ」「通知」「システム」です（uiorder で順序を調整）。summary はカードのタイトル行で、内容は同じカードの `.workspace-group-content` にあり、section-card を入れ子にしてはいけません。data-group は ideation／data／notifications／system／brand で、デフォルトではすべて折りたたまれ、展開は排他的ではなく、再読み込みすると折りたたまれた状態に戻ります。

アイデア出しには定例会議とテーマ、データには CSV、DM の補完取得、エクスポート、通知には通知ポリシー、システムには PC 起動時の自動起動と受信の健全性、ブランドテンプレートにはワークスペース名、テンプレートのプレビュー／適用、NG ワードを含みます。展開／折りたたみでは入力を保持し、ブランドとロールの権限は変わりません。古い単一の詳細設定や勤務時間の欄はありません。要約は text-main／bg-surface、card の角丸と共通のパディングを使い、カードの幅を揃えます。

check_all_features では、全 16 欄の保存、マスク、再読み込み、409、削除と、4 組の接続の成功／失敗の代替実装を操作し、viewer ではプラットフォームが読み取り専用であることを検証します。check_ai_resilience_frontend では 3 つのサブタブ（ローカル CLI なし）、未保存のデータ、古い URL とキーボード、古い CLI の使用量の行、デフォルトの AI を検証します。check_view_refresh ではメインの 4 タブ、check_workspace では 5 つのグループがデフォルトで折りたたまれ、それぞれ独立して開くことを検証します。check_ui_scale では各コントロールの元の寸法／文字／スクロールの検証を維持します。

## 手動 AI とデフォルトの AI（ai-unify-2。ローカル CLI は nocli で削除済み）

- アイデア出しの `.policy-grid` の実行方法はネイティブの select を使い、optgroup では分けません：設定済みの API プロバイダー（使用できない項目は無効にして「（未設定）」と表示）、最後に「Agent に作成を任せる」です。デフォルトの優先順は、使用可能な `ideation-choice:<brandId>` のブラウザーの記憶、ブランドのデフォルトの AI、最初の使用可能な API、Agent に作成を任せるの順です。CLI の記憶とデフォルト値は常に無視します。「Agent に作成を任せる」を選ぶと、レポートは「Agent によるテーマ作成待ち」で止まり、`.agent-awaiting` で、Claude Code では /mwb:ideas を使うか、他の Agent では get_guide("ideas") を使って引き継ぐよう説明します。データの読み込み前はメニューを無効にし、ブランドの切り替え時に古い値を引き継がないようにします。説明行は追加しません。

text-main／bg-surface、placeholder の text-muted／bg-surface、danger／danger-bg、primary、control／card の角丸トークンを踏襲します。390px で欄がはみ出しません。補足説明は以降の分類にだけ影響し、過去分を自動で再計算しません。

## サイト全体のページの枠組み

4 つのメインページは PageHeader を使い、設定の 3 つのタブは 1 つのページヘッダーを共有します：デスクトップではタイトルが左、ページの操作が右で、モバイルでは行を変えてもかまいません。デスクトップのサイドバーは 220px、コンテンツの開始位置は 252px です。外枠、左右の padding、ページヘッダーは ui-shell.css で共有します。アイデア出しも同じ枠組みを使い、外枠の寸法を別に定めません。

モバイルでは上部 56px、ページヘッダー 152px、下部に --ui-mobile-nav-space（64px にセーフエリアを加えたもの）を確保します。コンテンツは固定ナビゲーションの上までスクロールでき、受信の健全性の警告が出ているときも同じです。モバイルの設定ページではブランドの選択とログアウトを残し、デスクトップに切り替えるとサイドバーのコントロールを使い、選択中のブランドは変わりません。

ページの操作は primary、副次的な操作は quiet で、フォームと状態はシステムフォントと色のトークンを踏襲します。表の数値は右寄せ、等幅数字です。空のデータや不明な値で 0 を捏造しません。コントロールは共通の高さ、文字サイズ、角丸を使います。390px で横方向にはみ出してはならず、実際の文字をトリミングで隠してはいけません。

## 受信の健全性のバナーと文字の完全性

`--ui-health-banner-height`（72px）は、サイト全体の赤い受信の警告を定義し、ページの枠組みの上に置きます。ワークスペースの使用可能な高さからこの値を差し引き、モバイルの会話でもバナーが見える状態を保ちます。文字サイズは body、パディングは content-padding／shell-gap を踏襲します。返信の状態は flex で文字の行の高さより小さく縮めてはいけません。名前と要約は折り返し可能です。

`check_ui_scale.py` は現在 `.runtime/dm-only/` に出力します：既存の寸法のアサーションに加え、文字自体の scrollWidth と、overflow:hidden／clip の祖先によるトリミング（省略記号を含む）も確認します。意図的に clip で隠したアクセシビリティ用の表ヘッダーは表示される文字に含めず、縦スクロールのコンテナはスクロールして読むことを許容します。検出器は別途、横方向の省略記号、縦方向の hidden の 2 つの否定ケースで失敗することを検証します。3 種類のサイズで、マーケティングの 6 ページ、台本、エクスポート、投稿のコメント、サイト全体の異常バナーを 1 つずつスクリーンショットします。


## チェックボックスとラジオボタン

checkbox／radio を持つ label は、共通の横並び、左揃えを使います。コントロールの幅と高さは `--ui-choice-size`、ラベルの文字サイズは body、行の高さは `--ui-choice-line` を参照します。文字との間隔は brand-gap を参照します。長いラベルはモバイルで折り返し可能で、コントロールは 1 行目の文字に揃えます。

`check_ui_scale.py` は表示されているすべての（スクロール可能な領域を含む）checkbox／radio を 1 つずつ計測し、`input.labels` でラベルを見つけ、DOM Range で 1 行目の表示される文字を計測します。垂直方向の中心の差は 6px 以下で、コントロールの右端が文字の左端を超えないことを求めます。表示される文字のラベルが存在しない場合も失敗とみなします。さらに checkbox／radio それぞれについて、縦方向のずれ、左右の逆転、正しい横並びを検証し、検出器のケースは計 6 件です。最終のスクリーンショットとレポートは `.runtime/polish/` を参照してください。

## サイト全体のブロックのパディング（2026-09-27）

水平方向のパディングは `style.css :root` に、モバイルでの上書きは `ui-shell.css :root` に集約し、実際の適用は `ui-padding.css` で一元管理します。6 ページで以下の規則を共有し、ページごとに別の値を定めません。

`check_ui_scale.py` は `scripts/ui_padding.js` を読み込み、1440×900、1609×914、390×844 で、7 ページと開いたダイアログ、情報欄、投稿、コメント、ツールバー、下部のコンテンツを計測します。DOM Range で表示される文字の各行を確認し、文字自体から上にさかのぼって、不透明な背景色、背景画像、または表示される枠線を持つ最も近いコンテナを探します。デスクトップでは最低 20px、モバイルでは最低 14px、新たに分類した小さなデータのセルは最低 12px です。元のパネル／一覧のしきい値は変わりません。操作ボタン、chips／バッジ、フォームのコントロール（検索アイコンを含む）の内部は除外しますが、コンテンツ型のボタンは除外しません。フォント、React の画面、有限のアニメーションの完了を待ってから計測とスクリーンショットを行います。

> 削除済みの過去の仕様：
> 別途、パネル／一覧の左右の padding が共通値（±1px）と等しいこと、7 ページにわたる同種のコンテナの差が 2px 以下であることを 1 つずつ確認していました。既存の文字サイズ、高さ、横方向のはみ出し、文字のトリミング、チェックボックス、ページヘッダー、サイドバー、3 列、返信エリアの比率のアサーションは元の期待値を維持します。新しい SVG の文字はグラフの viewport でトリミングされてはならず、パディングの検出器の正負のケースが 18 件あります。

最新の出力はデフォルトで `.runtime/padding/after/` で、`UI_SCALE_ARTIFACT_DIR` でディレクトリを指定できます。`report.json` の `measurements[].padding.rows` は文字の距離、`containers` はブロックごとの左右のパディング、`padding_violations` は違反の一覧です。計測の出力はローカルの無視ディレクトリにだけ保存します。

数字の完全性は `scripts/ui_numbers.js` が DOM Range で文字の行数を計算します：数字、カンマ、小数点、パーセント記号、通貨記号だけを含む表示可能な文字は、スクロール可能な領域の内容も含めて、決して複数行になってはいけません。3 種類のサイズと 7 ページをすべて確認します。さらに IG の最新のビュー `1,234,567` の隔離データで実際のデータのセルとスナップショット表を通し、8 件の正例と反例で検出器を検証します。回帰の検収結果は `UI_SCALE_ARTIFACT_DIR=.runtime/padding-fix` に保存します。

## YouTube の読み取り連携（ytdata）

- プラットフォーム連携で Threads の後に YouTube を追加しました。チャンネル、連携状態、トークンの自動更新／失効の案内、有効期限を同じ行に並べます。クライアント ID／シークレットは認証情報の名前付きフォーム、マスク、保存を踏襲します。連携／再連携の primary は 1 つだけで、解除とテストは secondary です。未設定／内部 HTTPS 以外のときは連携を無効にします。ガイドはカード上の secondary の「設定ガイド」ボタンでサイト内のウィンドウを開く方式に変わり（guides を参照）、外部のタブはもう開かず、カードにはコールバック URL を表示しません。
- 投稿データの YouTube は FB／IG と同じ一覧と日付のフィルターです。ショートは既存の種類の文字ラベルを使い、それ以外は動画です。成果の 7 項目は順に、ビュー、いいね、コメント、シェア、平均視聴時間（秒）、総再生時間（時間）、新規登録者で、後ろの 4 項目の横に「1～2 日遅れで反映」と付けます。スナップショット表は取得日時／ビュー／いいね／コメントで、グラフのデフォルトはビューです。不明は —、0 と分かっている場合は 0 です。
- 登録者のツールバーは年／月／週と今週／今月の増減を踏襲し、名前を登録者数に変えます。チャンネルが非表示の場合は — を表示し、説明ボタンで理由を案内します。未連携の場合は登録者数の記録を開始するよう案内します。コメントは取得／すべて再取得／停止と日付のウィンドウを踏襲し、識別子と伏せた本文を表示します。アイデア出しでは YouTube の投稿がある場合だけそのタブを表示し、要約に加えます。
- 色／フォント／角丸はすべて P1-1 と共通トークンを踏襲します。遅延の説明は text-subtle／bg-surface、ガイドのウィンドウは guides を参照、ショートのチップは text-subtle／bg-subtle で、check_ui_contrast に含め済みです。check_youtube_data で 4 種類の連携状態、一覧、成果、コメント、登録者、1440／768／390 ではみ出さないことを検証します。スクリーンショットは変更後の 1440×900 と 390×844 だけを撮ります。

## YouTube への投稿（ytpublish）

- 投稿ページの YouTube タブ（`#composer-panel-youtube`）は、連携済みでアップロード権限があり、共通の形式が動画のときに有効になります。上部の行はチャンネル名と「オフ」のチップで、順にタイトル欄（`aria-label=YouTube 標題`、横に N／100 文字の注記。空のときはグレーの placeholder でデフォルトのタイトル＝説明の 1 行目を表示）、説明欄（`aria-label=YouTube 說明`、横に N／5,000 バイトの注記。「共通キャプションに戻す」と Markdown の案内を踏襲）、`公開狀態` のセグメントコントロール（公開／限定公開／非公開、デフォルトは公開）、子ども向けのチェックボックス「子ども向けに制作されたコンテンツです」（デフォルトはオフ）、`.publish-thumbnail` のサムネイル行です。カテゴリは設定ページにだけあり、投稿ページには表示しません。
- `.publish-thumbnail` には、「カスタムサムネイル」、幅 96px・16:9 のサムネイルのプレビュー、ファイル名とサイズ（サムネイルがまだないときは text-subtle の小さな文字で「JPG／PNG · 2 MB 以内 · 未アップロードの場合は自動サムネイルを使用」）、secondary「サムネイルをアップロード／サムネイルを変更」と primary danger「サムネイルを削除」を同じ行に並べ、モバイルでは自動で折り返して横方向にはみ出しません。サムネイルは共通のメディア一覧には入れません。
- 共通の形式が画像／カルーセル／テキストのみの場合、YouTube のスイッチを無効にし（title「YouTube は動画のみ対応しています」）、選択済みのプラットフォームから外します。タブには `.notice.warning`「YouTube は動画のみ対応しています」だけを表示し、タブのラベルに赤い点は付けません。縦長または正方形で 3 分以内の場合は `.notice.warning`「ショートとして分類されます…」を表示します。サムネイル行は「ショートはカスタムサムネイルに対応していません」に変わってアップロードを無効にし、サムネイルがすでにある場合は赤字で削除を求めて投稿を止めます。プレビューは 9:16 に変わり、サムネイルは適用しません。タイトルが 100 文字を超える場合、説明が 5,000 バイトを超える場合は赤字で投稿を止め、タブのラベルに赤い点を付けます。
- 既存の連携でアップロード権限が不足している場合：YouTube のスイッチはグレーで、タブには「アップロード権限を得るには連携し直してください」と secondary「設定 → プラットフォーム連携」を表示します（未連携の場合は引き続き「未連携」）。設定ページの YouTube カードでは `.notice.warning.oauth-permissions`「アップロード権限を得るには連携し直してください」で案内し、状態のチップは「連携済み」のまま、「再連携」は secondary に変わり、その他の読み取り機能には影響しません。連携済みのときは別途「アップロードカテゴリ」のドロップダウンがあります（デフォルトは「人物與網誌」（People & Blogs）で、選ぶとすぐに保存して「アップロードカテゴリを保存しました」と案内します）。
- YouTube のプレビュー `.publish-preview-post` は順に、動画（通常は 16:9、ショートは 9:16、サムネイルをカバーの poster として使用）、太字の `.publish-preview-title` のタイトル、`.publish-preview-identity` のチャンネル名、`.publish-preview-actions.is-youtube` のインタラクション行（高評価／共有／保存。見た目だけ描画）、`.publish-preview-caption` の説明（bg-subtle の角丸の枠で、引き続き折りたため、ハッシュタグは link-color で表示）です。
- 確認ダイアログの YouTube 項目は「動画 · 公開設定 · 子ども向け／子ども向けではない · カスタムサムネイル／自動サムネイル（· ショート）」と「タイトル：…」です。
- 投稿履歴：YouTube の結果のリンクは「動画を表示」です。サムネイルが失敗した場合は、同じ行に `.status-badge.pending`「サムネイル未適用」、安全な中国語の理由と secondary「サムネイルを再適用」を表示します（閲覧者には表示せず、投稿のマスタースイッチがオンである必要があり、先に ConfirmDialog「差し替えるのはサムネイルのみで、動画は再アップロードされません」を経ます）。動画は引き続き成功です。YouTube が報告した実際の公開設定が選択と異なる場合（たとえば非公開に制限された場合）は `.status-badge.pending`「YouTube での実際の公開設定：非公開」を付けます。
- 色、フォント、角丸はすべて P1-1 のトークンを踏襲し、ハードコードした色は追加していません。新しい文字／背景色の組み合わせは check_ui_contrast に含め済みです。check_publish で YouTube タブの欄と上限、サムネイル、ショート、動画以外での無効化、プレビューの順序／太字／比率／カバー、権限不足時の誘導、確認ダイアログ、履歴のサムネイル失敗／再適用を検証し、check_youtube_data で連携カードのアップロード権限の案内とカテゴリの保存を検証します。いずれも 1440／768／390 で横方向にはみ出さないことを含みます。スクリーンショットは変更後の 1440×900 と 390×844 だけを撮ります。

## UI の配置の調整（uiorder）

配置だけを変え、機能と文言は変えません。前述の関連する記述より優先します。

- 投稿（新規投稿とストーリーズは同じ規則）：`.publish-footer` で、「今すぐ投稿／予約投稿」の切り替え（予約投稿のときは日時の欄を含む。`.publish-schedule`）と、右側の `.publish-submit`（`.publish-actions` のボタン行とその下の `#publish-disabled-reason`）を同じ下部の操作行に置きます。デスクトップでは同じ行で、日時の設定は左寄せ、ボタンは右寄せ、無効の理由はボタンの下に右揃えで置きます。390px では 2 行に分けますが同じ操作行の中にとどめ、理由は左揃えです。「新規投稿／新規ストーリーズ」ボタンは `.publish-editor-heading` の右側、プラットフォームタブの上に置きます。
- アイデア出し：コメント範囲の順序は直近 7、30、60、90 日、カスタム日付です（デフォルトは引き続き 30 日）。390px ではセグメントボタンを折り返し、横方向にはみ出さず、トリミングもしません。ステップ 3 のボタンの順序は、secondary「選択したコメントを再ラベル付け」が左、primary「今すぐアイデア出し」が一番右です。ページヘッダーにはラベルのない数字をもう表示せず、「テーマ一覧」のタイトルは「テーマ一覧（N）」と表示します。
- 投稿データ：コメント同期エリア `.comment-sync`（状態、「コメントを取得」「すべて再取得」「停止」）は「コメントと返信」カードの中、コメントの日付フィルターと範囲の総数の後に置きます。右側の「投稿の成果」には成果の数値、グラフ、スナップショットだけを残します。FB／IG／Threads／YouTube で共通です。「コメントと返信」のタイトルの下の 1 行の `.comment-retention.muted` は、`/api/posts/platforms` の設定に基づいて視聴者のコメントの保存期間を説明します（FB／IG／Threads は取得から N 日。YouTube は 30 日以内に再取得しなければ削除。TikTok はコメントを読まない）。毎日の削除が有効でない場合も同じ文で説明します。これはプラットフォームの規約で求められる開示で、このカードで唯一の説明行です。設定が読み取れない場合は表示しません。

### ブランドメニューの統合と文言（uiorder 第 2 弾）

- ブランドはサイドバー（モバイルでは `.mobile-brand-picker`）でだけ選択します。AI の「ブランドを適用」、メッセージ分類の「ブランドを適用」、アイデア出しのステップ 1 の「ブランド」、投稿の「ブランド」、ワークスペースの「現在のブランド」はすべて削除し、各ページは App から渡される brand を使います。バックエンドに送る brand_id パラメーターは変わりません。
- ユーザーに見えるブランドが 1 つだけの場合、サイドバーとモバイルのどちらにもブランドメニューを表示せず、App の有効なブランドにはそのブランドを直接使います（URL には引き続き brand_id を付けます）。ブランドが 2 つ以上の場合は従来どおり「表示できるすべてのブランド」を含みます。ダッシュボードと投稿データでは「すべて」を使えます。アイデア出し、投稿、設定の AI、メッセージ分類では、代わりに `.need-brand`「まず左側でブランドを選択してください」（モバイルでは「まず上部でブランドを選択してください」。CSS で 600px を境に切り替え）を表示し、編集内容は表示しません。ワークスペースでは「すべて」のとき、ブランドに関係しないデータとシステムのグループだけを残します。URL の brand_id は従来どおり有効です。
- 文言：サイト全体で「ワークベンチ」とします。サイドバーから「品牌工作區」（ブランドワークスペース）のラベルと下部のキャッチコピーを取り除き、「ブランド運用ワークベンチ」だけを残します。ページヘッダーの右上でワークスペース名を重複して表示しません。タイトルは「ダッシュボード」「投稿データ」です。投稿のタイトル行から「已開啟／未開啟」（オン／オフ）のチップを取り除きます（上部の通知、スイッチのボタン、ボタンの下の理由は残します）。メンバー行は「Agent 接続 N 件」「Agent 接続をすべて取り消す」です。Webhook の欄のラベルは「公開 URL」「Meta コメント通知 URL」「LINE 通知 URL」です。認証情報の欄の .env の名前は小さな text-subtle の等幅文字に変えます。
- 設定タブの順序は、プラットフォーム連携、AI、メッセージ分類、ワークスペース、メンバー、マイアカウントです。デフォルトのタブはプラットフォーム連携です（URL で settings_tab を指定した場合は従来どおり）。投稿データのフォロワー数の行に小見出し「フォロワー数の期間」（YouTube では「登録者数の期間」）を付けます。アイデア出しのレポートの状態が完了でも、エクスポートファイルが存在しないかすべて生成されていない場合は、タイトルに「完了・エクスポート未完了」を表示します。
- check_brand_scope で、単一ブランドではメニューがないこと、複数ブランドでの「すべて」の案内と選択後の内容、文言の新しい値、タブの順序とデフォルトのタブを検証します。複数ブランドはブラウザー側の代替実装 /api/brands で 2 つ目のブランドを加え、データベースには書き込みません。

## 投稿データの成果の中央配置と投稿全文（postcenter）

前述の metricwidth、YouTube の「成果の 7 項目」、本文の「全文を表示／折りたたむ」の記述より優先します。

- デスクトップ（≥1280px）は 3 列です：左は投稿一覧 280px、中央は `.post-metrics`「投稿の成果」で自動幅（最も広い）、右は 360px の `.post-conversation`（投稿の要約カード＋コメントと返信）です。成果の数値のセルは幅に応じて自動で並べます（各セル最低 120px）。
- 600～1279px はモバイルと同じく 1 列です：投稿の要約、投稿の成果、コメントと返信の順に並べます。
- 投稿の要約カード：72px のサムネイル（トリミングして全体を埋める）を左に置き、右側にアカウント・種類、2 行の本文（`p.post-caption.collapsed`。本文はタイトルではないため h2 は使いません）、日時を置きます。その下の 1 行に secondary の「投稿全文」と「元の投稿を開く ↗」を置きます。「全文を表示／折りたたむ」はもうありません。
- 「投稿全文」は `.guide-dialog.post-full-dialog` のウィンドウを開きます（設定ガイドのウィンドウの外枠、フォーカスの出入り、Tab の循環、Esc と「閉じる」を踏襲）：アカウント・種類、元の比率の画像、全文（改行を保持）、投稿日時、元の投稿へのリンクです。モバイルでは全画面です。
- 「視聴パフォーマンス」エリア（`.watch-metrics`、h4）は成果の数値グリッドの後に置き、動画の投稿にだけ表示します（FB／IG の動画とリール、YouTube すべて、TikTok すべて、Threads の動画）：FB は「平均視聴時間（秒）」と「総再生時間（時間）」、IG はさらに「最初の 3 秒のスキップ率（%）」を加えます。YouTube は平均視聴時間、「平均視聴率（%）」、総再生時間で、3 項目とも「1～2 日遅れで反映」と表示します。FB に維持率の曲線があるときは `.retention-chart` の「視聴者維持率」と「中盤まで視聴／最後まで視聴」も表示します。TikTok と Threads は、公式 API にこれらのデータがないことを 1 行で説明するだけです。曲線のカードはすべて外枠（`.metric-chart`）とタブ（`.tabs.chart-tabs`、role=tablist「グラフの指標」。ラベルが多いときは折り返し、横スクロールしない）で指標を切り替え、ドロップダウンは使いません：「データの推移」にはエンゲージメント指標を、動画の投稿ではさらに「視聴の推移」カードに視聴パフォーマンスの 3 項目を置きます。FB の「視聴者維持率」も同じ外枠のカードです。2026-10-24 から「データスナップショット」の表を削除しました：同じスナップショットのうち 3 項目を並べていただけで、「データの推移」の曲線がすべての指標をカバーしている（点にマウスを重ねると正確な数値が見える）ため、曲線だけを残します。スナップショットが 100 件に達したら、曲線の下に「直近 100 件のスナップショットを表示しています。」と表示します。YouTube の上部にある成果の数値グリッドは、ビュー、いいね、コメント、シェア、新規チャンネル登録者の 5 項目に変えました。
