# 平台政策與 API 限制

> **語言 / Language / 语言 / 言語**：繁體中文 | [简体中文](../cn/平台政策与API限制.md) | [English](../en/platform-policies.md) | [日本語](../jp/プラットフォームポリシー.md)

整理工作檯會碰到的平台條款與 API 規格，免得每次重查。每條都標出處與查證日期；**「推論」**是我們依條文做的判斷，**「未查證」**是還沒在官方文件找到依據的說法。條款會改版，發現與官方不符時以官方為準，並更新這份文件與查證日期。

查證日期：2026-10-15～2026-10-17（應用程式模式、Google OAuth、TikTok Sandbox 於 2026-10-17 補查；FB 粉專 Webhook 與各平台受眾資料於 2026-10-19 補查）。

> 這份文件只記規定與工作檯的對應做法，不是法律意見。開源後每位自架者都是自己應用程式的開發者，義務在他們身上（README 待補，見開源規劃）。

## 共通原則

- 只用官方 API 與官方金鑰；不爬網頁、不模擬登入。
- 對外文字（App 名稱、說明、官網）據實描述用途與功能，不包裝成不是事實的用途去送審。
- 隱私權政策與服務條款：放在自架者自己的網站（範本見 `docs/zh-tw/templates/`，須知見 `docs/zh-tw/合規須知.md`），各平台後台填這組網址，資料刪除說明可指向隱私權政策的 `#delete` 段落。
- 觀眾留言保存期限：自工作檯**取得**起 365 天（`COMMENT_RETENTION_DAYS`），不是自留言發布起算。這是工作檯自訂的規則（Meta 沒有規定天數），隱私權政策寫同樣的期限。實作見 `docs/zh-tw/部署與維運.md` 的資料保留段落。

### Meta 應用程式模式與存取等級（2026-10-17 查證）

出處：[應用程式模式](https://developers.facebook.com/docs/development/build-and-test/app-modes)、[存取等級](https://developers.facebook.com/docs/graph-api/overview/access-levels)、[Instagram Webhooks](https://developers.facebook.com/docs/instagram-platform/webhooks)、[Threads 入門](https://developers.facebook.com/docs/threads/get-started)。

- **一般存取權限（Standard Access）**：所有商家應用程式自動取得，不需 App Review；只能向「在應用程式上有角色」的使用者（管理員、開發者、測試人員）要求。只給自己用的工具，這樣就足夠。
- **進階存取權限（Advanced Access）**：要服務沒有角色的使用者才需要，必須逐項通過 App Review，並完成商家驗證。
- **開發模式**：只能向有角色的使用者要求權限；文件沒寫期限，但也沒明講可以長期這樣用。
- **Instagram 留言 Webhook**：應用程式必須是 **Live** 模式，`comments` 需要 **Advanced Access**，帳號必須公開。只用一般存取權限時收不到 IG 留言 Webhook，要靠定期 API 讀取。FB 粉專留言 Webhook：開發模式只送後台測試事件與有應用程式角色者自己觸發的事件，其他人的留言要應用程式上線才會送；另外粉專必須用粉專存取權杖呼叫 `POST /{page-id}/subscribed_apps?subscribed_fields=feed` 安裝應用程式（需 `pages_manage_metadata`），只在後台訂閱欄位不夠。工作檯目前沒有做這個呼叫（2026-10-19 查證：[Webhooks](https://developers.facebook.com/docs/graph-api/webhooks)、[Webhooks for Pages](https://developers.facebook.com/documentation/pages-api/webhooks-for-pages)）。
- **Threads**：有角色的測試人員可隨時授權，不需 App Review；服務沒有角色的使用者時，每個權限都要審核並發佈應用程式。

### Meta API 規格（發佈相關）

- **IG Reels 封面**（[IG User Media](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/media)）：`cover_url` 只限 Reels，公開網址、JPEG、8 MB 內、sRGB；建議 9:16，否則裁切中間，分享到動態時裁成 1:1。同時給 `cover_url` 與 `thumb_offset` 時用 `cover_url`。限動與輪播子項目不支援 `cover_url`。工作檯 0048 已實作（PNG 轉 JPEG 送出）。
- **FB 一般影片封面**（[Page Videos](https://developers.facebook.com/docs/graph-api/reference/page/videos/)）：上傳時的 `thumb` 參數（圖片原始資料）；文件沒寫格式與大小限制。
- **FB Reels 封面**（[Reels Publishing](https://developers.facebook.com/docs/video-api/guides/reels-publishing)）：Reels 發佈三步驟（start／upload／finish）都沒有封面參數；文件最後指向 [Video Thumbnails](https://developers.facebook.com/docs/graph-api/reference/video/thumbnails) 來「為 Reels 加自訂封面」。
- **Video Thumbnails**：`POST /{video-id}/thumbnails`，`source`（圖片檔）＋ `is_preferred=true`；最大 10 MB，建議與影片同比例；只能用在已關聯粉專的影片。需要 Page 權杖與 `pages_read_user_content`、`pages_manage_engagement`、`pages_show_list`。文件沒有明講適用 Reels，只是 Reels 文件指向它 → 實測確認。工作檯 0049 對一般影片與 Reels 都用這支（不用 `thumb` 參數），在貼文成功後才套用；`pages_manage_engagement` 是選用權限，Meta 後台開啟後還要重新連結才會出現在權杖裡（2026-10-17 確認正式權杖缺少）。
- Graph API 版本：`v26.0`（`oauth.FB`）。

## YouTube／Google

出處：[YouTube API 服務開發人員政策](https://developers.google.com/youtube/terms/developer-policies)、[Google API 服務使用者資料政策](https://developers.google.com/terms/api-services-user-data-policy)、[YouTube 服務條款](https://www.youtube.com/t/terms)。

| 規定 | 內容 | 工作檯的做法 |
|---|---|---|
| 30 天規則（III.E.4） | 統計數字（觀看、按讚）可長期保存，但每 30 天要確認授權與影片仍在；其他資料（標題、縮圖、留言）最多 30 天，到期刪除或重新抓取。 | 每小時同步更新影片；YouTube 留言 30 天沒重抓就刪；YouTube 上已刪除的影片資料 30 天後刪。 |
| 撤銷授權 | 撤銷後 7 天內刪除透過該授權取得的資料；要提供刪除已存資料的方式，7 天內完成。 | 「中斷連結」撤銷授權並立即刪除 YouTube 影片、快照、縮圖、留言與報告引用（不會刪 YouTube 上的影片）。 |
| 隱私權政策 | 說明使用 YouTube API 服務，附 [Google 隱私權政策](https://policies.google.com/privacy) 與撤銷授權頁 `https://security.google.com/settings/security/permissions`。 | 隱私權政策範本已包含。 |
| 服務條款 | 附 YouTube 服務條款連結，並寫明使用者同意受其約束。 | 服務條款範本已包含。 |
| 範圍最小化 | 只申請需要的範圍。 | `youtube.readonly`、`yt-analytics.readonly`、`youtube.upload`；不要求 `youtube`／`force-ssl`。 |

OAuth 發佈狀態（2026-10-17 查證，[OAuth 2.0](https://developers.google.com/identity/protocols/oauth2)、[何時不需要驗證](https://support.google.com/cloud/answer/13464323)）：
- 同意畫面是「外部」且發佈狀態為 **Testing（測試）** 時，refresh token **7 天後失效**（只要求名稱、email、個人資料的例外），等於每週要重新連結一次。
- **個人使用（100 人以下）不需驗證**：發佈狀態改成「正式版（In production）」後，使用者登入時可以點過「未經驗證的應用程式」警告畫面；超過 100 人才必須驗證。未驗證時仍須遵守 API 使用者資料政策。
- 未驗證的 API 專案上傳的影片**不會**被限制成私人（`videos.insert` 文件原文，2026-10-17）；工作檯實際上傳過一支「不公開」影片，實際狀態也是不公開。

API 規格：`videos.insert` 用 resumable upload；縮圖 `thumbnails.set` 收 JPEG／PNG、2 MB 內；Shorts 自訂縮圖 API 未列支援（工作檯停用）。配額：`videos.insert` 另有每日上傳額度，其餘讀取共用 `youtube.quota`（見 `docs/zh-tw/部署與維運.md`）。

### 審核與發佈限制

- **Sandbox**（[文件](https://developers.tiktok.com/doc/add-a-sandbox)）：「不用送審就能試用整合的受限環境」，最多 5 個、每個最多 10 個目標帳號，文件沒寫到期日；**沒有說能不能長期當正式用途**，定位是測試。Sandbox 不開放公開影片的 Content Posting API。工作檯目前靠 Sandbox 運作，屬於灰色地帶（推論：最壞情況是應用程式被限制，不是 TikTok 帳號被封，因為影片是你自己在 App 內發佈）。
- **未審核（Sandbox）**：Direct Post 只能 `SELF_ONLY`，發文帳號必須是私人帳號，24 小時內最多 5 個使用者發文。收件匣上傳（`video.upload`）可用，由使用者在 App 內完成發佈。
- **App 審核準則的通則**（2026-10-17 查）：「Apps must not be for private or personal use」、「Apps that are still in development or testing will not be approved」、只申請需要的權限且每個產品與權限都要在示範影片中呈現；示範影片要用 Sandbox 錄完整流程，網域要與填寫的網站一致。準則本身沒有 Content Posting API 的用途清單（清單在內容分享規範）。**推論**：只給自己或自家客戶帳號用的工作檯，屬於「私人用途」，送審（不論是否申請 Direct Post）很可能被拒。
- **Direct Post 審核**：用途要「協助真實創作者發佈原創內容」並面向廣泛使用者。明列**不接受**：「幫你或團隊管理的帳號上傳內容的工具」、只供測試、搬運其他平台內容。審核表單填使用量估計，決定每 24 小時的創作者上限。**推論**：工作檯目前的定位（管理自己帳號）過不了，只有變成真正給多位創作者使用的產品才能照實送審。
- **Direct Post 介面要求**（審核才需要）：每次讀 creator_info 並顯示暱稱、依 `max_video_post_duration_sec` 檢查長度、隱私下拉無預設值、留言／合拍／拼接預設不勾、音樂使用聲明、商業內容揭露、預覽、提示處理需數分鐘並追蹤狀態。示範影片與 2–6 週審核期只見於第三方文章，**未查證**。
- **收件匣上傳**：init 端點沒有文案欄位（文案只能在 App 內貼）、也沒有封面欄位（封面在 App 內選；`video_cover_timestamp_ms` 只屬 Direct Post）。24 小時內最多 5 支待處理（`spam_risk_too_many_pending_share`），每帳號每天約 15 篇。
- **收件匣能不能帶文案**（2026-10-17 再查）：影片收件匣 init 的 body 只有 `source_info`（`source`、`video_size`、`chunk_size`、`total_chunk_count` 或 `video_url`），沒有 `post_info`／`title`／`description`；`video.upload` 範圍的說明也是「以草稿送到創作者帳號，再到 TikTok 編輯發佈」。能帶文字的只有：Direct Post（`post_info.title`，需 `video.publish`＋審核）、相片貼文（`/v2/post/publish/content/init/` 的 `post_info.title`／`description`，但相片要從已驗證網域拉取）、Share Kit（原生 iOS／Android SDK，文件只提到 partner hashtag，沒有文案欄位，網頁工具用不到）。實測：2026-10-17 未審核的 Sandbox 應用程式已成功把影片送到收件匣。
- **影片規格**：API 上傳最長 10 分鐘；64 MB 內可一段送完，否則分段（工作檯用 10 MB）。依帳號查上限的 `creator_info` 需要 `video.publish`，工作檯沒有申請。
- **相片貼文**：只能從已驗證網域的公開網址下載 → 工作檯不支援，提示「僅支援影片發布，圖文需從APP上傳」。
- **權杖**：access token 24 小時；refresh token 365 天，每次換發會輪替。
- **資料**：Display API 影片清單只回公開影片（含觀看等計數）；粉絲數從 user/info。私人影片不在清單，所以「已刪除或改為私人」一起處理。
- **封面**（[Query Videos](https://developers.tiktok.com/docs/en/tiktok-api-v2-video-query)，2026-10-19 查）：`POST /v2/video/query/` 需 `video.list`，一次最多 20 個影片 ID，只回授權帳號自己的影片，文件說可用來「更新封面網址的有效期限」（沒寫多久）。工作檯縮圖快取用它取 `cover_image_url` 後立即縮成 JPEG 存檔。CDN 網域文件沒寫，工作檯先允許 `tiktokcdn.com`／`tiktokcdn-us.com`／`tiktokcdn-eu.com`，**未實測**。
- **留言**：只有 TikTok API for Business 能讀，申請者須為公司並用公司網域 email，不收個人開發者 → 工作檯不讀 TikTok 留言。

| Threads | `follower_demographics`（國家、城市、年齡、性別，一次一種） | `threads_manage_insights`；追蹤者 ≥100 人；不支援 since／until。沒有上線時段指標 | 每天抓一次 |

| LINE | Messaging API 有官方帳號好友的人口統計（`/v2/bot/insight/demographic`） | 需要連品牌官方帳號；工作檯的 LINE 只用於通知（`AGENTS.md`） | 不做，介面說明原因 |
