# Architecture / current architecture

> **Language / 語言 / 语言 / 言語**: [繁體中文](../zh-tw/架構.md) | [简体中文](../cn/架构.md) | English | [日本語](../jp/アーキテクチャ.md)

Marketing Workbench provides a multi-brand internal marketing workspace. Brands, accounts, content and prompts are isolated from each other; back-office users have admin / marketing / viewer permissions.

## Agent entry point

The internal `/mcp` uses the MCP SDK's Streamable HTTP on the same port as the FastAPI web service; the public boundary still only lets through the existing Webhook / media paths. Agents sign in with the member's own OAuth authorization or a connection token; Bearer is used only for `/mcp`, while the web API keeps its session, CSRF and Origin checks. Every tool call re-reads the member's status, role and brand scope; following `docs/en/mcp-spec.md` (MCP spec), it provides queries plus saving back ideas and scripts for marketing / admin users, and the interface version is still 1.

`agent_tools` unifies tool descriptions, input validation, auditing and response size; `agent_queries` explicitly projects and masks content, and `agent_content` reuses the domain services. Agent reports have provider=agent, with the source stored in data_json.source (connection name and grant id). The existing comment worker, jev classification and aggregation finish and then stop at awaiting_ideas without calling a text AI; the existing ideation schedule marks reports that have waited more than 24 hours as failed. After the user settles on them in the conversation, the fifteen ideas are saved back and follow the ready / edit / export flow, keeping the Agent source. Each script save adds a new VideoScript and ScriptVersion; older drafts for the same idea are kept. No table changes and no new migration.

0037 adds tables for clients, grants, pending approval requests, authorization codes and tokens; secrets are stored only as hashes. Authorization codes are bound to the client / redirect URI / S256 PKCE; refresh tokens rotate on every use and reuse revokes the whole grant. Connections expire after 30 idle days and are revoked immediately on deactivation or password reset; last-used time is written at most once per minute, and the existing schedule cleans up expired data every hour. The old Hermes stdio MCP has been removed; Hermes now connects to `/mcp` with a viewer account (see `docs/en/mcp-spec.md`).

## noinbox scope

The inbox, reply drafts / checks / sending, price list, hand-off-to-human conditions, supervisor and routing assignment, pending-reply / deadline reminders and deal progress have been removed. The workbench only receives post comments. Comment Webhooks, the classification queue, urgent notifications for public comments, ideation, scripts and export remain; direct message data is deleted by the deployer with a separate purge script after a backup, with no new migration.

Classification still stores the Classification intent, raw response, signals, version and fingerprint; the new action is classified (skip for spam / no text), and no one is assigned anymore. Historical columns and tables are kept. The only schedules are classify, notify, comments, metrics and ideation. The banned-promise check for scripts is now shared through content_safety. Urgent notifications cover only complaints, high urgency and public reputation risk in public comments, with no link to a workbench conversation; the old general / deadline notifications are no longer sent.

## Technology and data

- FastAPI verifies signatures on the raw bytes; LINE inbound events that pass are always answered 200 and discarded, without storing or looking up a profile. Meta messaging events are discarded; feed comments / IG comments are ACKed only after they are persisted. LINE notify still receives group events with separate credentials.
- SQLite WAL is the only business source of truth; SQLAlchemy 2 handles data access and schema upgrades use Alembic. Events are upserted on a unique key of the platform's external ID, so redeliveries are not duplicated.
- The backend has built-in classification, notification, metrics and ideation schedules; the comment worker only continues one-off jobs created when the user clicked the button. Each persists its own lease, cursor, schedule switch and results, without depending on an external workflow engine.
- ngrok points to the backend loopback; the Traffic Policy and the backend block, in two layers, the public UI/API, path traversal and spoofed forwarding origins. The admin interface is only for local / Tailscale access.
- Public comments are read-only on the post page; the DM worker, backfill service and API have been removed. Historical DM tables / columns are kept for compatibility with the existing schema, and data deletion uses scripts/purge_direct_messages.py. Ideation source selection stays at this baseline, and existing reports are not deleted.

### Interface language

- Supports Traditional Chinese (default), Simplified Chinese, English and Japanese. `t('繁中原文', 變數)` in `frontend/src/i18n.ts` uses the Traditional Chinese source text as the key, and Traditional Chinese does not look anything up; other languages look up the translation tables in `frontend/src/locales/<語言>/` and fall back to Traditional Chinese when a translation is missing. Translation tables are loaded dynamically per language; `main.tsx` calls `initLanguage()` before loading pages, so module-level constants are also in the right language; switching language reloads the page. When the same source text needs different translations in different places, use `tx('情境', '原文')`; terminology follows `docs/en/i18n-glossary.md` (i18n glossary).
- The language preference is stored in `staff.language` (0051, nullable) and set with `PUT /api/auth/language`; every role can change its own. Before sign-in it is kept in localStorage.
- The backend still returns Traditional Chinese errors; `api.ts` looks up `detail` in the tables (`locales/*/backend.ts` contains the fixed messages). When you need to match a specific error, compare against the source text. Date and number formats follow the interface language; the time zone stays fixed at Asia/Taipei.

### SQLite transactions and locking

SQLAlchemy issues BEGIN uniformly, and the PRAGMAs from connection initialization run outside transactions; WAL, foreign keys and a five-second busy timeout are kept. Explicit `session.begin()` / `factory.begin()` from `session_factory()` are the write boundary and take the write lock with `BEGIN IMMEDIATE` before the first query; the autobegin transaction of a plain `factory()` uses `BEGIN` to keep a read snapshot without holding the write lock. Writes must not reuse a possibly stale read snapshot; ordinary requests first end a clean read transaction, then open a write transaction with `ensure_write()` and re-read / re-validate. This function refuses to discard uncommitted changes. New write paths must use these boundaries; nested transactions are still handled with SAVEPOINT.

If a WAL read snapshot is upgraded to a write after another connection has committed, SQLite returns `SQLITE_BUSY_SNAPSHOT` (517), which the busy timeout cannot resolve. Acquiring the write lock is attempted at most three times, each with the five-second timeout, waiting 0.05 / 0.15 seconds in between, for at most about 15.2 seconds (excluding OS scheduling). Only a BEGIN that has not yet executed any business SQL is retried; already-executed SQL, model calls or platform calls are never replayed, and background jobs do not get extra business retry rounds. When retries are exhausted it returns `503`, `Retry-After: 1` and a Chinese retryable message; other errors are handled by the existing rules.

External services, jev and models all run after the write transaction commits; results and usage records are written in separate short write transactions. Script / ideation content is first kept in the memory of the current run, so the limited retries to obtain the save lock do not generate content again. Permission, version, lease / claim and late-result checks still happen under the write lock. Read transactions must not be used as write transactions, and read-only GETs do not take the write lock for this.

If an asynchronous ideation report cannot even store its failed status, the process memory keeps at most 128 save-failure markers of "database location, report ID, the lease of that run", without keeping the exception or generated content. Queries keep the database's processing status, show a Chinese error and allow a manual retry; a new lease or a completed result does not apply an old marker. Restarting clears the markers, and retries resume under the database's existing 30-minute lease expiry rule. This is temporary operational state; SQLite remains the only business source of truth.

Sources: [SQLite isolation and BUSY_SNAPSHOT](https://www.sqlite.org/isolation.html), [SQLAlchemy SQLite transaction control](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#enabling-non-legacy-sqlite-transactional-modes-with-the-sqlite3-or-aiosqlite-driver). No new tables or migration; the Alembic connection setup lets SQLAlchemy manage BEGIN, and upgrade / downgrade verification must still pass.


## DM window and comment sync scope

DM messages are read newest to oldest; a page containing messages older than the date lower bound first imports the messages inside the window and then ends that conversation. Conversations requests keep `id,updated_time` and skip conversations older than the date lower bound; while response times keep running newest to oldest, discovery ends at the boundary, and when a time is missing or the order reverses it conservatively continues paging. Full history applies no date stop condition. Consecutive timeouts / 5xx on the same messages cursor are counted persistently in the progress and reset to zero after a page is read successfully; after reaching `META_DM_CURSOR_RETRY_LIMIT` (default 5) that conversation ends and counts as a partly incomplete conversation the platform did not answer, other conversations continue and the job can complete. The notice uses the existing waiting style.

Comments are only read by a one-off single-post read created with “Fetch comments” on the post detail page; admin / marketing can fetch and stop, viewers are read-only; brand permissions, CSRF and the `comments.request` / `comments.stop` audits are all enforced by the backend. The single state per post is deduplicated under the write lock. Without a manual job the schedule does not run the comment worker; the post list and performance metrics are still synced by the metrics worker. The old batch sync / backfill POSTs return 410 and no longer discover posts or queue. The old `META_COMMENTS_AUTO_DAYS` is ignored by settings parsing.

cwindow: a manual fetch sets `window_start` from the comment date filter; `window_end` is fixed to the earlier of the day after the chosen end date and the request time, as a half-open interval; only an explicit period=all makes the start null. Ideation also passes its own separate comment range, and the post publish period is still only used to select posts; old comment data is not deleted. IG uses `comments?fields=id,text,timestamp,from{id,username},replies.limit(50){id,text,timestamp,from{id,username}}`; FB uses `comments?filter=toplevel&order=reverse_chronological&fields=id,message,created_time,from{id,name},parent{id},comments.filter(stream).order(reverse_chronological).limit(50){id,message,created_time,from{id,name},parent{id}}`. Top level and nested each request at most 50 items. A missing nested edge means there are no visible replies, and it is not looked up again per comment; only when a nested `paging.next` exists is its `cursors.after` saved, to continue paging on that comment's replies / comments edge. The next URL returned by the platform is not used, to avoid carrying credentials or being sent to unofficial hosts; a missing, duplicate or overlong cursor is an error.

Top-level comments and replies each stop paging when a whole non-empty page is older than window_start; mixed pages continue, and a missing time is an error. Old parent comments on pages already read can still save in-range replies, but after top-level paging stops, replies to earlier parent comments are no longer explored. FB explicitly uses reverse_chronological; IG keeps the platform's native order, with no added ordering parameter that is not listed in the official SDK. On completion the manual queue entry is cleared at once and fetching does not continue. Each worker run is limited to 35 GETs / 50 seconds; when the budget runs out or the platform rate-limits, the fixed window, cursor, pages processed and items saved are kept, and the same job resumes under the hourly quota, usage headers, backoff and wait reasons. Recoverable temporary network failures are also kept for retry; errors that need a human, such as permissions, credentials or invalid responses, end this read, and the user clicks the button again after dealing with them.

Stopping first revokes the run_id / lease and clears the manual queue entry, keeping messages and saved progress. A GET already on the network cannot be recalled; after revocation its result cannot write comments and no further GET can be issued. Fetching again starts from a new fixed window and the first page, deduplicating on platform ID. Migration 0025 safely ends all old comment jobs and backfill discovery, clears old cursors and schedule ownership, keeps all business data and the last success time, and does not revive old jobs.

Display queries only the DB: the detail page defaults to the last 30 days and offers 7 / 30 / 90-day Taipei calendar filters; each page has 50 groups with their in-range replies, and “Show more” only reads the next batch. When a parent comment is out of range or not stored, replies with the same explicit parent ID are grouped together and marked as having an invisible parent; the parent text is not fabricated or fetched. The old API's all / custom date options are kept so existing reports can locate and query them, but the detail page does not offer them. Status polling only reads the DB and does not trigger Meta.

Official references: [Field Expansion](https://developers.facebook.com/docs/graph-api/guides/field-expansion/), [IG media comments](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-media/comments/), [IG comment replies](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-comment/replies/), [FB object comments](https://developers.facebook.com/docs/graph-api/reference/object/comments/). These reference pages returned 429 this time, so no successful read is claimed; fields / edges were cross-checked against [Meta's official IGComment SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/igcomment.py) and [Comment SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/comment.py), and three read-only IG GETs confirmed nested reads, omission of empty edges and independent paging. The production database copy has no FB posts; two more read-only FB GETs obtained one post, whose expanded query returned 200 with no comments, so FB reply paging is not claimed as tested live. FB replies are covered by the official SDK and HTTP mocks; the deployer must check the actual replies on a post with comments and the platform's availability.

## Follower tracking

`follower_snapshots` (0026) stores the account, UTC observation time and a non-negative integer follower count; a unique key on account / time prevents duplicates from redelivery. The table and daily recording flow are unchanged. `GET /api/posts/followers` requires `platform` and accepts `brand_id`, `account_id`, `year`, `month`, `week`; when year, month and week are omitted, it picks the year, month and week containing today in Taipei. It reuses the post sign-in and brand permissions; admin / marketing / viewer can all read, and the query only reads the local DB without triggering platforms or models.

It returns the platform connection status, the years that have snapshots (at least the current year), the week dates within the month, the current count, the change for the selected week / month and whether it is the current week / month; it also keeps per-account values to support filtering by a single account. The platform toolbar totals the visible accounts; if any account is missing data for the period, that total is null, to avoid treating unknown as zero. Snapshot input uses the shared platform type, so future platform fetchers can reuse the same table, write service, API and display without duplicating the calculation logic.

Weeks start on Monday and are split at Taipei month boundaries: in October 2026, week 1 is 10/1–10/4, week 2 is 10/5–10/11 and week 5 is 10/26–10/31; in January 2027, week 1 is 1/1–1/3. Week and month boundaries use Taipei 00:00; the end includes the last day and is counted up to the time of the query at most. For each date the last record is taken; the baseline is the boundary snapshot or the last one before it, and when the start is earlier than the first record, the first raw snapshot is the baseline. If there is no snapshot at all for the period, null is returned; negative values keep their minus sign, and missing days are not filled in. The current count always comes from the latest snapshot.

Follower counts sit below each platform tab; FB / IG / Threads share a compact follower toolbar, with the dropdowns and three inline numbers on one row on desktop, and at 768 / 390px the dropdowns on one row and the numbers on another. Changing the year, month or week queries immediately, and choosing a past week or month switches to the “That week” / “That month” labels. Unconnected platforms show a specific notice. The block grows to its natural height and uses the shared size / padding variables; it may wrap on mobile. Custom dates, daily series, line chart, first-record / snapshot time and baseline explanation have been removed; old `date_from` / `date_to` queries return 422, and no other follower API user needs that feature kept. Date filters and charts for post performance are unchanged.

The existing hourly metrics schedule checks follower snapshots first and then syncs post metrics; only when there is no snapshot for the day does it call FB / IG `GET /{account-id}?fields=id,followers_count`, or Threads `GET /v1.0/{threads-user-id}/threads_insights?metric=followers_count`. Threads uses its own token and the existing insights permission gate: missing permission skips it, permission errors pause it; it does not count against the Meta quota, and format / value anomalies are not written but logged as errors. Normally this is one extra GET per account per day (two for FB + IG), with no need to read any Insights history; failures can be retried on later runs and are still subject to the shared hourly call limit, usage headers and Retry-After / backoff. One metrics run is requested at startup so a persisted next run time does not delay the first record; nothing runs when the schedule is disabled. A successful publish and “Sync now” in post analytics also each request one run: “Sync now” is limited to admin / marketing, the backend records the last request time in `scheduler.manual.metrics`, and clicking again within 60 seconds returns 429; if a run is already queued or running it is not queued again and does not count toward the cooldown; it is audited as `scheduler.request`. Actual calls are still subject to the shared hourly limit and usage-header backoff above. A failed field does not block post sync that can run; the schedule result lists `followers` errors separately, and existing snapshots are kept.

Both IG and FB use only `followers_count`. Official field references: [IG User](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user/), [Page](https://developers.facebook.com/docs/graph-api/reference/page/). These documentation pages returned 429 this time; the field was cross-checked against [Meta's official IGUser SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/iguser.py) and [Page SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/page.py), both of which list `followers_count`. No live Meta API was called this time; the availability of platform authorization is still for the deployer to check. When the field is not returned, a failure is recorded and no zero is written; `fan_count` is a Page field with a different meaning and is not mixed into the series automatically.

## Audience insights (0052)

`audience_insights` stores only the latest copy for each account and each distribution (`metric` followers / viewers / online × `breakdown` age / gender / country / city / hour), including status (ready / unavailable), missing-data code (permission_missing / not_available / no_data), the platform's statistics period, unit (count / percent), `items_json` and fetch time; it is overwritten daily and keeps no history. Fetching hangs off the hourly metrics schedule after thumbnails (`Workers.audience`), once per account per Taipei calendar day: all items for the same account are written together only when every one has a result; network errors, rate limits, 5xx or format anomalies are not written and are retried on the next run; an explicit platform refusal (permission, threshold, unsupported metric) is stored as unavailable and not tried again that day. When there is nothing to do it returns 0 and the schedule counts it as an empty run. Deleting a disconnected account's data deletes this too.

- **Instagram**: `GET /{ig-user-id}/insights?metric=follower_demographics&period=lifetime&timeframe=this_month&metric_type=total_value&breakdown=age|gender|country|city`, four calls; plus one `metric=online_followers&period=lifetime&since&until` call (last 7 days). online_followers returns one set of hours 0–23 per day (a Pacific Time day, with `end_time` at the next day's Pacific midnight), which is converted to Taipei hours and averaged. Permission reuses `instagram_manage_insights`; the platform returns no data when there are fewer than 100 followers.
- **Facebook Page**: one `GET /{page-id}/insights?metric=page_follows_country,page_follows_city&period=day` call, taking the latest day. Meta deprecated `page_fans_gender_age` and other age / gender metrics on 2024-03-14 with no replacement; `page_fans_country／city` was deprecated on 2025-11-15, with `page_follows_*` as the official replacement.
- **Threads**: `GET /{threads-user-id}/threads_insights?metric=follower_demographics&breakdown=…`, four calls (the official API only allows one breakdown per call), reusing the Threads insights permission gate; on a permission error it pauses and keeps the previous day's data, and an ordinary API error (usually fewer than 100 followers) is stored as not_available.
- **YouTube**: YouTube Analytics `reports`, last 28 days (up to two days ago in Pacific Time), two calls: `dimensions=ageGroup,gender&metrics=viewerPercentage` and `dimensions=country&metrics=views&sort=-views&maxResults=10`, counted against the existing `youtube.quota`. Age / gender only covers signed-in viewers.
- **TikTok, LINE**: not called. The Display API has no audience data; LINE is used only for notifications. The interface shows the reason directly.

Meta calls are logged through `meta_api` and subject to the hourly limit, cooldown and usage headers; after rate limiting, no other Meta account is called in the same run. Normally that is five IG calls and one FB call per day. `GET /api/dashboard/audience` accepts an optional `brand_id`, reuses the account's brand permissions, can be read by admin / marketing / viewer and only reads the local DB. The dashboard “Audience insights” card switches by platform segment (URL `audience_platform`); available items are shown as bars (counts converted to shares) or 24-hour columns, and when data is missing or the platform does not provide it, the reason is shown. Country codes are shown with `Intl.DisplayNames` in the interface language. The live response format is unverified: the value format of FB `page_follows_*` is assumed to match the old `page_fans_country` (`{code: count}`), and Threads `follower_demographics` is assumed to match IG's `total_value.breakdowns`; check these after deployment.

## AI and message classification

The official Gemini / OpenAI / Anthropic clients share application-level retries, with the SDKs' built-in retries turned off. 408, ordinary 429, 500, 502, 503, 504 and connection / read timeouts are attempted at most 4 times, waiting 2 / 5 / 10 seconds, each plus 0–0.25 seconds of jitter; Retry-After (seconds or HTTP date) and Google's `google.rpc.RetryInfo.retryDelay` take precedence. When the provider's suggested wait exceeds the remaining time, the error is reported immediately, without idle waiting, early resending or extending the limit.

A Google 429 whose error content contains `free_tier` returns `provider_quota_free_tier`, treated as not fixable by short retries: it ends immediately and does not switch to the same provider's fallback; other 429s return `provider_rate_limited`. An OpenAI 429 with `insufficient_quota` or a billing / spending-limit code returns `provider_quota_exhausted`, with no retry and no fallback; an Anthropic 429 `rate_limit_error` returns the ordinary rate-limit code, and no billing cause is inferred from that code. Only the code and a bounded non-negative wait in seconds are stored, appended as `;retry_after_seconds=N` to the existing error field for the UI; the provider's raw error text and absolute monotonic clock values are not stored, and there are no table changes.

The brand `ai.brand.<id>` settings add `*_fallback_model` for the three providers, reusing brand write permissions, version-conflict checks and the `ai.settings` audit. Gemini defaults to `gemini-3.7-flash` and the other providers default to blank; an explicit blank disables the fallback, and when primary and fallback are the same there is no repeated switch. Only when the primary model is still at 408 / ordinary 429 / 5xx / timeout / connection failure after retries does it switch to the same provider's fallback; permanent errors and incomplete / refused content end immediately. Primary and fallback share `AI_API_TIMEOUT_SECONDS` (default 60 seconds); when a fallback exists, `max(20 seconds, total limit / 3)` is reserved, so by default the primary model gets at most 40 seconds. If less than 10 seconds would remain after backoff to send the next request, primary retries stop and the fallback takes over; time left over when the primary ends early can also be used by the fallback. The fallback gets at most 4 attempts, each with the SDK timeout set to the remaining time of the stage. If less than 10 seconds remain before any request, the request is not made and `provider_time_exhausted` is returned. A shorter total limit may skip the primary model entirely, and the 20 seconds cannot be guaranteed beyond the total limit; with a total limit under 10 seconds no request is sent at all. The Retry-After of the last response also applies to the fallback; if waiting would eat into the time reserved for the fallback, the rate-limit / provider error is reported directly, without idle waiting or early requests.

Gemini quota is managed per project, and the actual limits vary by model and plan; a limit in an individual error is not treated as the overall default. Free-tier quota failures use a conservative stop strategy, and you cannot assume a fallback model lifts the limit. For ongoing use, set up paid billing for the project in Google AI Studio, then check the effective quota, usage and budget. Official docs: [Gemini quotas](https://ai.google.dev/gemini-api/docs/rate-limits), [billing setup](https://ai.google.dev/gemini-api/docs/billing), [OpenAI error codes](https://developers.openai.com/api/docs/guides/error-codes), [Anthropic error codes](https://platform.claude.com/docs/en/api/errors).

Text models and background tasks only use official Gemini, OpenAI and Anthropic API keys; the local CLIs have been removed and writing is now handled by Agents. All text sent to the cloud first has personal data masked, and model usage is tracked per brand. Shared and brand prompts have versions, diffs and restore, and cannot loosen backend guardrails.

jev uses TypeSafe v1's Choice / Noul / Score; each question quotes named state fields in backticks, and customer text and content under review are treated as data. Independent questions on the same state are sent together, and all go through `redact.scrub` and `jev.valid_response`. Choice keeps a no-match exit; Noul is the probability that a condition holds, and near 0.5 does not mean medium strength; Choice / Score confidence is how concentrated the distribution is. Existing policies and thresholds are unchanged; adjustments must first be evaluated on labeled data. Sources: [questions](https://docs.typesafe.ai/primitives), [state](https://docs.typesafe.ai/concepts/state), [confidence](https://docs.typesafe.ai/confidence).

Brand category notes are stored in Setting as `classification.intents.brand.<id>`; the nine intent codes are fixed, each entry is trimmed and limited to 200 characters, and unknown fields are rejected. `GET/PUT /api/classifications/intents?brand_id=` reuses brand permissions, settings version conflict 409 and the `classification.intents` before / after audit. Brand examples are appended after the generic service description, stating explicitly that examples are not instructions; text is still redacted before going to the cloud. `QUESTION_VERSION=triage-2026-10-23-v3`, and raw_json stores `intent_notes_version`; the notes are not added to the context / fingerprint, the fingerprint stays fixed at `triage-2026-09-26-v3`, existing results stay valid and are not recomputed or re-queued, and new settings only affect later new messages and manual re-triage.

The triage state defines sender as the customer, and the message and masking counts cannot be overridden by same-named fields in context; the question version and input hash version are separate, so rewording keeps existing results valid. Only manual re-triage or new existing jobs use the new questions; policy recomputation still only applies stored signals. The question version for idea classification is likewise independent of the fingerprint, so rewording does not trigger paid recomputation, and the existing classification flow remains subject to its original limit / budget.

The representative-quote Choice can return none, in which case the sources already chosen are kept and it stops, without padding to five; later selections update the state based on what has been chosen, so requests are still made one at a time. The CSV state uses `columns.column_<index>`; question IDs and returned column indexes are unchanged, and ignore is kept. `scripts/eval_jev_questions.py` compares the fixed old wording with the current builders on five synthetic data sets (sixteen triage cases, eight each for the rest); it uses a stub transport by default, connects to the official API only with `--live`, and limits output to `.runtime/`. Passing with the stub only proves the pipeline works, not that quality improved.

## Brand-neutral settings

`settings.workspace.display_name` (the actual key is `workspace.display_name`) stores the product name. The public internal sign-in identity API returns only the name and version; changing it is admin-only and audited. The sign-in page, navigation, header, tab title and Word header share this value.

`ideation.brand.<id>` stores recurring meetings and topics; the new defaults are disabled, with blank weekday / time, and the only topic is “Other”. `brand.rules.<id>` stores banned words; the default is an empty list. Historical price data is kept but has no entry point.

Templates are version-controlled JSON; the admin first previews the diff, then confirms with a hash covering the brand state and template content. Applying updates topics, banned words and a new brand prompt version in a single database transaction, keeping recurring meetings and send permissions. Any data change invalidates an old preview.

Content research uses only real evidence; reports must cite actual message IDs on the same topic, and missing items are not fabricated. Brand content comes directly from settings and prompts, without reading any particular external knowledge base. Scripts can be edited, rechecked and versioned, but cannot publish platform content.

## Dashboard marketing summary and daily trends

`GET /api/dashboard` covers Taipei Monday 00:00 up to the time of the query and returns new_messages (existing non-historical DMs), new_comments (count of direction=in / author_type=fan messages in public comment_threads, including comments fetched later within the period) and top_intent (the latest classification with a valid fingerprint for this week's non-historical customer messages, excluding spam / unknown codes). Top categories include both DMs and public comments, with ties ordered by code; with no data it returns null. Each brand builds the classification context only once. The question distribution remains the latest classification of this week's new DMs. pending_threads, first_reply_seconds, first_reply_samples, stages and related queries have been removed.

`GET /api/dashboard/trends?days=30` accepts an optional brand_id and reuses Access; days is only 7 / 30. The response is `{days, timezone: "Asia/Taipei", series: [{date, new_messages}]}`, with zero values filled in per Taipei calendar day. The summary and trends share incoming_messages, counted by sent_at, excluding historical DMs and future messages.

Trends run a single batch SELECT and aggregate by day in memory, without opening a write transaction or triggering platforms / models. Existing indexes are reused, with no migration. test_workspace keeps 2,000 messages / 500 threads, read-only, with a 300ms limit (1 second in CI), and now verifies a single SELECT. Exported reports never had the customer-service KPIs above, so their format is unchanged.

### Growth comparison and conversion funnel (deferred items added 2026-10-16)

- The summary also returns `previous: {start, end, new_comments}`: from last Monday 00:00 to this moment seven days ago (the same length as this week, end exclusive). Trends also return `previous_total`: the total new comments for the equally long 7 / 30 days immediately before the window, fetched in the same SELECT as the series. When the previous period is 0, the frontend does not compute a percentage.
- `GET /api/dashboard/funnel?days=30` accepts an optional brand_id with the same permissions as trends; days is only 7 / 30. The population is posts published in the last N days (Taipei calendar days), not deleted, whose latest snapshot has reach; the four stages in order are reach (total reach), engagement (total count of likes + comments + shares + saves, which can exceed reach), comments (inbound customer comments on these posts) and purchase inquiries (those whose latest valid-fingerprint classification is price / booking / model_question). The response is `{days, timezone, posts, stages: [{key, value}]}`, and the frontend computes conversion rates from the previous stage. The originally planned “deal” stage was removed along with noinbox and no longer appears.

## Post thumbnail cache (0046)

Platform CDN image URLs expire, so each post also stores a shrunken JPEG (longest side 480px) in `post_thumbnails` (one row per post, data lazy-loaded). Fetching hangs off the hourly metrics schedule, with `post_thumbnails.hourly` handling at most 20 posts per run (new posts first): FB reads `GET /{post-id}?fields=full_picture`, IG reads `media_type,media_url,thumbnail_url` (cover only for videos), Threads reads the fields of the same names, TikTok uses the Display API `POST /v2/video/query/` (`fields=id,cover_image_url`, needs `video.list`, with the same connection requirements as TikTok sync) to get a currently valid cover URL and downloads it immediately (cover URLs expire; if the video is not in the list it has been deleted or made private and is marked unavailable; on rate limiting or expired authorization the whole run skips TikTok without using up retries), and YouTube uses the public `i.ytimg.com/vi/{id}/hqdefault.jpg` directly, using no Data API quota. FB / IG make one Meta call per post, logged through `meta_api` and subject to the hourly limit and cooldown; during cooldown the whole run skips Meta. Images are downloaded only from https URLs on `fbcdn.net` / `cdninstagram.com` / `ytimg.com` / `tiktokcdn.com` / `tiktokcdn-us.com` / `tiktokcdn-eu.com` (other hosts log a `thumbnail_untrusted_host` warning containing only the host name; TikTok's cover domains are not documented, so an unknown domain goes to retry rather than being dropped), redirects are not followed, the source limit is 8 MB, and Pillow shrinks the image and converts it to JPEG (transparent backgrounds become white). Text-only or deleted posts are marked unavailable and not tried again; temporary failures such as network errors or rate limits are retried after 1 / 6 / 24 hours and stop after the fourth failure. `GET /api/posts/{id}/thumbnail` returns the image using the post's brand permissions; the post list, single post and dashboard rankings return `thumbnail_url` (including a digest fragment for cache busting), which is null when there is no thumbnail. Only official GETs are used and nothing is written to platforms; verification uses stub HTTP.

## Export and auditing

Markdown / Word files go into a brand subfolder under a configurable root directory. Word uses the workspace name, exports filter out secrets, and paths are protected against traversal. MCP tool responses always mask personal data, and every call leaves an agent.tool.read / write audit (see `docs/en/mcp-spec.md`).

Normal changes keep audits and prompt versions; clearing historical content requires separate explicit authorization, a preview and a backup, and audits are never rewritten automatically.


## How text models run (nocli)

Writing is handed to Agents (`/mcp`, the Claude Code plugin, Codex, the Claude desktop extension, Hermes). From 2026-10-12, execution, detection, sign-in checks, model listing, updates, the settings page and related APIs for the three local CLIs `codex_cli`, `claude_cli` and `agy_cli` have been removed; the workbench no longer starts any codex / claude / agy process. All text AI uses only official Gemini, OpenAI and Anthropic API keys; the rules for keys, models, fallbacks, usage and monthly budgets are unchanged, and text sent out still goes through `redact.py` first. `ai.run` only accepts the three API providers; other values return `provider_unavailable`; new usage records are always `mode=api`.

Old data stays compatible, is not rewritten and gets no migration:
- A CLI-type setting value read from the brand's `ai.brand.<id>` (`default_provider`, `manual_provider`, `background_provider`) is treated as unset; `ai.config` converts only on read and the database keeps the original value. `AISettings` writes accept only the three API providers and empty values, and an old value does not block saving the budget or fallback models. The global `ai.local_cli` and `ai.cli.*` Settings are no longer read, and are not deleted either.
- Old `mode=subscription` records in `ai_runs` (including those with null tokens) still appear in the “This month's usage” table, labeled as the discontinued old CLI; the monthly budget counts only `mode=api` and is unaffected.
- Old reports whose provider is a CLI can still be viewed and exported; they cannot be retried (`can_retry` is false), and the error text shows “Local CLI is no longer supported (legacy record)” (`本機 CLI 已不再支援（舊紀錄）`). Schedules and retries only handle API and agent reports.

`GET /api/ai/settings` returns only settings, available API options, budget and usage, with no top-level `draft_provider` anymore; the `draft_provider` of `GET /api/ai/execution-options` is the brand's `default_provider` (an empty string when unset), and the options include only the three API providers. “Default AI” now only decides the default execution method for ideation.

When web ideation creates a report, `provider` can be one of the three API providers or `agent`. Choosing an API follows the original flow: fetch comments, jev classification, aggregate evidence, then the API generates fifteen ideas in one go (`compose_prompt` is now used only for ideation, with the prompt field order unchanged). Choosing `agent` stops at the existing `awaiting_ideas` after evidence aggregation, without calling any text AI; the screen explains to use `/mwb:ideas` in Claude Code, or `get_guide("ideas")` in other Agents, to take over and save back within 24 hours, reusing the evidence, save-back and timeout rules of `agent_content`. Agent reports created from the web have no connection source marker, and retry is allowed on failure (including timeout). Recurring-meeting schedule reports (`trigger="background"`) always use the Gemini API. Default order on screen: the browser's `ideation-choice:<brandId>` memory (written only on a manual change), the brand's default AI, the first available API, then “Let an Agent write it”; CLI memory and default values are always skipped.

Removed: the “Regenerate”, “Extended idea” and “Generate script” actions on idea cards, plus `POST /api/ideation/reports/{id}/ideas/regenerate`, `.../ideas/{index}/extend`, `POST /api/ideation/reports/{id}/scripts`, `idea_actions.request／process` and `video_scripts.generate／compose_prompt` (the routes have been removed from `permissions.py`, and calls return 404 or 405). Kept: idea editing and restoring the previous version (the Agent's `edit_idea` shares `idea_actions.edit`), script viewing and editing, `video_scripts.review`, and the Agent's `save_script`. The card keeps only “Edit” at the top right; at the bottom there is an extra “View script” when a script exists, and otherwise “Create publish draft”, or “Open publish draft” when a draft already exists. The old `ideas_job` and `regenerated` / `extended_from` markers in the report's `data_json` are only for showing history and no longer have progress or error UI; old jobs still queued at upgrade time are no longer run, and when the report is processed it goes straight back to the original ideas and the job field is removed. `video_scripts.view` adds `topic_index` so the card can find the latest script for that idea.

Publish drafts no longer use AI to write captions: `POST /api/publish/ideation-draft` builds the first draft from the idea title, opening and hashtags (`publish.idea_caption`), without referencing the script; the `include_script` field is ignored, so submissions from old screens do not fail. Removed: `GET /api/publish/ideation-preview`, `POST /api/publish/posts/{id}/caption/retry`, `.../caption/apply`, the `publish_caption` service and the startup marking of interrupted caption jobs. The `publish_posts.caption_job_json` column is kept (no destructive migration); the code no longer reads or writes it, and `view` and the list do not output it. When an old draft carries caption job data, the publish page shows no AI status and does not list empty drafts because of it. The Agent's `create_draft_from_idea` behavior is unchanged (it uses the caption passed in directly).

`services/processes.hidden_process_kwargs()` is still shared by auto-start at boot and backup 7-Zip, and is not CLI-specific.

## Publishing

Platforms: Facebook Page, Instagram, Threads, YouTube, TikTok (sent only to the inbox; publishing must be completed in the app); formats: short video, image, carousel, text only, stories. Target accounts follow the accounts set for the current brand in “Platform connections”.

- **Rules and checks**: one main caption, which can be overridden per platform. Rules are centralized in `backend/app/services/publish_rules.py`: `RULES` (caption, duration and so on, returned to the frontend as-is) and `MEDIA_RULES` / `IMAGE_BYTES` / `VIDEO_BYTES` (media aspect ratio, width, size, mime); `GET /api/publish/options`, the Agent's `get_publish_options`, upload checks and Agent uploads share the same set (character count, hashtags, video length / aspect ratio, file size, mime, width). Platforms that don't comply are marked red and block publishing; the system never automatically truncates, rewrites or transcodes (the only exception: PNGs sent to Instagram are converted to JPEG). Formats a platform doesn't support are disabled with an explanation (for example, Instagram doesn't support text only, and YouTube only supports video).
- **Scheduling**: immediately or at a specified Taipei time; the workbench scheduler runs every minute and hands due posts to a background thread for publishing (the scheduler doesn't wait for uploads to finish, so a long upload won't get other posts due at the same time marked as missed); from one minute before the scheduled time, editing / cancelling is locked. Posts more than five minutes overdue are not sent late; they are marked “Missed” with a notification, and the user decides whether to publish now or reschedule. When the master switch is off, all schedules are paused; after it is turned back on, posts not yet due proceed as normal and overdue ones are marked missed.
- **Partial success and retries**: platforms that succeeded are never resent; only “Retry failed platforms only” is possible. At service startup, interrupted publishing is marked interrupted and not resent automatically; the user checks the platform first and then decides whether to retry. For multi-part content (Threads threads, multiple stories), the platform ID is saved in a short transaction after each successful part, and a retry after failure only continues with the remaining parts; once some parts have succeeded, the parts, media and accounts are locked. A timeout whose result cannot be confirmed must be checked manually on the platform to avoid duplicate posts. An unexpected error during publishing marks unfinished platforms as `unknown` (check on the platform) and settles the post, so it doesn't get stuck publishing. When a schedule is cancelled or marked missed, unsent platforms are removed if never attempted and go back to failed if attempted; each submission only sends the platforms chosen this time that are still checked.
- **Media**: stored under PUBLISH_MEDIA_ROOT with random file names; cleared 30 days after all platforms succeed, kept in other states. When IG / Threads need a public URL, a temporary `/media/<token>` link is created (revoked after 15 minutes or once fetched, at most 32 times; anything invalid is always 404, and it is included in the public boundary checks); YouTube is uploaded directly by the workbench without a temporary link.
- **Facebook unpublished posts**: `facebook_unpublished` creates the post with `published=false` and affects only Facebook; once Facebook has succeeded or is publishing, it is locked and retries reuse the original option. These posts don't appear in `/published_posts`, so their performance isn't fetched; deletion is determined by per-post queries instead (first confirm the Page can be read; only 100/33 or 10 counts as not existing, other errors decide nothing).
- **Reels and Threads threads (composer1, 0041)**: FB Reels go start → rupload → finish; when chosen together with unpublished, they are created via feed instead, with a notice. IG sends `share_to_feed` explicitly only when it is `false`. The IG Reels cover (0048, `publish_media.role=cover`, bound to `instagram.cover_media_id`, maintained by the server) is sent as `cover_url` through a time-limited public link, with PNGs going through a `.jpg` derivative (the official API only accepts JPEG); without a cover the request stays as before (the platform uses the first frame). Once IG has succeeded or is publishing, the cover cannot be changed. The FB video / Reels cover (0049, `role=fb_cover`, bound to `facebook.cover_media_id`) is applied with `POST /{video-id}/thumbnails` (`source` + `is_preferred=true`) only after the post has succeeded and been saved, with the result written to the target's `detail.cover`; failure doesn't affect the post, and “Reapply cover” is available (`POST /api/publish/posts/{id}/facebook-cover`, never re-uploading the video). This needs the optional permission `pages_manage_engagement` (`oauth.META_OPTIONAL_SCOPES`): it is requested along with authorization, and when missing it doesn't affect connection status or publishing readiness; the publish options only return `cover_hint`. In Threads, the first part carries the media and later parts are chained with reply_to_id; automatic splitting prefers blank lines / line breaks, then sentence-ending punctuation, and finally a hard cut, without adding numbering, and emoji are counted in UTF-8 bytes. Platform IDs and deletion detection only look at the first part; FB videos and Reels record the video ID, compared against the `/videos` list.
- **Stories (composer3, 0042)**: `format=story`, 1–10 items, each one image or one video, only for FB / IG, with no text or post options. For IG stories that succeeded, insights are read every hour within 24 hours, stopping when a signature-verified `story_insights` final snapshot is received; unsupported metrics are left empty, not filled with zero. FB stories have no performance data for now. Stories have no deletion detection.
- **YouTube (ytpublish, 0043)**: needs the `youtube.upload` scope (the broader `youtube` / `force-ssl` is not requested); when missing, the publish tab is grayed out and guides the user to reconnect. Official resumable upload: 8 MiB chunks; on interruption or 5xx, back off 1 / 2 / 4 / 8 / 16 seconds up to 5 times, each time first asking how many bytes were received before resuming; on a session 404, start over once; the session URL is stored in `detail_json.upload` and never returned to the browser or MCP. After the video completes, `video_id` and the actual privacy status are saved first, so later thumbnail success, failure or interruption never re-uploads the video. The thumbnail is set separately with `thumbnails.set`; failure doesn't affect the video's success, and “Reapply thumbnail” is available; videos that will be classified as Shorts (vertical / square and ≤180 seconds) have thumbnails disabled (`RULES.youtube.shorts_thumbnail`). Before calling `videos.insert`, the daily `youtube.uploads` allowance is deducted; thumbnails deduct from the shared `youtube.quota`.
- **Deletion detection**: determined only by "absent from the complete list", not by errors on single-post queries (except FB unpublished posts, see above); if any page fails, the paging limit is reached, the format is anomalous or the account changed, nothing is determined. Reappearing in the list clears deleted_at.
- **Safety**: the “Allow publishing to platforms” master switch (Setting `publishing.enabled`) is off by default and only admins can toggle it; a confirmation dialog is shown before every publish or schedule; every publish writes an audit; success, partial success, failure, missed and token-expiring-soon events are queued to the existing brand LINE notification group (without media URLs or credentials). After publishing only the platform link is kept; the workbench never edits or deletes platform posts.

## Platform credentials (creds)

0031 adds platform_credentials (provider / encrypted_key / version / timestamps); every field, including IDs and official base URLs, is Fernet-encrypted, and the master key stays only in .env. The jev ciphertext and version in the existing ai_credentials moved to JEV_API_KEY without decryption and without losing the original value; the old AI jev API is kept for compatibility and shares the new table. Removal keeps the version with an empty ciphertext, so a stale screen cannot pass the version check by deleting and recreating.

credentials.resolve(name, settings, session) is the single resolution entry point for platform settings: DB first, env only when there is no override; a bad ciphertext does not fall back to env. Values are not cached; every new request / worker operation takes the latest value. Webhook signatures, identity, Meta Graph token / accounts, LINE profile / notifications, health notifications and jev all go through this entry point; webhook_normalize.secret delegates to it for platform fields. The Python evaluation tool and the Node platform setup script use the same shared resolution; Node obtains settings through a local Python subprocess, the one-time AES-GCM IPC key is passed only on stdin, stdout carries only ciphertext, errors use fixed wording, and there is no public decryption API.

GET / PUT / DELETE /api/credentials and POST /api/credentials/{group}/test are admin-only. Writes check the version, and audits store only field names, action and operator; the API returns only configured / source / mask / version / error. Connection tests run only when an admin explicitly clicks, and writing itself makes no outbound connection; Meta /me and LINE bot info are single GETs, and jev reuses the existing post_json and redact. Fixed timeouts, no redirects, no raw responses / exceptions returned, and the jev URL is limited to the official endpoint. Tests all use HTTP / CLI stubs.
