## Agent install (agentpack)

- Add `.agent-install` between the My account password form and Agent connections. The h3 “Install Agent” sits on the same row as a compact `SegmentedControl` that switches between Claude Code / Codex / Claude desktop. Visible to all roles; on narrow screens the control moves to the next row and its width matches the card.
- Each `.agent-install-command` holds only one line of command code and a `.secondary` copy button; on narrow screens the command may wrap. After a successful copy the button changes to “Copied”. The two Claude Code install commands are built from the current location.origin, followed by just one sentence about automatic updates.
- Codex uses `.secondary.agent-install-download` to download the skills/config bundle, then lists the unzip command, one sentence on where to put the skills and how to merge the config, and the OAuth sign-in command; the UI does not list every tool setting. The version comes from the existing workspace/identity API.
- On http://127.0.0.1, show `.notice.agent-install-origin` telling other members to use the internal HTTPS address. The link comes from backoffice_origin in the same API; the host is not hard-coded.
- Commands use text-main / bg-subtle / ui-font-mono / help; descriptions use text-subtle / bg-surface. Corners use the control token; everything else follows P1-1 and the shared components, with zero external resources. No horizontal overflow at 1440 / 768 / 390px; check_agent_auth and similar checks measure only after data, fonts and layout are stable, and check_ui_contrast covers every new pair.
- Claude desktop has only a `.secondary` “Download desktop extension” and a three-step list: install the file, enter the workbench URL, paste the connection token. The URL and copy button sit on the same row and show location.origin; on HTTPS it can be copied directly. On 127.0.0.1 over HTTP, reuse the origin notice; on the second step's row suggest that members use the internal HTTPS address and that the local machine uses <http://127.0.0.1:8000>. No extra subheadings; reuse the text and background tokens above.

## Agent ideas and scripts (agentquery)

- The report list `.report-row-state` and the report page `.report-heading-meta` show `.agent-source-chip` “From <connection name>” on the same row; the script `.script-heading` uses the same pill next to its h2, with width matching its block and wrapping naturally.
- awaiting_ideas shows “Waiting for an Agent to write ideas”. The report page uses one `.agent-awaiting` paragraph explaining that the evidence has been gathered, that the ideas are saved back after being finalized in the conversation, and the 24-hour deadline. In this state, export and regenerate are not shown; delete is allowed. Polling picks up the ready state saved back over MCP.
- The source uses text-subtle / bg-subtle, help font size and control radius; the waiting description uses text-subtle / bg-surface. Only P1-1 tokens, zero external resources; no horizontal overflow at 1440 / 768 / 390px, and the pairs are included in check_ui_contrast.
- On the idea/script pages, submit uses primary; cancel, relabel, adding/removing shots, apply history, view and download script, and create/open publish draft use secondary; delete uses primary danger. This section overrides the history button rules further below.

## New version notice

- On signed-in screens, every 5 minutes and whenever the window regains focus, compare the main bundle file name referenced by the server's `index.html`; if it differs from the one currently loaded, show `.update-notice` in the bottom-right corner: “Workbench updated” + `.secondary` “Refresh”. On mobile it sits above the bottom navigation. Not checked in development mode.

## Agent connections and approval (agentauth)

- The approval screen is `.agent-approval-page > .section-card.agent-approval`, containing only an h1 and `.agent-approval-details`; the app's self-reported name, callback address, current member/role and what it can do each sit on one row. Viewers see only queries; admins and marketers also see creating drafts and publishing (which needs separate confirmation). Approve is primary, deny is secondary, submitted through a same-origin form carrying the existing CSRF value. Not signed in and must-change-password reuse their existing screens, and the URL keeps the authorization request. The response uses DENY to prevent framing; the approval page's same-origin referrer policy preserves the native form's Origin check.
- After the My account password form, add `.agent-connections`, with the title and a secondary “Create connection token” on the same row, width matching the card. Creation reuses `.member-dialog`, with only a name and a primary create button; on success `.agent-token-row` shows the full token once, with secondary copy/close. The value lives only in component memory and is cleared on close or unmount; it never goes into the URL or browser storage.
- In `.list-box.agent-connection-list`, each `.agent-connection-row` shows on one row the name, an OAuth / connection token pill and a primary danger revoke. Created, last used and expiry times are merged into one row, shown in Asia/Taipei; a connection expires after 30 days unused. Revoke uses ConfirmDialog, with cancel focused first, Escape/Tab support and focus restoration.
- Member rows get `.member-connections`, with the connection count and a secondary revoke-all on the same row; disabled at zero, and ConfirmDialog before submitting. Below 900px the rows flow naturally into two columns; at 390px the connection controls take the full row. Callback, name and token may wrap.
- Only P1-1 color/typography and control/card radius tokens, zero external resources; no horizontal overflow at 1440 / 768 / 390px. Text/background pairs are added to check_ui_contrast; check_agent_auth measures after data and fonts are stable, and the one-time token in screenshots is shown with a neutral mask.

## Publishing (publish)

- Agent drafts, editing and scheduled posts show `.agent-source-chip.publish-agent-source` “From <connection name>” on the existing format row; publish history first shows the name of the connection that confirmed publishing, otherwise the draft's source. The idea source pill is kept. The editing source goes in `.publish-editor-heading`, with no new subheading or description row. Uses text-subtle / bg-subtle, help font size and control radius; long names wrap naturally, no overflow at 1440 / 768 / 390px.

The desktop sidebar and mobile bottom bar have five items, in order: Dashboard, Post analytics, Ideation, Publish, Settings. Publish uses `view=publish` to keep state across refresh and back navigation; this section overrides the old four-item navigation rule below.

- `.publish-page.settings-page` keeps a single PageHeader “Publish”; on the right, `.publish-switch` is a ready/neutral pill plus a secondary toggle for admins. When off, a top `.notice.warning` shows “Publishing is turned off, so posts can only be saved as drafts”. The brand and each account sit on one row, wrapping naturally.
- `.publish-tabs` is an underlined tablist, in order New post / Stories / Drafts / Scheduled / Publish history, linked with tab, tabpanel, aria-controls and roving tabindex, supporting Left/Right and Home/End. Viewers see only Publish history.
- composer2: above New post / draft editing, `.publish-composer-tabs` has six tabs: Shared, Facebook, Instagram, Threads, YouTube, TikTok, with tab/tabpanel, arrow keys and Home/End; the platform tabs include the publish toggles. Ready platforms are green; not connected / token expired and unsupported platforms are gray, with the toggle disabled but the tab still reachable, showing “Not connected” and a secondary “Settings → Platform connections” that reuses settings_tab=connections navigation. The TikTok tab, like YouTube, supports video only: for non-video formats the toggle is disabled (title “Only videos can be published. Upload photo posts in the TikTok app.”) and the tab shows only that sentence; for video it shows the TikTok caption and `.notice.tiktok-caption-notice` “The inbox doesn't include the caption…”, with no other options. In the confirmation dialog the TikTok item reads “Video · Sent to TikTok inbox (caption isn't sent; paste it and publish in the app)”. In Publish history, successful TikTok rows get a `.status-badge` “Sent to inbox” (pending) / “Published in app” (ready) / “Processing on TikTok”, and a secondary “Copy caption” (copies the TikTok caption, or the shared caption if not overridden; shows “Copied” after clicking). Platforms that are off can still be edited and are marked “Off”.
- composer3: Stories has only two platform tabs and toggles, Facebook/Instagram; connection colors, disabling and settings guidance follow composer2. Each story set has 1–10 items, one image or one video per item, with drag, secondary move up/move down and primary danger remove. There are no caption, format or post option fields; autosave is reused and only the publish/schedule submit buttons remain. Spec violations are merged into one red-text spot. The 9:16 preview switches with secondary previous/next and shows the item count. Non-9:16 only gets a notice that borders will be added. IG video 3–60 seconds, images ≤8MB (PNG gets a warning “Instagram converts PNG to JPEG automatically; transparent backgrounds become white”; other non-JPEG formats are errors), FB video ≤60 seconds; errors block publishing in red text. Immediate/scheduled confirmation lists platform, account, item count, media and time. History is labeled “Stories” and expands to per-item IG insights / final values, with missing values shown as “—”; FB shows “Facebook doesn't provide story insights”, and nothing is added to the dashboard. After a partial success the media is locked; retry shows the number of items already posted and where it failed.
- `.publish-composer-grid` has the editor on the left and the preview on the right. Shared holds the format, shared media and main caption; each platform holds a caption that follows Shared by default and becomes platform-specific once edited, and secondary “Revert to shared caption” restores following. FB video form is video post / Reels (new drafts default to Reels, old drafts keep feed); the unpublished option lives on the FB tab. IG video uses an “Also show in feed” toggle, on by default. Below it, `.publish-thumbnail.publish-cover` puts on one row “Reels cover”, a 54px-tall 9:16 cover preview, file name and size (with no cover, small text-subtle text “JPG/PNG · Up to 8 MB · 9:16 recommended · Uses the first frame if none is uploaded”), secondary “Upload cover” / “Replace cover” and primary danger “Remove cover” (file input aria-label “Upload Reels cover”). The cover is the poster of the IG preview video; non-9:16 or PNG only get a `.notice.warning`. Cover buttons are disabled once IG has succeeded or is publishing. The IG video item in the confirmation dialog reads “Reels · Also show in feed / Not shown in feed · Custom cover / Default cover”. FB video has, below “Save as FB draft”, a `.publish-thumbnail.publish-cover.publish-facebook-cover` “Video cover” row (54px tall, original aspect ratio, at most 96px wide; with no cover, small text “JPG/PNG · Up to 8 MB · Same aspect ratio as the video recommended · Facebook picks one if none is uploaded”; buttons as for IG; file input aria-label “Upload Facebook video cover”). Without pages_manage_engagement the row adds `.notice.publish-cover-hint` (a neutral hint, not a warning) “Custom covers need the pages_manage_engagement permission. Reconnect Meta.”. The cover is the poster of the FB preview video; a different aspect ratio from the video only gets a hint. The FB video item in the confirmation dialog reads “Video post / Reels · Custom cover / Default cover (· Draft)”. In Publish history, when FB succeeds but the cover fails, the row shows `.status-badge.pending` “Cover not applied”, the reason in plain language and secondary “Reapply cover” (confirmation dialog “Reapply the cover to Facebook? Only the cover is replaced; the video isn't re-uploaded.”; viewers don't see the button). Platforms that have succeeded or are publishing, and Threads options already partly sent, are locked.
- `.publish-preview` uses the brand's initial as avatar, the account name, text and local media, with no external resources. The Shared preview lists secondary small buttons only for platforms that are on; a platform tab is fixed to its platform. Text collapses by simplified character/line thresholds and toggles with secondary “More / Show less”; @ and hashtags use link-color. Threads shows the first topic tag and the first post / reply thread posts, with media only in the first post. IG images use 4:5 / square uses 1:1, Reels use 9:16, FB video posts / Threads keep the original ratio. Videos are always shown in full (contain); when the frame and video ratios differ, `--media-letterbox` fills the gaps (for example top and bottom bars for a horizontal video in a vertical frame), because the original file is sent and platforms don't crop it. Images still fill the frame. At ≤767px the preview sits at the top of the editor; no horizontal overflow at 1440 / 768 / 390px.
- Threads splitting prefers blank lines, then line breaks, then sentence-ending periods, then a hard cut. Unicode counting data and test vectors live in shared/publish_threads_vectors.json and are verified by both pytest and the frontend. Auto mode follows the source caption live; any manual edit/add/delete stops recalculation. At least one part is always shown; each part has one row with part number / character count / primary danger delete part. Secondary “Re-split from main caption” first confirms the overwrite with ConfirmDialog; published text gets no numbering.
- Platform tabs show red-text errors for character count, hashtags, @, media length/ratio rules, and the tab label gets a red dot; backend hints show as notice warning. Any blocking error on a platform that is on disables publishing. Errors appear in one place only: `#publish-disabled-reason` on the first row of `.publish-footer` (red text, its own row, above “Publish now / Schedule” and the submit button), joined as “Platform: reason” with “; ”, listing the platforms that are on plus the platform tab currently viewed even if it is off. Tabs don't list errors separately; only the tab label red dot remains. Threads over-length errors are marked only under the input box and not repeated here; when only such errors remain, show “Fix the errors marked above first”. When publishing is turned off, show only “Publishing is turned off”; when no platform is on, start with “Turn on the platforms to publish to” followed by the current tab's errors. The button title keeps the full reason. publish-actions keeps a single primary publish/schedule and a secondary save as draft. The confirmation dialog lists per platform the form, the IG feed option, FB unpublished, the Threads part count, and account/caption/media/time. The Threads detail progress in history shows “Posted N/M parts”.
- New post starts as an empty form. After the first caption/platform input it autosaves with a delay; the first upload or save as draft saves immediately; unsaved content is saved before switching tabs/navigating. Selecting a format alone doesn't create a draft. `publish_post_id` keeps the current draft in the URL across pages; secondary “New post” saves first and then clears; a plain refresh doesn't add drafts.
- The Publish page has no UI for AI caption writing: above the main caption there is no progress, failed or done notice, no “Rewrite” or “Apply AI caption”, and the draft list has no “AI writing”. Even if old drafts carry caption job data in the database, the screen shows no AI state. For drafts created from an idea, the main caption is a first draft made of the title, hook and hashtags, and can be edited directly.
- Drafts use `.list-box.publish-records`; each row shows last modified time, format / from idea / AI writing pills, single-line truncated caption, media count, platforms, and secondary edit / primary danger delete. Delete needs ConfirmDialog. Old blank drafts with no caption, media or platforms are just hidden; Publish history lists only posts that were sent, failed or missed.
- In `.list-box.publish-records`, `.list-row.publish-record` shows time, format, start of caption, platforms and status on one row; scheduled posts lock one minute before. After the platform name, “ · Unpublished” marks Facebook posts sent with “Don't publish to Page” (both on list rows and in per-platform results). Records can expand `.publish-targets` with success links / safe plain-language reasons. For a successful unpublished Facebook result, the pill is `.status-badge.neutral` “Facebook · Succeeded · Unpublished” (same color family as “Deleted on platform”; failed or in-progress keep their original colors with the same suffix). On failure, only failed platforms are retried; missed posts can be published immediately or rescheduled. Delete draft is primary danger with confirmation; all other actions are secondary.
- Colors, fonts and radii reference only P1-1 / shared tokens, zero external resources; text/background pairs are included in check_ui_contrast. No horizontal overflow at 1440 / 768 / 390px; the five-column mobile navigation keeps the safe area; check_publish and similar checks measure after data, fonts and layout are stable.

## Platform setup guide dialog (guides)

- On the Meta, Threads, YouTube, LINE notifications and TikTok cards, at the right of the title row and before “Test connection”, there is a secondary “Setup guide” (jev has none). Clicking it opens an in-app dialog, not a new browser tab; the cards and the page itself must have no `target="_blank"` links (the only exception is the back-office links inside the dialog, see below). Callback URLs and Webhook URLs are shown and copied only inside the dialog, not repeated on the card.
- `.ideation-modal-backdrop > .guide-dialog` is mounted on body: `role="dialog"`, `aria-modal`, `aria-labelledby` pointing to the title. The title row is fixed, with a secondary “Close” at top right, and the content `.guide-body` scrolls on its own. On open, focus is on “Close”; Tab cycles within the dialog; Esc, Close and clicking the backdrop all close it, and focus then returns to the “Setup guide” button. At 390px it is full-screen (no backdrop margins, height 100dvh), with scrollable content and no horizontal overflow.
- The content lives in `frontend/src/platformGuides.ts`, written for people touching a developer console for the first time (rewritten in guides2): each guide has an estimated time `minutes`, a “Before you start” `needs` list, a collapsible glossary `glossary`, and step sections. Each step does one thing, and buttons and menus are marked with the actual UI wording in quotes; when unsure, “(in the English UI: …)” is appended. Steps can carry `check` (“✅ When done, you'll see”, `.notice.success`) and `trouble` (“⚠️ Stuck? Common issues”, `.notice.warning`). Meta has three sections: “Facebook Page”, “Instagram”, “Connect account”. Except for TikTok, the last step is always “Back in the workbench…”: Meta, Threads and YouTube explain “Connected” and the hourly sync; LINE explains “Test connection” and “Connection successful”.
- The dialog opens with `.guide-intro`: “Takes about N min”, the “Before you start” list and `details.guide-glossary` (the glossary), collapsed by default. Steps in `.guide-steps` use small square numbers (`::before` counters, continuing across sections). URLs and permissions are shown as `.guide-copy` (`<code>` plus a secondary “Copy” that shows “Copied” on success). Callback URLs come from callbacks in `/api/oauth/status`; the LINE Webhook URL comes from the configured WEBHOOK_PUBLIC_URL, and when not set it shows “Not set” and copy is disabled. Steps can carry `links`, listed in `.guide-links` as hyperlinks straight to the platform consoles (developers.facebook.com, console.cloud.google.com, manager.line.biz, developers.line.biz, developers.tiktok.com and so on), with `target="_blank"` and `rel="noopener noreferrer"`. The content contains no real accounts, names or local paths.
- The TikTok card uses the same layout as YouTube (`.connection-card`): account row with status pill, the “Access token renews automatically” note, and the refresh token expiry time in Taipei time. The two credential fields Client key / Client secret are listed directly on the card (no “Manual setup” collapse); until they are set, “Connect TikTok account” is disabled. When connected, a secondary “Disconnect” goes through ConfirmDialog, explaining that synced data will be deleted and videos on TikTok are not affected. The card's last row, `.notice.tiktok-comments` “Comments (optional)”, explains that reading comments requires a business identity. The guide walks the user through creating an app in Sandbox and connecting it; the callback URL and the four permissions can each be copied. Scope is in `docs/en/tiktok-plan.md`.
- Colors use only existing tokens: body text and intro info text-main / bg-surface, glossary explanations text-subtle / bg-surface, URL blocks and “Common issues” text-subtle / bg-subtle, “When done, you'll see” state-success / bg-subtle, step numbers bg-surface / brand-primary; radii control/card; zero external resources, already included in check_ui_contrast. Checks are in `check_platform_guides.py` (the five guides' titles, before-you-start lists, checkpoints, glossary expansion, copy, Esc / backdrop / close, focus restoration, no new-tab links on cards, and the domains and `target`/`rel` of back-office links inside the dialog; at all three widths, no horizontal overflow with the glossary expanded, the last step reachable when scrolled to the bottom and the title row fixed; screenshots in `.runtime/guides2-screens/`) and in the frontend `platformGuides.test.mjs`.

## Post analytics sync now (metricsync)

- For admins/marketers, the Post analytics page header replaces “Refresh ↻” with a secondary “Sync now”, which queues one round of post and insights sync; viewers still have only “Refresh ↻” (which only re-reads workbench data). While running it shows “Syncing…”, once queued “Sync queued…”, and during cooldown “Sync now (Ns)”, disabled, with the seconds taken from the backend's `retry_after`. When done it refreshes automatically and reports via sync-notice; the hourly scheduled run does not refresh automatically.

## Post analytics insights panel width (metricwidth)

- Superseded from 2026-10-23 by postcenter below: insights now sit in the middle. Original rule: in the desktop single-post detail, the right-hand insights panel (`.post-metrics`) is fixed at 380px, the left list 320px, and the middle comments column auto. ## Members and role permissions (members)

This section overrides the old rules for settings tabs and read-only settings for non-admins. For admins the settings tabs are, in order, AI, Platform connections, Message classification, Workspace, Members, My account; other roles see tabs according to their feature permissions (Platform connections = `connections.manage`, AI = `ai.manage`, Message classification and Workspace = `settings.manage`, Members admin-only). Marketers and viewers see only “My account”, including when a bookmark points to another settings tab. The sidebar brand menu lists only accessible brands; non-admins with no brands see “No brands assigned yet. Contact an admin.”. Mobile keeps `.mobile-logout`.

- The role in member editing becomes a `fieldset.member-role-options` radio list: each row is a native radio, with the name (weight 600, serving as the radio's name) and below it small text-subtle text listing what it can do (`aria-describedby`); the three built-in roles come first, custom roles after. Below the member list, `.member-roles` is the “Role” section: `.role-row` lays out the name (built-in roles get a neutral “Built-in” badge), a permission summary and “N members”; custom roles also get secondary edit/delete (delete is disabled while members still have the role, with a title explaining why). Adding/editing a role reuses `.member-dialog`: role name and an “Allowed features” checkbox list. Checking “Publish, retry, and cancel” also checks “Edit publishing drafts”, and unchecking the latter also unchecks the former. On the Publish page, without `publish.submit`, muted text replaces the “Publish / Schedule” button, and cancel schedule, retry and reapply buttons are hidden.
- The members page uses `.section-card.members-card`, with one primary “Add member” on the right of the title row; `.list-row.member-row` inside `.list-box.member-list` lays out name/username, role, brands, status and a secondary edit. Name in weight 600, username text-subtle; brands listed with commas, single-line truncated with a full title. Status uses ready/neutral/pending. At 390px the name and role share a row, edit is on the right, and the rest wraps naturally.
- Add and edit reuse the existing modal frame; `.member-dialog` has dialog/aria-modal, title association, Esc, Tab focus cycling and focus restoration after closing. Roles use the `.member-role-options` radio list; non-admins get brand checkboxes, with a single brand checked by default. For admins the brand checkboxes are hidden and “Admins can access all brands” is shown.
- Submit uses primary; cancel / copy / reset password / enable use secondary; disable uses primary danger with a second confirmation through ConfirmDialog. Protection rule errors use `.notice.danger`; window.confirm is not used. Each submit area has only one primary submit button.
- After the My account password form, admins get an extra `.recovery-code` section: the h3 “Password recovery code” and a status pill (set `.ready` / not set `.neutral`) on one row, a description, a “Confirm current password” field and a secondary “Generate recovery code / Generate new recovery code”. On success it reuses `.member-dialog` and `.temporary-password` to show the recovery code once, with secondary copy and “I've saved it”.
- First-time setup page: when the database has no accounts, the signed-out screen shows first-time setup instead, reusing the sign-in page layout and field styles. On the left, the eyebrow “First-time setup” + “Welcome to your marketing workbench.”; on the right, h2 “Create the admin”, admin username, password, re-enter password, brand name and a primary “Create and sign in”. If the two passwords differ, role=alert shows “The passwords don't match” and nothing is submitted. When opened from a non-local URL it shows only “Finish setup on the host computer” and an explanation, with no form. On success it goes straight into the workbench; afterwards only the sign-in page is shown.
- On the sign-in page, below “For authorized team members only”, there is a collapsed `.login-forgot` “Forgot password?”: an explanation for members, the admin recovery code form rendered only when expanded (admin username, recovery code, new password twice, primary “Reset password”; labels don't duplicate the sign-in form's names), the host command `.login-command` for when there is no recovery code, and a lockout reminder.
